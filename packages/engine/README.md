# narrarium-engine

Shared Narrarium engine: the **autopilot**, the **director**, the **simulated readers** and the **personal-server sync**. The same code runs in the Narrarium web app (browser) and in [`narrarium-server`](../server/README.md) (Node.js), so a book behaves identically wherever its autopilot runs.

The package is isomorphic: it only uses `fetch`, Web Crypto, `AbortController` and `structuredClone`, with no Node or DOM APIs.

## Install

```bash
npm install narrarium-engine
```

## Running the autopilot

A host provides two adapters: a `BookStore` over the book files and an `AiPort` over its AI configuration.

```ts
import { AutopilotSession, createFetchAi, pickAiRuntimeConfig } from "narrarium-engine";

const session = new AutopilotSession({
  bookId: "my-book",
  store,                                  // your BookStore
  ai: createFetchAi(pickAiRuntimeConfig(settings)),
  host: "server",
  hostLabel: "my laptop",
});

session.subscribe((event) => console.log(event.type, event));
await session.start({
  brief: { idea: "A harbor town built on glass hides a lie.", wordsPerScene: 1400 }, // the chapters are the outline's entries
  options: { pauseAfterPlan: true },
});
await session.waitForIdle();
```

Every step is one atomic commit of the book files plus `autopilot/state.json` and `autopilot/activity.json`. A step whose files changed in the meantime (for example because the author edited them) is never overwritten: it is repeated on the latest text.

### Session options

| Option | Meaning |
|---|---|
| `bookId`, `store`, `ai`, `host`, `hostLabel` | Required: the book, its `BookStore`, the `AiPort`, `"browser"` or `"server"`, and the name the author sees. |
| `hostId` | Stable identity of the host (device or server id). Without it the label identifies the host. |
| `ownRunnerAlive` | Whether a run recorded by this same host is alive outside this session (another tab). Without it such a run is taken for interrupted. |
| `hooks` | `beforeStep(signal)`, `afterCommit({ task, message, paths })` and `afterChapter({ chapterNumber, title })`, for a host that syncs. Which of the last two is called, and when, is decided by the engine from where the book is published: see *Quick controls → Publishing*. |
| `defaultPublish` | Where the host publishes when the author has not chosen (`options.publishEvery`): `"step"`, `"chapter"` or `"off"`. Without it a server host publishes after every step, as it always did, and a browser host as `options.syncAfterChapter` says. |
| `now`, `maxEvents` | The clock, and how many live events are kept for late subscribers (400). |
| `retryDelayMs` | The base delay of the retries of a failed step (4000 ms): see *Retries*. Every wait scales with it, the waits of «Retry later» (`options.longRetry`) too; `0` makes them all instant. |
| `random` | Source of the retry jitter, in [0, 1) (default `Math.random`). |
| `heartbeatMs` | While a run is active the session emits a `state` event this often (default 30 000 ms), with the run's heartbeat in memory; nothing is saved for it. `0` switches it off. |
| `persistHeartbeatMs` | The longest silence of `autopilot/state.json` during a run (default 300 000 ms): after it the run saves a fresh `runner.heartbeatAt`, so that another host does not take a long step for a dead run. `0` switches it off. |

A run whose heartbeat is older than `RUNNER_STALE_MINUTES` (20) is taken for dead. `runnerActivity(state)` says `"none"`, `"active"` or `"stale"`, and `runnerHeartbeatAgeMs(state)` how old the heartbeat is, in milliseconds, for a state and for the summary of a live `state` event (`null` when nobody runs).

### Pipeline

1. **Concept** — story design, world context, characters, locations, factions and secrets (skipped when the book already has a design or prose). The author's outline, when there is one, is binding for it too.
2. **Summaries of the author's chapters** — only for a book with chapters written by the author: see *Chapters the author wrote*.
3. **Plan** — chapter plan, following the author's outline as binding when there is one, and filling the outline with what it planned; simulated readers react to it and the director approves it or asks for changes (judging with the method and the severity of the evaluation style). The run can pause here for the author. See *Outline (Scaletta)*.
4. **Per chapter** — when the author changed the outline of the chapter since it was planned, the chapter is planned again (`replan`); then the scene plan, prose scene by scene (streamed), then the review cycle:
   - blind simulated readers (no canon, no secrets) and a panel summary;
   - specialists (continuity, canon, secrets, timeline, voice, style, pacing) with evidence anchored in the text, and the criteria of the evaluation style;
   - the **director** accepts or rejects every finding, judging with the evaluation style; the software, not the model, derives the repairs;
   - accepted fixes are applied; a new round verifies them, up to the director's round limit;
   - consolidation: chapter summary, recap, story so far, `plot.md`.
5. **Final** — the director's judgement on the whole book, with the evaluation style.

### Author interventions

`session.intervene({ scope, text, interrupt? })`:

- `next_step` — delivered once to the next writing step;
- `from_now` — a permanent rule for every following step, the director included;
- `rewrite` — the director picks the written scenes that must change; they are rewritten and reviewed again.

With `interrupt: true` the running step is abandoned and repeated with the new instruction. An intervention is saved at once, also while a step runs.

Permanent rules (`from_now`) are edited with `session.updateRule(index, text, expectedText?)` and `session.removeRule(index, expectedText?)`; `expectedText` is the rule as the author saw it, and a rule that changed in the meantime is never overwritten. A rule that cannot be saved throws `AutopilotRuleError`, whose `code` is `rule_empty`, `rule_too_long` (a rule is at most `MAX_RULE_CHARACTERS`, 800, because it goes into every request; it is refused, never cut), `rule_not_found`, `rule_changed` or `rule_duplicate`. The author's answer to a question of the director (`QuestionAnswer`) is a note used once; with `asRule: true` it becomes a permanent rule instead (never the default).

### Quick controls

What the web app's quick-command bar uses: pause at the end of the chapter, the limits of one run, where the book is published, the settings that can change while a run goes on, and «Retry now». They live here, once, so the browser and the personal server behave the same.

**Pausing.** `session.pause(mode)` takes `"now"` (the request in flight is abandoned), `"after-step"` (the default: the step in flight finishes and is saved, then the run pauses) or `"after-chapter"` (the step in flight finishes and the run goes on to the end of the chapter in progress, its closing and the publishing of the chapter included, then pauses with `Chapter N completed: paused, as you asked.`, in the language of the book). It answers whether there was a run, or a start in flight, to ask.

- A chapter is *in progress* from the moment its scenes are planned until it is closed. With none in progress (the concept, the plan, the summaries of the author's chapters, the first step of a chapter that has not started, the moment between two chapters) it is `"after-step"`, and so is a wait before the retry of such a step; the wait before the retry of a step of the chapter goes on, because the chapter still has to be finished. A request made at the boundary, right after a chapter was closed, pauses before the next one starts. After the last step of the book the run is complete, and says so.
- The stricter request counts, whatever the order: `"now"`, then `"after-step"`, then `"after-chapter"`. A request made while `start()` is in flight is kept for the run.
- `session.cancelPause()` takes back a pause that is waiting (`"after-step"` or `"after-chapter"`) without stopping anything, and answers whether there was one. A `"now"` that happened cannot be taken back. `AutopilotRun` has the same: `stopAfterChapter()`, `cancelPause()` and `pausePending`.
- When the run ends for it, `run-ended` carries `code: "chapterPause"`. If the option `pauseAfterEachChapter` would pause at the same moment, the request that was just made is the one that is said.

**Limits of one run.** `session.start({ limits: { steps, chapters } })` pauses the run after that many steps saved, or chapters completed, by this run. Nothing of it is saved: the next run has no limit unless it asks. A value that is not a whole number above zero is no limit (`normalizeRunLimits`). A step that fails or is abandoned does not count; with `steps: 1` a run makes one step (also one of the plan, or the final judgement) and stops, so three of them make three steps and three commits. `chapters` is the same limit as the saved option `chaptersPerRun`: the stricter of the two counts. A limit never takes the place of a reason the book has to stop (a plan that waits for the author, a question, a complete book), and the pause the author asked for is the one reported when both are due at once. `run-ended` carries `code: "stepLimit"` or `code: "chapterLimit"`.

**Publishing.** `options.publishEvery` is `"step"` (after every saved step, and again when a chapter is closed, so that the chapter is published whole), `"chapter"` (when a chapter is closed) or `"off"` (never). It is saved with the other options and can change while a run goes on. `effectivePublish(options, defaultPublish)` is the one rule that says where the book is published: `options.publishEvery`, else the host's `defaultPublish`, else the older option `options.syncAfterChapter` (`"chapter"` when it is on, `"off"` when it is off), so the files of an older engine behave as they did. A host that passes no `defaultPublish` gets `hostDefaultPublish(host)`: a `"server"` host publishes after every step (its `afterCommit` hook has always been called then), a `"browser"` host has none, so `syncAfterChapter` decides.

The engine applies it, so a host only says *how* to publish: `hooks.afterCommit` is called after every saved step when the way is `"step"`; `hooks.afterChapter` when a chapter is closed and the way is `"chapter"` or `"step"`; neither when it is `"off"`. A host that publishes in every way needs both hooks. The way is read at the end of every step and of every chapter, from the state that step saved. A publish that fails is reported as before (a `sync` event with `syncFailed`, or `publishFailed` for a chapter) and never stops the run. `beforeStep` is not a publish: it is called before every step whatever the way.

**Changing settings during a run.** `session.updateOptions(partial)` saves the options and answers the saved state. While a run is active only `publishEvery` (`null` takes the choice back, so that the host decides again), `pauseAfterEachChapter`, `frozenEdits` (see *Frozen chapters*), `longRetry` («Retry later», `null` turns it off: see *Retries*) and `resumeAfterRestart` («Resume after a restart», below) can change (`LIVE_AUTOPILOT_OPTIONS`); any other option throws `AutopilotBusyError`, as `configure` does, and nothing of that request is applied. With no run active any option can change. The change is a compare-and-swap commit, like an intervention: the step in flight is neither failed nor repeated, the run takes the author's value into the state the step saves (`reconcileAuthorChanges`) and reads it at the end of that step, or of the chapter (`longRetry` when a step has failed: a run that waits for it stops when it is turned off, and new minutes or cycles count from the next cycle). A value nobody knows changes nothing, and a request that changes nothing writes nothing.

**Retry now.** `session.retryNow()` ends the wait before the next attempt of a failed step (a quick retry, or a cycle of «Retry later») so that the attempt starts at once: see *Retries*.

**Resume after a restart.** `options.resumeAfterRestart` («Resume after a restart», «Riprendi da solo dopo un riavvio del server») is `true` or absent: off, the default, also for every book written before it (a value that is not `true` or `false` changes nothing, as for every switch of the options). It is saved with the other options and can change while a run goes on. Only a personal server reads it, when it starts again; the engine gives it what it needs:

- `session.stopForShutdown()` is the host's own stop (Ctrl+C, a service stop): it stops the run as `pause("now")` does (a start in flight is stopped as soon as its run exists) and the run ends `paused` with `state.stoppedBy: "server-shutdown"`, the message «In pausa perché il server si è fermato.» (*Paused because the server stopped.*, in the language of the book) and the `run-ended` code `serverShutdown`. A pause the author asked for before it (`now`, or one that waits for the end of the step or of the chapter) stays the author's, and the state says nothing of the server. It answers whether a run was active or starting.
- `state.stoppedBy` is written only so, only on a `paused` state, and read only so from a file: a missing field is none (null), as in the files of older engines, and any other value is dropped. Any start (a resume, a single step, a start of the host) takes it away when the run saves its start (`withoutStopCause`), and so does a pause of the author with no run active: `session.pause()` then answers `false` and writes nothing, and the host calls `session.forgetStopCause()`, which answers the saved state, or `null` (and writes nothing) when there was nothing to take away.
- `session.restartResumeCause()` reads, and changes nothing: `"server-shutdown"` for a run paused so, `"interrupted"` for a state that still says `running` with this host's runner (its process ended without pausing it) or with a runner silent for longer than `RUNNER_STALE_MINUTES`, and `null` for anything else (the option off, a pause of the author or of the run itself, a live run of another host, a run active here, no state, a state that cannot be read).
- `session.start({ afterRestart: true })` is the host's resume after a restart (never taken from a request): the run says so first, right after `run-started`, with the insight `resumedAfterRestart` («Ripreso da solo dopo il riavvio del server.», *Resumed by itself after the server restarted.*, in the language of the book).
- `session.holdAfterRestart({ times, hours })` leaves such a run to the author when the host will not resume it (it already did so `times` times in the last `hours` hours): the state is `paused`, without `stoppedBy` and without a runner, with a message that says why («Non ripreso dopo il riavvio del server: l'autopilot si è già ripreso da solo 3 volte nelle ultime 24 ore. Riprendilo quando vuoi.», *Not resumed after the server restart: the autopilot already resumed by itself 3 times in the last 24 hours. Resume it when you are ready.*). It writes nothing for a run that is no longer such a run, nor for a book without a state, and answers `null` then.

**What the summary says.** `AutopilotStateSummary`, which the `state` events carry and `snapshot().summary` holds for a client that connects later, has five fields that are never saved: `frozenChanges` (how many chapters have a change that waits for the author, absent when none does: see *Frozen chapters*), `pausePending` (`"after-step"`, `"after-chapter"` or `null`), `limits` (`{ steps?, chapters?, stepsDone, chaptersDone }` of the run in progress, `null` when it has none or is over; `chapters` is the stricter of the run's limit and `chaptersPerRun`), `publish` (`effectivePublish` of the options and the host's default) and `retry` (the retry the run is waiting for, present only while it is, with `longTerm` in a wait of «Retry later»: see *What the interface reads*). A summary made from the state file alone (`summarizeAutopilotState(state)`) has no `frozenChanges`, no `pausePending`, no `limits` and no `retry`: nothing in the file says them, so a client takes them from the events and the snapshot. They change without the state being written, so `updatedAt` does not move: every change of the pause that waits, and every saved step, is a `state` event, and a client keeps the newest event it has seen, whatever its `updatedAt`.

**Message codes.** `run-ended` and `insight` events carry a `code` when a client can say it in its own language: `chapterPause`, `stepLimit` and `chapterLimit` join `takenOver` and the others (`AutopilotMessageCode`). The `message` of the event, and of the saved state, is always in the language of the book. The insights about the outline have codes of their own and say which chapter they are about (`chapterNumber`, and `ghostwriter` for one that does not exist): `outlineGhostwriter`, `outlineChanged`, `outlineRemoved`, `outlineChangedWhileWriting`, `outlineWrittenChanged`, `outlineRemovedWritten`, `outlineWrittenAuto` and `outlineWarnings` (see *Outline (Scaletta)*); so do the insights about the frozen chapters: `frozenMigrated`, `frozenChanged`, `frozenAuto`, `frozenReviewed`, `frozenCleared` and `frozenInvalid` (see *Frozen chapters*). The retries have theirs: `failureRetry` (a quick retry), `longRetryWait` (a wait of «Retry later», with `cycle`, `cycles` and `waitMs`), `retrySkipped` («Retry now» ended a wait, with the `waitMs` that was left), and two that end a run, as the `code` of `run-ended` (and, the first, as an insight with the last `cycle` and `cycles`): `longRetryExhausted` (the cycles are used up) and `longRetryOff` («Retry later» was turned off while the run waited for it). See *Retries*. A restart of the server has two: `serverShutdown` (the `code` of `run-ended` when the server's stop paused the run) and `resumedAfterRestart` (an insight: the server resumed the run by itself). See *Resume after a restart*.

### What the interface reads

Data the web app's pages used to have to guess (from the text of a step, from the 200 activities of the log) and now find in the state and in the summary. All of it is additive: every field is absent until the engine that writes it has something to say, and a state or a summary without one is what an older engine wrote.

**The final verdict.** When the `final` step is done, `state.finalReview` is `{ verdict, score, text, at }`: the director's judgement of the whole book as data, where the line of the step said `approve 8/10 — …`. `verdict` is `"approve"` or `"revise"` (a `rewrite` is a `revise`, and so is an approval withheld because its score is under the `approvalScore` of `director.md`); the book is closed all the same, as it always was. `score` is on the scale of the chapters (0-10, one decimal at most), `text` is the director's summary cut with `clipText` at `FINAL_REVIEW_TEXT_CHARACTERS` (1200) characters, and `at` is when the director gave it. `summary.finalReview` has the same fields with the text cut at `FINAL_REVIEW_SUMMARY_CHARACTERS` (400). A book that is not complete any more (its chapters were extended, or a `rewrite` reopened it) has none until the final step is done again.

**Working time.** `stats.workedMs` is the sum, over every run, of the durations of the steps that were saved, each from its start to its end as its activity shows. Not counted: the wait for the author, the pauses between runs, the attempts of a step that failed and the waits between them (a step counts the attempt that was saved), the steps that were abandoned. A whole number of milliseconds, never negative, in the state (so it outlives the 200 activities of the log) and in `summary.stats`. A state written before it existed has none (and neither has its summary: not zero, not `NaN`) and it counts from zero at the first step that is saved. `stats.workedMsSince` is the ISO time (UTC, `2026-02-01T08:00:00.000Z`) at which the first step that the count included began: the count is born with the first step it counts, and the moment is written then, once, and never changed after (not by the steps that follow, not by another run), so that a client can say *since when* the time is counted. A book whose count began before the moment was written has `workedMs` and no `workedMsSince`, and the engine does not make one up: it cannot know. `stats.workedMsPartial: true` says that the count began on a book that had already saved steps (an engine that did not count wrote them): the time is then the time since `workedMsSince`, not of the whole book (a client says *at least*, or *since*). It is written once, with `workedMsSince`, and read from a file only when it is `true` and next to `workedMs`. Read from a file it is a date or a date and time with its zone (`2026-02-01`, `2026-02-01T10:00:00+02:00`, said again in UTC) and only next to `workedMs`; any other value is dropped.

**Errors.** A step that fails puts `errorKind` and `errorDetail` in its activity (the `task-finished` event carries them too) and, when it ends the run, in `state.lastError`; `summary.lastError` has the same two under the names `kind` and `detail` as well. A step that the author cancelled is no failure and has neither. `state.lastError` (and `summary.lastError`) also says *which* step failed: `activityId` is the id of its activity, the one in the log and in the `task-finished` event (the last attempt, when the step was retried), so a client does not have to guess it from the time. A failure that belongs to no step (the ceiling of steps of a run) has none, and neither has an error saved by an engine that did not say it; the id is read from a file only when it is short and made of letters, digits and `_ . : -`. When «Retry later» is what stopped the run, `state.lastError.code` (and `summary.lastError.code`) says it with the code the `run-ended` event carries: `longRetryExhausted` (the step failed again after its last cycle) or `longRetryOff` (it was turned off while the run waited for it): a page opened after the run, or another device, reads it from the state and can say that «Riprova più tardi» ended the run, which the event, seen only by the client that was connected, could not tell it. `LAST_ERROR_CODES` is the closed list; it is absent for any other failure, and a value of a file that is not in the list is dropped. `AutopilotErrorKind` is a closed list (`AUTOPILOT_ERROR_KINDS`), told from what the engine knows of its errors (`classifyAutopilotError(error)` is the one function, a status or a flag deciding before the words do):

| Kind | What it is |
|---|---|
| `auth` | 401 or 403: a key, or a permission. |
| `rate_limit` | 429. |
| `timeout` | The request ran out of time (`timedOut`: the provider did not begin answering, it went silent, or the call took too long), or 408. |
| `network` | The provider could not be reached, or the connection dropped: no status, `transient`, or the words of a network failure. |
| `provider` | Any other failure of the provider (another 4xx or 5xx, an error inside the stream) or of its reply (`AiReplyRejectedError`, a reply that is not JSON). |
| `truncated` | The reply was cut by the output limit (`truncated`, `reasoningOnly` included). |
| `refused` | Nothing was called: the privacy setting for fallbacks left no candidate (`AiFallbackBlockedError`), or no model is routed to the task (`AiUnavailableError`). |
| `budget` | The routing limits leave no candidate to call (`AiRoutingBudgetError`). |
| `limit` | No context window holds the prompt (`AiPromptTooLargeError`), or the run's own ceiling of steps. |
| `profile` | A file of the book the autopilot would rewrite cannot be read: its frontmatter is not valid YAML (`FrontmatterError`). The author fixes it. |
| `config` | The AI configuration has to change, and repeating the step cannot help: with "Tools only" on, no model of the task can call a function (`AiToolsRequiredError`, see *Tools only*). Nothing was sent. |
| `conflict` | A file changed under the step and the retries are used up (`BookConflictError`); or, on a personal server, the server's work conflicts with GitHub (code `github_conflict`, with `githubConflicts` in the detail: the author chooses the version of each file, see *The personal server client*). |
| `unknown` | Everything else. |

`errorDetail` is `{ status?, endpoint?, model?, provider?, integration?, retryAfterMs?, attempt?, retries?, timeoutMs?, timeoutPhase?, githubConflicts?, transport?, route? }` (`route`: every candidate of the route of the call that failed, in the order the author wrote it: see *The route of a call*), short and with no secret in any field: `githubConflicts` is there only for a conflict with GitHub (an error whose `code` is `GITHUB_CONFLICT_CODE`, `"github_conflict"`, and whose `total` says how many files: never retried, the author chooses), a whole number from 1 (read back from a file the same way); `status` is the HTTP status when the provider answered; `retryAfterMs` is what the provider asked for with `Retry-After` in milliseconds, on a 429 or a 503 only and only when it said (the engine's client keeps at most five minutes of it, `0` is a value, and a value read from a file is a whole number from 0 to a day, else it is dropped), so that a client can say *the provider asks to wait 30 s* without guessing it from the retry; `endpoint` is only the **origin** of the integration's address (`new URL(address).origin`: never a path, a query, a fragment or credentials, and nothing at all for an address that is not a web address); `model`, `provider` and `integration` (the id) are passed through `redactSecrets` and cut at 160 characters. `attempt` and `retries` are there only for a failure that is retried: the retry it belongs to (the one that followed it, or the last one made when the run gave up) and how many retries this kind of failure gets, the numbers of the `failureRetry` insight; a failure that is never retried (a 401) has neither. `timeoutPhase` (`"start"`, `"idle"` or `"total"`) and `timeoutMs` are there only for a timeout of the engine's client: which deadline ran out (the provider did not begin answering, it went silent while it answered, or the call took longer than any call may) and how long it was, in milliseconds (a value read from a file is a whole number from 1 ms to a day, else it is dropped); see *Timeouts and streaming*. Where an error came from is `AiProviderError.target` (`{ provider, model, integrationId, endpoint? }`, the endpoint already an origin), which the engine's client sets on the error of the last candidate it tried; it is separate from the error's own `model`, `provider` and `integrationId`, whose presence means that the model had started to answer and is billed. `transport` is there for a call that failed after the provider answered and whose response said something beyond its status (it carried bytes, a request id, an end or a finish reason): `{ status?, bytes?, chunks?, events?, lastChunkAfterMs?, silentMs?, end?, finishReason?, usageReceived?, usageRequested?, tail?, requestId?, partialCharacters? }`, the numbers of `AiTransportDiagnostics`, the last 300 characters of the stream (credentials replaced, no reasoning) and how many characters of the reply had arrived; every field is checked when a state is read, and a file cannot make one longer or put a key in it. A state written before the errors were classified has `lastError` with a message and no kind: `summary.lastError` then has none either.

**The retry that is waiting.** While the run waits to try a failed step again, `summary.retry` is `{ at, attempt, retries }`: `at` is the ISO time of the next attempt, `attempt` and `retries` those of the `failureRetry` insight (`retry 2 of 3`). In a wait of «Retry later» it is `{ at, attempt, retries, longTerm: { cycle, cycles } }`: `attempt` and `retries` are then the quick retries that were made, `cycle` the cycle of the wait (from 1) and `cycles` how many there are, `null` for no limit (the numbers of the `longRetryWait` insight: «ripartenza 2 di 3», *restart 2 of 3*); the rest of the summary is what it always was. It is never saved, and it is the fourth field of the summary that only a live session knows (see *What the summary says*). Every change is a `state` event, so a client counts down without guessing: one event when the wait begins (right after the `failureRetry` or `longRetryWait` insight), one when it is over and the attempt starts (the summary has no `retry` then; after «Retry now» that event follows the `retrySkipped` insight at once), and the last summary of a run that ends, or is paused, during the wait has none. A host that gets the state from a `state` event replaces its summary by the newest one it has seen, and so the retry goes away. A client offers «Retry now» (`session.retryNow()`, or `retryNow(bookId)` of the server's client) while `retry` is there.

**Retry later.** `options.longRetry` is `{ everyMinutes, cycles }` (`AutopilotLongRetry`: `everyMinutes` a whole number from 1 to `LONG_RETRY_MAX_MINUTES`, 10080, a week; `cycles` a whole number from 1 to `LONG_RETRY_MAX_CYCLES`, 1000, or `"unlimited"`), saved with the other options, or absent: off, the default, also for every book written before it. A value that is not a policy is read as off (from a file), or changes nothing (in a request): never made into one, never cut to fit (`readLongRetry`); `longRetryProblem(value)` says in words why a value a host is about to send is not one (`null` for a policy, and for `null`, which turns it off). See *Retries* for what it does.

**Dates in what the author reads.** A date the engine writes in a text for the author (the question about a frozen chapter that changed, the message of the stop, the notice of `frozenEdits: "notify"`) is written as the author reads one, in the language of the book: «congelato il 21 novembre 2026», *frozen on 21 November 2026*, the day in UTC and nothing taken from the machine (its time zone, its language). `formatBookDate(moment, language)` is the one function (Italian, and English for every other language, as the words around it are). The data keep their ISO times (`frozenAt`, `askedAt`, `created_at`…).

**The rounds of every chapter.** `PlannedChapter.rounds` is a compact history of the rounds of review of a chapter that closed: one `{ director?, readers?, verdict?, accepted?, rejected? }` for each, oldest first, written when the director judges the round and kept after the chapter is closed (`state.review` is the round in progress and is cleared when the chapter closes). `director` is the director's vote and `readers` the average of the simulated readers' votes (0-10, one decimal at most); `accepted` and `rejected` are what the director decided, whole numbers. `verdict` is `"approve"` (the round closed the chapter) or `"revise"` (it sent the chapter back for fixes): the verdict the plan acted on, which is not always the one the model gave (an approval under the `approvalScore` of `director.md` is withheld and is a `revise`, and a revision with no applicable fix is an `approve`), so a client reads it here instead of from the text of the log. A round saved by an engine that did not say it has none; a `verdict` read from a file is `approve` or `revise` (case and spaces do not matter) or it is dropped, and a verdict with no number is no round. The readers read a chapter once, in the first round of its review, so only that round has `readers` (a chapter rewritten after the author's request is reviewed again without readers). A chapter keeps at most `MAX_CHAPTER_ROUNDS` (8): a chapter that is rewritten adds the rounds of its new review and the oldest leave. A chapter that was never reviewed has none (`rounds` is absent, never an empty list), and the history survives the plan being made again around the chapters when the author raises the number of chapters of a finished book. In `state.json` every round takes one line of about 100 bytes (the file is still plain JSON), so a book of 5000 chapters with three rounds each adds about 1.4 MiB, and with the eight rounds every chapter may keep about 3.9 MiB, to a file the server accepts up to 8 MiB.

**The step that is answering.** `task-progress` says that the model of the running step is answering. A step that writes prose says it as it always did: `preview` (the tail of the text so far) and `characters`, at most about three times a second. A step that answers with a structured value (the concept, the plan, a reader's evaluation, the director's decisions, the summary of a scene) says it with numbers only: `{ type: "task-progress", activityId, characters, bytes, preview: "" }`, where `bytes` is what has arrived of the reply and `characters` the characters of its function arguments, never a word of the reply, and **one event a second** for each step at most (the client reports up to four times a second, and the stream of a server is not flooded). It only exists while the provider streams: with `streamMode: "off"` there is nothing to say until the reply is whole. Like every `task-progress` it is never saved (not in `state.json`, not in the log, not a commit) and never replayed to a client that connects later; `snapshot().live` carries what a client shows of the step (see below). The event is the same one the prose steps have: `preview` stays a string (empty here), and `bytes` is the only new field, so a client that knows nothing of it reads `characters` and an empty preview. A step that writes a scene and then asks for its summary says both kinds one after the other, as two calls of the step. A client of the personal server gets the events as they are (the engine's client hands over every message of the stream, and a type it does not know is the host's to ignore). **What a client shows of it** (`AutopilotLive`, which `snapshot().live` is) follows the events by one rule, `applyLiveProgress(live, event)` (`startLive(activity)` at `task-started`, `normalizeLive(value)` for a live part read from another host), which the web app uses too: every progress says which call of the step it is (`callSeq`, from 1; `callId` when the book keeps records), and a call starts from nothing, so nothing of a scene is shown while its summary streams and nothing of one call while the next answers (an engine that names no calls is read by the kind and the bytes: prose after a structured reply, a structured reply after prose, or numbers whose bytes went back, are another call). The text of a call (its prose, or the JSON of a structured reply, `json: true`) replaces what was shown and never goes back to nothing until the call ends: the empty text that says a new attempt begins changes nothing, and the new attempt takes the place of the old one when it writes. A progress without a `preview` keeps the text shown. The numbers of a structured reply set `bytes` and never touch the text (a shorter JSON, the next attempt's, drops the bytes of the one before), and its count is the JSON's (`characters` of the numbers event is the JSON's once it streams, the client's own count before), so a reply that streams its JSON keeps it on screen while its numbers arrive, and one that does not says «answering» with its bytes.

**What a model declares.** The safe view of the AI configuration (`redactAiRuntimeConfig(config).integrations[].models[]`, which the personal server's `GET /ai` forwards as it is) says, for every model, what its configuration declares: `supportsToolCalls`, `supportsStreaming`, `supportsReasoning`, `supportsVision`, `maxInputTokens` and `maxOutputTokens`, and the `reasoningParameter` that says how its thinking level is sent (the "Thinking parameter" of the model, «Parametro del thinking»: `reasoning_effort`, `chat_template_kwargs.reasoning_strength` or `none`, with `AI_REASONING_PARAMETERS` for the list and `suggestedReasoningParameter(name, underlyingModel?)` for a hint that a screen may offer, which the engine never applies by itself), each only when it is declared or set (a model that declares nothing is `{ name, capabilities }`, as it always was). An attempt says what it did not do because of it: `onAttempt.notes` (English, absent when there is nothing to say; `ChatRequest.notes` for a host that builds the request itself), and `onAttempt.reasoningParameter` where the level went when it did not go as `reasoning_effort`. A reply cut with nothing written by a model declared as reasoning is a `truncated` error with `reasoningOnly`, so its `errorKind` is `truncated` like any cut reply. What an endpoint says of its models, and whether it answers at all, is what `fetchModelCatalog` and `probeEndpoint` return: see *Model catalog and declared capabilities*. All of it is additive: a configuration that declares nothing reads and runs as it always did.

**The outline and the ghostwriter of every chapter.** `PlannedChapter.ghostwriter` is the ghostwriter the outline gives the chapter (the slug of `ghostwriters/<slug>.md`), absent when it is the book's; the chapter's `chapter.md` says it too, so a page that shows the chapter reads it where it always did. `PlannedChapter.outlineDigest` is the digest of the chapter's entry of the outline (`outlineEntryDigest`) as it was when the plan followed it, or wrote it: an entry whose `contentDigest` is not the chapter's `outlineDigest` has been changed by the author since (`outlinePlanStatus(reader, state, language)` says which ones, for a chapter not written yet and for the written ones). `plan.removedChapters` lists the chapters taken out of the plan because the author deleted their entry. `options.fillOutline` (on by default, saved with the other options, not changeable while a run is active) says whether the plan fills the outline. `state.concept.logline` is the pitch of the concept, which becomes the description of the outline. New task kind: `replan` (a chapter planned again from its new entry, or taken out of the plan). New insight codes: `outlineGhostwriter`, `outlineChanged`, `outlineRemoved`, `outlineChangedWhileWriting` (the entry of a chapter still being written changed: it is decided once the chapter is closed), `outlineWrittenChanged` (the entry of a written chapter changed, and with `frozenEdits: "notify"` it is only said), `outlineRemovedWritten` (a written chapter is no longer in the outline: it stays in the book), `outlineWarnings`, each with `chapterNumber` (see *Outline (Scaletta)*). An engine from before them said the first and the third with `outlineWrittenChanged` as well. An engine from before these fields drops them on its first write; the outline files stay, the next plan of a newer engine reads them again, and a chapter whose plan lost its digest is not planned again from an entry the autopilot wrote (only from one of the author).

**Frozen chapters.** What the pages read of them (see *Frozen chapters* for what they mean): `summary.frozenChanges` (not saved: how many chapters have a change that waits for the author's decision, as the run found it before its last step or the last `frozenStatus()`; absent when none waits, as `retry` is, until one of them looked, and from a summary made from the state file alone); `options.frozenEdits` (`"ask"`, `"auto"`, `"notify"`); `state.pendingReviews` (the decisions recorded: `{ id, kind, number, action, fingerprint, at, note?, auto?, started? }`, `started` while one is carried out, with `phase` and the chapter as it was `before`); `state.question` of kind `frozen-change` or `outline-change`, with `choices` (`{ id, label }`, the labels in the language of the book), `options` (the same labels) and `frozen` (`{ kind, number, slug, fingerprint, title?, by?, frozenAt?, changed?, others? }`); `QuestionAnswer.choice`; `state.frozenSince` and `state.frozenSeen` (the engine's bookkeeping); `state.review.authorEdit` (the round of review of an author's change); `state.revision.afterChapter`, `onlyChapter` and `source` (a revision that comes from a change: `{ kind, chapterNumber, note?, auto?, before?, after? }`); the snapshot's `ChapterInfo.frozen`, `frozenProblem`, `bodyDigest` and `document`, and `ParagraphInfo.bodyDigest`. New task kind: `freeze` (without the model). New insight codes to say in the language of the interface, each with `chapterNumber` but the first: `frozenMigrated` (the chapters an older engine approved are frozen now), `frozenChanged` (`notify`: a frozen chapter changed), `frozenAuto` (`auto`: a change is reviewed and the book updated from it), `outlineWrittenAuto` (`auto`: a chapter is rewritten to follow its outline), `frozenReviewed` (a decision was carried out, or a change was marked as reviewed), `frozenCleared` (a change is gone: its question, or its decision, is dropped), `frozenInvalid` (a record that cannot be read; a warning). New kinds of question: `frozen-change`, `outline-change`; their choices are the actions, by id: `review-and-update`, `review-only`, `mark-reviewed`, `rewrite-to-outline`, `keep-text`.

**Older and newer engines.** Every new field is read tolerantly (a value that is not valid is dropped, never made up) and an older file reads as it always did. An engine from before these fields reads a file that has them without trouble but does not know them: `normalizeAutopilotState` of that engine drops `finalReview`, `stats.workedMs`, the kind and the detail of `lastError`, and the `rounds` of the chapters, so the first time it writes the state the history is lost (the activities keep their `errorKind` and `errorDetail`, which it does not look at). The worked time then starts again from zero in the engine that knows it, and the rounds start again with the next review. An engine that knows the rounds and the worked time but not what was added after them (the `verdict` of a round, `stats.workedMsSince`, `lastError.activityId` and the `retryAfterMs` of an error detail) drops those four on its first write, and the engine that knows them does not make them up again: a book that goes back and forth between the two keeps its rounds and its time, and loses the verdicts, the moment and the id of the failed step written meanwhile. The frozen chapters are the same story: an engine from before them drops `pendingReviews`, `frozenSince`, `frozenSeen`, `options.frozenEdits`, the `authorEdit` of a review and the `afterChapter`, `onlyChapter` and `source` of a revision, and reads a question about a change as a question of the director with free text (its `choices` and `frozen` dropped); the records in chapter.md stay. The engine that knows them then asks again about what is still changed, and a state without `frozenSince` freezes the chapters the autopilot approved, once, without asking. «Retry later» is the same story: an engine from before it drops `options.longRetry` (and `stats.workedMsPartial`) the first time it writes the state, so the option is off after that; a run of a newer engine that waits for it then stops as if the author had turned it off (`longRetryOff`). An engine that knows «Retry later» but not `lastError.code` drops the code the first time it writes the state: the error stays, and a page that opens after that cannot say what stopped the run (the `run-ended` event still says it to a client that was connected). A client that does not know a new code of an insight (`longRetryWait`, `retrySkipped`, `outlineChangedWhileWriting`, `outlineRemovedWritten`…) shows its `title`, which is always in the language of the book. «Resume after a restart» is the same story: an engine from before it drops `options.resumeAfterRestart` and `stoppedBy` the first time it writes the state, so the option is off after that and a run the server paused when it stopped reads as paused by the author: nothing resumes it by itself. A conflict with GitHub is the same: an engine from before it drops `errorDetail.githubConflicts` the first time it writes the state (the kind stays `conflict`), and a personal server from before it stops the run with an error of no kind whose words send the author to the web app, answers a sync with `409 sync_failed`, and has no list to resolve it (the client refuses it with `feature_unavailable`).

### Long books

There is no maximum number of chapters. A plan longer than `PLAN_BATCH_CHAPTERS` (20) is made of several `plan` steps, one per batch, so that no reply outgrows the model's output; `plan.revisionBatches` lists the first chapter of every batch a revision of the plan still has to regenerate, and `plan.skippedReaders` the readers whose reaction stayed incomplete after a retry and who are not asked again. The lists of chapters in a prompt are windowed around the chapter at hand (`outline`, at most `OUTLINE_MAX_CHARS`, 24 000 characters), so a prompt never outgrows its budget and the work to build it grows linearly with the book.

### Chapters the author wrote

A chapter written before the autopilot took over has no summary unless the author wrote one, and without it the story so far of the chapter that follows would start blind. Before anything is planned or written after them, the planner adds one `summarize-imported` step for every such chapter without a `summary`: the model of the `simple-tasks` route summarizes it in two to four sentences, and the summary is saved in its `chapter.md` (created when there is only a folder of scenes) and in its resume file when it has none. A chapter that already has a summary, in its file or in the plan, is skipped and its file is not touched; the plan learns the summaries the files have. One chapter is one step and one commit, with a title and a reason in the language of the book, so it respects pause and budget like any other step, is repeated safely and resumed where it stopped, and is never asked again once the summary is saved. A finished book is not summarized.

## The director

The director is the author's stand-in: it approves plans and chapters during the autopilot and can be asked at any time what it thinks of the book, a chapter or a scene:

```ts
import { askDirector } from "narrarium-engine";

const { opinion } = await askDirector({ store, ai, target: { kind: "chapter", chapter: "003-the-storm" }, question: "Is the ending strong enough?", save: true });
```

Its profile lives in `director.md` at the book root (persona, autonomy, strictness, approval score, review rounds, priorities, taste, red lines, simulated reader weights and a free vision). Saved opinions go to `evaluations/director/`.

Values are read as the author wrote them: an autonomy whatever its case (`Full`, `ask on critical`), numbers with their decimals (`approval_score: 7.5`, a reader weight of `0.4`) and a decimal comma (`'9,5'`).

### Profiles that cannot be read

`parseDirector`, `parseGhostwriter`, `parseReaderPersona` and `parseEvaluationStyle` never throw and never hide a problem: they return `warnings: string[]` (empty when the file is as it says), each naming the file. A warning is YAML that cannot be read (with its line), a value that is not understood (an autonomy nobody knows, a score that is not a number, a list that is not a list, a reader type that is none of `standard`, `genre`, `custom`, a switch that is neither yes nor no, a criterion of the evaluation style that cannot be read), and the profile then has the default for that value, as it always had. The defaults themselves carry `warnings: []`.

A profile with warnings is not what the author wrote, so the engine never goes on with it silently and never replaces the file with the defaults:

- before a step, the autopilot checks the director, the evaluation style (`evaluation-guidelines.md`, when the book has one), the files of the simulated readers when readers are used, and the ghostwriter of the chapter for a step that writes. When one has warnings it spends nothing, emits an insight with code `profileProblems` and stops with `status: "waiting-author"` and a `message` that lists the problems (in the language of the book); the author corrects the file and resumes.
- `askDirector` still gives its opinion, and reports the problems of `director.md` in `warnings` next to it.
- a host that saves a profile should not do it over a file that has warnings.

## Outline (Scaletta)

The outline is the author's chapter-by-chapter trace of the book: the idea, promise or pitch of the book (its description) and, for every chapter, a hypothetical title, what happens in it and, when it is not the book's, the ghostwriter that writes it. It is a main part of the book, useful without the autopilot too, kept in files of the book, and the autopilot follows it as binding. It is not `plot.md`, which the autopilot generates from the chapters it closes.

### The files

| Path | Frontmatter | Body |
|---|---|---|
| `outline/book.md` | `type: outline`, `id: outline:book`, `title?` (a working title: the book's own stays in `book.md`), `origin?`, `digest?` | The idea, promise or pitch of the book (the description), free Markdown, at most 1 000 000 characters. It is the brief's idea too: stored here and nowhere else. |
| `outline/_brief.md` | `type: outline-brief`, `id: outline:brief`, `genre?`, `audience?`, `wordsPerScene` (a whole number from 200 to 8 000; 1 400 when absent) | The synopsis, free Markdown. An `idea` key found here is ignored and never written. It is the brief of the autopilot, not an entry: see *The brief*. |
| `outline/chapters/<NNN>.md` | `type: outline-chapter`, `id: outline-chapter:<NNN>`, `number`, `title?` (the hypothetical title), `ghostwriter?` (the slug of `ghostwriters/<slug>.md`; absent: the book's), `origin: author \| autopilot`, `digest?` | What happens in the chapter, plain text. |

One file per chapter: the outline has no maximum, and no file grows with the book. `<NNN>` has the zero-padding of the chapter folders (`formatOrdinal`): `outlineChapterPath(7)` is `outline/chapters/007.md`, `outlineChapterPath(1500)` is `outline/chapters/1500.md`, and `parseOutlineChapterPath(path)` reads the number back. The number of an entry is the one of its file's name; a frontmatter that says another is a warning, and the name wins. The keys the format does not know are kept whenever the engine rewrites a file. The core (`narrarium`) has the same paths (`OUTLINE_BOOK_FILE`, `OUTLINE_CHAPTERS_DIRECTORY`, `outlineChapterPath`, `parseOutlineChapterPath`), validates the files with `outlineBookSchema` and `outlineChapterSchema` (passthrough), searches them and renames references in them with the rest of the book (`CONTENT_GLOB`), and its doctor warns, never errs, about a number that is not the file's and a ghostwriter that does not exist.

### Who wrote an entry: `origin` and `digest`

- `origin: author`, or no `origin`: the author's. It binds the autopilot, which never rewrites it.
- `origin: autopilot` with a `digest`: written by the autopilot from its plan. The digest is `outlineEntryDigest({ title, body, ghostwriter })` of what it wrote: sixteen hexadecimal characters of a SHA-256, where line endings and the spaces around the texts do not count. While the entry still matches its digest it is *intact*: the autopilot's own, which binds nothing and which the autopilot may write again when its plan changes. As soon as the author changes its title, its text or its ghostwriter it no longer matches it, and it is the author's.
- An entry whose frontmatter cannot be read is the author's: it is read as far as it can be (its text is all there), the author is told, and the autopilot never rewrites it.
- The description of the book follows the same rules, with `outlineBookDigest({ title, body })`.

`parseOutline(files)` (pure: no I/O) gives `{ book, chapters, warnings }`. Every entry has `number`, `title` (empty when it has none), `body`, `ghostwriter?`, `origin`, `digest?`, `contentDigest` (the digest of what it says now), `intact`, `unreadable?`, its `frontmatter` and the `hash` of its file. It never throws: two files for one chapter (`007.md` and `0007.md`: the one named as the core names it counts), a number that is not the file's, an `origin` nobody knows, a text over `OUTLINE_ENTRY_MAX_CHARS` (20 000 characters), YAML that cannot be read, a file of `outline/` that is not an entry and chapters without an entry between two that have one are warnings: `{ code, message, path?, number? }`, the message in English and naming the file.

### Editing it

`outlineChanges({ outline, edit, ghostwriters? })` makes an edit of the author into `{ changes, warnings }`: the `BookFileChange[]` of one commit, each expecting the file as it was read (`null`: a file that must not exist yet), so an edit made on an outline that changed in the meantime is refused by the store instead of overwriting it. `outline` is what `parseOutline` read, with the hashes of the files; `ghostwriters` the slugs of the book's ghostwriters (without it they are not checked). The edits:

| `edit` | What it does |
|---|---|
| `{ kind: "append", entry }` | A chapter after the last one. |
| `{ kind: "insert", at, entry }` | A chapter at position `at`; the entries from there on move one number up. Inserting at the head of an outline of 5000 chapters is 5000 renames and one new file, in the same list. |
| `{ kind: "move", from, to }` | The entry `from` goes to position `to`, the ones in between follow. |
| `{ kind: "remove", number, renumber? }` | Deletes the entry and leaves its number empty; with `renumber: true` the following ones move one number down. |
| `{ kind: "update", number, entry }` | Changes the `title`, the `body` or the `ghostwriter` given (`ghostwriter: null` takes it away: the book's writes); creates the entry when there is none. |
| `{ kind: "book", title?, body? }` | Changes the working title or the description. |

`entry` is `{ title?, body?, ghostwriter? }`. Every entry an edit writes or moves is the author's (`origin: author`, no `digest`): an outline the author arranged is never undone by the autopilot. An entry whose frontmatter cannot be read is moved as it is; one that is edited is written anew from the edit, with a warning. What the outline says is never an error: a ghostwriter that does not exist (`ghostwriter-missing`) or is not a file name (`ghostwriter-invalid`), a text cut at 20 000 characters (`text-too-long`), a title cut at `OUTLINE_TITLE_MAX_CHARS`, 200, because it names the chapter's folder (`title-too-long`), and the chapters left without an entry (`gap`) are warnings. Only an argument that is not a number of a chapter throws. `serializeOutlineChapter(entry)` and `serializeOutlineBook(book)` write one file.

### Composing edits

`composeOutlineEdits(source, edits, options?)` makes a **series** of edits as the files of one commit: the one function for a host that makes the author's edits in a row (the personal server's MCP tool does; a page that shows the outline composes the same way). It is pure: the outline comes as `source`, `{ index, paths?, read(path) }` (the `OutlineIndex` of the snapshot, the paths of the book's files, and a function that reads one file; nothing else is read), the `edits` are the engine's own (`OutlineEdit`) and the answer is `{ changes, warnings, steps, created, updated, removed, moved, changed, gone, chapters, entries, book?, identities }`.

- **In order, once.** Each edit is made on the outline the one before left (a `number` is the number the chapter has at that point of the series), the files are written once with their final text, each expecting the file as it was read, and a file that comes back to what it was is left alone. Every entry it writes or moves is the author's. `steps` has one line of data for each edit (what it did, so a host words it in its language, with the `origin` of the entry it is about: the number that entry had when the series began, so that naming it by its title names the right one though the numbers shift), `created` and `updated` are the numbers, when the series is over, of the entries it made and changed (`entries` gives their new hashes), `removed` the numbers when it began of the entries it deleted, `moved` the entries that changed number as runs (`{ from, to, count }`), `changed` and `gone` the chapters whose entry says something else, or has none, when it is over (`groupOutlineChanges` below), and `chapters` how many entries the outline has. `remapOutlineNumber(edit, number)` is the renumbering of one edit, the rule the series follows and a page may use to keep what the author typed in an entry that moved.
- **Only the files that are needed.** An entry is known by its path and hash and read when an edit is about to rewrite it: an `update` reads one file, an `append` or a `remove` none, an `insert` the entries it moves (on an outline of 5000 chapters, fifty updates of fifty different entries are fifty reads). A second file for a chapter, or a file that is not named as an entry is (`7.md`, `0007.md`), is seen only in `paths`: the outline is then read whole and read again after every edit, as the engine reads it, so that what an edit frees is taken by the file that waited for it. The files that are not the outline's are left out.
- **Never over what changed meanwhile.** An edit that replaces what someone read (`update`, `remove`, `book`) may carry `expectedHash`, the hash of the file as it was read, and the series follows every entry through the renumbering to check it against the entry it is of, wherever the edits before have put it (`identities` says where each entry the series moved, deleted or changed went, with its hash when it began). A hash that is given is always checked; `options.requireHash` makes a caller's rule (`outlineEditNeedsHash` is the one of the personal server: the text of an entry that exists, an entry that is deleted, a description that is replaced); an entry the series made has no hash, and none can be given.
- **Limits.** `options.maxEdits` (50) and `options.maxFiles` (1000; checked at every moment of the series, so a series that has changed more files is refused there and says how many it had by then; a file changed and changed back is not counted); `Infinity` for none.
- **Refusals.** An `OutlineComposeError` whose `code` is `not_found` (a `move` or a `remove` of a chapter that has no entry; with `options.missing: "warn"` the engine's own answer instead: that edit changes nothing, a `not-found` warning says so, and the others are made), `expected_hash_required`, `conflict` (`reason`: `changed`, `removed`, `made-in-series`, or `gone` for a file that was listed and is not there when it is read), `too_many_edits`, `too_many_files` or `invalid_edit`, with the `index` and the `edit` of the series and the `number`, `path`, `subject`, `count` and `limit` it is about, so that a host words it. Nothing is written then. What the outline says is a warning, as in `outlineChanges`, told once, and of the gaps only the one the outline ends with, and only when the series made or changed it.

`changeOfWritten(state, number, { entry?, outlineEmpty? })` says what the autopilot does when the entry of chapter `number` changes (`entry: "changed"`, the default) or is deleted (`"removed"`), from its `state` (`options.frozenEdits`, the chapter of the plan, the work it has in its hands), as one of `OUTLINE_CHANGE_OUTCOMES`. The rule is the engine's own (`outlinePlanStatus` and `settleFrozenChanges`), and a test runs those two on a real book for every row:

| Outcome | When |
|---|---|
| `ask`, `auto`, `notify` | The chapter is closed (`done`, or written by the author before the autopilot took over) and the plan remembers its entry: as `options.frozenEdits` says. Under `auto` a chapter the author wrote is only reported, never rewritten for the autopilot's decision. A frozen chapter is met the same way: the record in `chapter.md` decides nothing here. |
| `later` | The chapter is being written, or the autopilot has it in its hands (a revision rewrites it, the decision about it is being carried out): the change is said once and decided once the chapter is closed. |
| `replan` | The chapter is not written yet: it is planned again from the new entry, before its scenes (only the chapter about to be started is looked at; a later one when its turn comes). |
| `unplan` | The entry was deleted and the chapter is not written: it leaves the plan. |
| `stays` | The entry was deleted and the chapter is written: it stays in the book, and the run says it once. |
| `none` | No plan, a plan that has no such chapter or remembers no entry of it, or the whole `outline/` was deleted (`outlineEmpty`: deleting it is not deleting every chapter). |

An entry that cannot be read changes nothing until the author corrects it, and nothing is decided before the plan is approved: the change is noticed when it is. `groupOutlineChanges(state, changes)` groups the `{ number, entry? }` of a series by outcome, in the order of `OUTLINE_CHANGE_OUTCOMES`, so that a host says one sentence for each.

### What the autopilot does with it

- **What binds.** The outline binds through the entries of the author (every entry but the autopilot's intact ones) and the description of the author. A book whose outline has nothing of the author, none at all or only the autopilot's intact entries, is asked exactly what it was asked before the outline existed.
- **As many chapters as it has.** The book is `bookChapters(outline)` long: the number of its last chapter entry (the entries are the chapters; a number between two entries that has none is planned freely). An entry the author adds after the last chapter of a finished book extends it. With no chapter entry and no approved plan the run stops with «The outline has no chapters: write the chapters in the Scaletta, then resume.»
- **The plan follows it.** The request of every batch of the plan carries the description of the book (at most 3000 characters), the entries of the chapters it plans (whole, as far as their share of 24 000 characters allows) and, condensed like every list of chapters, the entries of the chapters not planned yet, with the rule: the same chapters, in the same order, with the same hypothetical titles (the model refines a title only where the entry has none: the engine keeps the entry's own) and the same events; enrich, never change. `brief.synopsis` stays the fallback: alone it binds as it always did; next to an outline it applies where the outline says nothing, and the outline wins. The concept is told that the outline binds it, and the director is told not to ask the plan to change it.
- **The ghostwriter of a chapter.** A chapter takes the ghostwriter of its entry (`PlannedChapter.ghostwriter`) and the `chapter.md` the plan creates says it, when it is not the book's: the chain scene, chapter, book is the one it always was. An entry that names a ghostwriter that does not exist is said (`outlineGhostwriter`, with `chapterNumber` and `ghostwriter`), and the book's writes the chapter; when the author creates it before the chapter starts, the chapter takes it.
- **The plan fills it.** After every plan, and every revision of it, the plan writes, in the same commit, the entries of the chapters it planned that have none: the title, and as text the summary of the plan followed by its key events as a list, with `origin: autopilot` and the `digest` of what it wrote; and `outline/book.md` when it is missing, with the logline of the concept (or the brief's idea). The chapters the author wrote get an entry only when they have none, with their summary. An entry of the author is never touched; an intact one of the autopilot follows the plan when the director has it revised. `options.fillOutline: false` writes nothing. Every chapter keeps the digest of its entry (`outlineDigest`).
- **The author changes it.** Before the scenes of a chapter with nothing written are planned, its entry is compared with `outlineDigest`. An entry the author changed (or wrote for a chapter that had none) has the chapter planned again (`replan`: its title, summary, purpose, events and ghostwriter follow the new entry, its scenes are planned again), with the insight `outlineChanged` ("You changed the outline of chapter 7: I am planning it again"), and no other chapter is touched. An entry the author deleted takes its chapter out of the plan, and out of the book when its folder is empty (`outlineRemoved`): the following chapters keep their numbers, and the chapter counts in `plan.removedChapters` so that the book is not extended to replace it. Deleting the whole `outline/` takes no chapter out. An entry that cannot be read changes nothing until it is corrected (`outlineWarnings`). The entry of a chapter already closed that the author changed is decided like a change of a frozen chapter (`options.frozenEdits`: asked by default, with the choices `rewrite-to-outline`, `keep-text` and `mark-reviewed`; see *Frozen chapters*); one of a chapter still being written is said once a run (`outlineChangedWhileWriting`), and decided once the chapter is closed; one that was deleted is said once a run (`outlineRemovedWritten`) and the chapter stays in the book.
- **What it costs.** The snapshot knows the files of the outline and their hashes from the list of the book (`snapshot.outline`, an `OutlineIndex`), without reading them; `OutlineReader` reads an entry only when a step needs it, through a cache of the run keyed by path and hash.

### The brief (`outline/_brief.md`)

The brief the autopilot starts from is kept in two files of the Scaletta, and each text has one home. The **idea** (the idea, promise or pitch of the book) is the description of the book: the body of `outline/book.md`, stored there and nowhere else. `outline/_brief.md` keeps `genre`, `audience`, `wordsPerScene` and the **synopsis** (its body). Two functions compose and split them:

- `readOutlineBrief(store, sources?)` → `{ brief: { idea, genre, audience, wordsPerScene, synopsis }, hash?, unreadable?, bookUnreadable?, frontmatter }`. `brief.idea` is the body of `outline/book.md`, or `""` when there is none or the autopilot wrote it (a logline of its own is not the author's idea). `hash` is the hash of `_brief.md` (absent when the file does not exist). `sources` says what is known already (`book`: the description already read, `null` for none; `brief: false`: the brief file is known not to exist), so that a host reads each file once.
- `writeOutlineBrief(store, fields, message?)` → `OutlineBrief` (the brief as saved). `fields` is any part of `{ idea, genre, audience, wordsPerScene, synopsis }`; the rest is kept. The idea goes to `outline/book.md` through the outline's own builder (`serializeOutlineBook`: the working title and the other keys of the file are kept; the author is the writer), the fields to `_brief.md`, in ONE commit, compare-and-swap on both files (a change made meanwhile is merged, never overwritten; five attempts). A file whose frontmatter cannot be read is never written over. `outlineBriefChanges(store, fields)` → `{ changes, brief }` is the same write, not committed: the start uses it.
- `parseOutlineBrief(content, hash?)` and `serializeOutlineBrief(fields, frontmatter?)` are the file of `_brief.md` alone: `OutlineBriefFields` is `{ genre, audience, wordsPerScene, synopsis }`, with no idea.

**The limits.** The idea is the description of the book, and it is never cut: an idea of more than `OUTLINE_BOOK_MAX_CHARS` (1 000 000 characters) is refused with `OutlineTextLimitError` (`code: "text_too_long"`, the length and the limit in the message) and nothing is written. The server answers a configure or start that carries it with 413 `text_too_long`; the MCP `edit_outline` schema refuses a `book` body over 400 000 characters (its text limit) before the engine is asked. A description over the limit that a file already holds is read whole, with a warning, and a title-only edit leaves it as it is. Chapter entries keep their own limit (`OUTLINE_ENTRY_MAX_CHARS`, 20 000, cut with a warning as before).

**Legacy.** A state saved with a brief idea, in a book whose `outline/book.md` has no author's description, gets that idea written into `book.md` once, in the start commit (with the state, in the same commit). A description the author wrote is never overwritten. The fields of a state move to `_brief.md` only when that file does not exist yet.

- **The name starts with an underscore, and it is no entry.** `OUTLINE_BRIEF_FILE` is `outline/_brief.md`. `outlineIndex` and `parseOutline` never read it as a chapter, so it has no number, is never counted, and is never a warning. `write_file` refuses the whole `outline/` folder, so the brief changes only through the brief's own routes; `edit_outline` writes only the chapter entries and `outline/book.md` (the description, which is also the idea), so it can neither delete, renumber nor move `_brief.md`.
- **The brief has no number of chapters.** The chapters are the chapter entries of the Scaletta: `bookChapters(outline)` is the number of the last entry (its number; the entries are the chapters). `targetChapters` and `scenesPerChapter` are not read any more.
- **The scenes are the planner's.** `scenesForChapter(text)` gives a chapter 2 scenes when its outline entry is up to 40 words, 3 up to 100 words, and 4 above (`SCENES_PER_CHAPTER` is 2 to 4). The text is the entry's body; a chapter without an entry is read from its summary, goal and key events. `wordsPerScene` is the target of every scene.
- **The run reads it at every start and configuration.** `AutopilotSession.start({ brief })` and `configure({ brief })` save a brief sent to the file first; the run then reads the file (`readBrief`). `state.brief` is the snapshot the run uses, and it is refreshed when the run starts or the author configures it. A book whose brief is only in its state (saved before the brief had a file) gets the file in the start commit, once.
- **No chapter entries, no run.** With no chapter entry and no approved plan, the planner stops: «The outline has no chapters: write the chapters in the Scaletta, then resume.» A plan that is already approved keeps going to the end of its own chapters.
- **Legacy states.** A state saved with `targetChapters` and `scenesPerChapter` in its brief still loads and runs: the two counts are not read. A plan of N chapters runs to the end of ITS plan. A completed book is not extended unless the author adds chapter entries to the Scaletta: the highest planned chapter number is compared with the last chapter entry, never the number of chapters planned (a book may go on from chapter 1 200, and no chapter past its last entry is ever planned).
- **Presets.** The brief has none: `autopilotPresetSkeleton(id)` gives the chapter entries a new book's outline starts with (see *Presets*).

## Frozen chapters

A chapter is **frozen** when the autopilot's director approves it, or when the author freezes it by hand: its `chapter.md` holds a record of the chapter as it was. A change of its text after that is never ignored: before every step the autopilot notices it and, unless the author chose otherwise, stops and asks what to do (as BookWriter's "Review from a saved change": nothing starts by itself).

### The record

```yaml
frozen:
  at: 2026-01-01T00:00:00.000Z   # when (ISO 8601, UTC)
  by: autopilot                  # or author
  digest: 0f1e2d3c4b5a6978       # the body of chapter.md, its title heading excluded
  files:                         # every scene, by the name of its file in the chapter's folder
    001-the-arrival.md: 8a7b6c5d4e3f2a1b
```

- **What it fingerprints.** The text, never the frontmatter: a new summary, an id rewritten by a rename, a new title (and the `# Title` line of chapter.md that repeats it), line endings, spaces at the end of a line and the Unicode normalization are no change. A scene is named by its file in the folder, so a folder that is renamed or renumbered keeps its record; a scene file renamed with the same text is no change, two scenes that swapped their texts are. The digests are sixteen hexadecimal characters of a fast 64-bit hash (`textFingerprint`, `chapterBodyDigest`, `sceneBodyDigest`): they tell a change, they do not protect against one.
- **Read once.** `loadBookSnapshot` computes the digest of every chapter.md and scene when it reads the file, which it does once for each content (`SnapshotCache`): `ChapterInfo.bodyDigest`, `ParagraphInfo.bodyDigest`, the whole document of chapter.md in `ChapterInfo.document`, and the record in `ChapterInfo.frozen`. A record that cannot be read (`frozen: yes`, a digest that is not one, a moment that is not one…) is `ChapterInfo.frozenProblem` and the chapter counts as **not frozen**: it never blocks anything (the run says it once with `frozenInvalid`, and the core's doctor warns with `chapter-frozen-invalid`). `frozen: false`, or no key, is no record. A record is read tolerantly (`by: Author`, a moment in any zone, digests in capitals) and normalized.
- **Pure functions** (`book/freeze.ts`, no I/O): `freezeChapterChanges(snapshot, slug, by, at)`, `markReviewedChanges(snapshot, slug, at)` (frozen again as it is, keeping `by`) and `unfreezeChapterChanges(snapshot, slug)` answer the `BookFileChange[]` of one compare-and-swap commit of chapter.md (every other key and the body as they are; the file is made for a folder of scenes that has none; a chapter that does not exist is `FrozenChapterError` `chapter_not_found`, a frontmatter that cannot be read `FrontmatterError`). `frozenChanges(snapshot)` answers every frozen chapter whose text changed, in the order of the book: `{ number, slug, title, path, by, frozenAt, changed: { added, removed, modified, body }, fingerprint }`, where `fingerprint` is the same for the same edits and another for any other. It reads nothing: 5000 frozen chapters are checked in a few milliseconds, and a snapshot loaded again reads only the files whose hash changed. `parseChapterFreeze(value)` and `chapterFreezeRecord({ at, by, chapterBody, scenes })` are the reading and the making of a record.
- **The core** declares the key: `chapterFreezeSchema` (its shape) and `chapterSchema.frozen` (kept as it is, whatever it holds: a tool that rewrites chapter.md never drops it).
- **A whole text from elsewhere.** `keepChapterFreeze(proposed, current)` is chapter.md as a host writes it from a whole text it did not make itself (a proposal of a model, a tool that writes any file): with the record the file holds now, exactly, and with none when it holds none; everything else as written. A model never freezes a chapter or takes its freeze away, so its change of a frozen chapter is noticed like the author's, and a record it made up is dropped. A frontmatter that cannot be read, in either text, leaves the text as it is. The site's Copilot and the server's MCP `write_file` call it for the paths `parseChapterFilePath` reads.

### When the autopilot freezes

- **When it approves a chapter**: the closing of the chapter (`consolidate`) writes the record in the same commit as its summary, from the texts it read. A chapter frozen by the author keeps `by: author` when the autopilot closes it again.
- **After a revision** that rewrote a frozen chapter: the chapter is reviewed and closed again, so it is frozen again.
- **Never a chapter the author wrote** (`imported`): only the author freezes those (`freezeChapter`).
- **An older book.** A state saved before frozen chapters existed has no `state.frozenSince`: its first run freezes the chapters the autopilot approved (status `done`, not imported, with no record) in one `freeze` step that needs no model, says it once (`frozenMigrated`), and sets `frozenSince`; a new state has it from its creation. A chapter the author unfreezes afterwards stays unfrozen until the autopilot closes it again.

### When a frozen chapter changes: `options.frozenEdits`

Before every step the run compares the frozen chapters with their records (and the outline entries of the chapters already closed with the digest the plan keeps of them), and does with every change that has no decision yet what `options.frozenEdits` says:

| Mode | What happens |
|---|---|
| `ask` (the default) | The run stops (`waiting-author`) with a question, before anything else is done or spent: one change at a time, in the order of the book, the question saying which other chapters changed too. |
| `auto` | The change is reviewed and the book updated from it (`review-and-update`; for an outline entry, `rewrite-to-outline`) without asking, with the insight `frozenAuto` (`outlineWrittenAuto`). A chapter the author wrote is never rewritten for a decision of the autopilot: its outline change is only said, and the impact of a change never rewrites one. |
| `notify` | Every change is said once (`frozenChanged`, `outlineWrittenChanged`; its fingerprint is kept in `state.frozenSeen`, so it is not said again in another run), and nothing is done. |

The option is saved with the others, read tolerantly (any case; a value nobody knows changes nothing) and can change while a run goes on (`LIVE_AUTOPILOT_OPTIONS`).

- **What is never asked about**: the chapters the autopilot has in its hands (being written or reviewed, rewritten by the revision in progress, or the change being carried out): what happens to their files then is its own work. While it finishes work the author asked for (a revision, the chapters it rewrote reviewed again, the review of a change) no new question is asked: what it rewrites is frozen again at its end, and a change it did not reach is asked about once it is over.
- **A scene deleted** from a frozen chapter is a change to ask about: the plan follows the files of a frozen chapter, so the scene is never written again in silence (a chapter that is not frozen is reconciled as it always was).
- **A change taken back** withdraws its question; a change changed again is asked again (the question's `id` is `frozen-<number>-<fingerprint>`). A question that is open stops every run until it is answered.

### The question

`state.question` has `kind: "frozen-change"` ("You changed chapter 3, frozen on 1 February 2026. What should I do?", in the language of the book, with the date as the author reads one: see *What the interface reads*) or `kind: "outline-change"`, the typed `choices` (`{ id, label }`), the same labels in `options` (for an interface that only shows those), the context in words (what changed, the other chapters) and `frozen`: `{ kind, number, slug, fingerprint, title?, by?, frozenAt?, changed?, others? }`. The run's `message` says why it stopped.

`session.answer({ questionId, choice })` chooses by `id`; so does `answer: "<id>"`, and so does a label in either language, which is what an interface that shows `options` sends (and what an older personal server forwards, as it forwards `answer`). `accept: true` without a choice keeps the author's text (`mark-reviewed`; `keep-text` for the outline). Any other text reviews and updates the book (rewrites to the outline) with the text as the author's note for the director; with `asRule` it becomes a permanent rule too. An empty answer chooses nothing (`FrozenChapterError` `invalid_action`).

### The actions

| Action | What it does |
|---|---|
| `review-and-update` ("Review and update the book from this change") | The changed chapter goes back to review, before the plan: one round of the director (and of the specialists when they are on), without readers, whose accepted fixes are advice for the author and are **never applied** (the author's change stands); the round joins its `rounds`, and the chapter is closed (summary, story so far) and frozen again. Then the later chapters already written are checked: a revision (`state.revision` with `afterChapter`, analyzed with the tool `revision_impact`) is given BEFORE (what the autopilot knew of the chapter when it was frozen: its summary, key events and story so far at its close) and AFTER (its new closing), and chooses the scenes of the later chapters to rewrite; they are rewritten (`revise`), reviewed, closed and frozen again. The book's final judgement is made again. |
| `review-only` ("Only review the chapter") | The same round of the director on the changed chapter, and its closing, frozen again: nothing is rewritten and the later chapters are not checked. A complete book stays complete. |
| `mark-reviewed` ("Mark as reviewed") | Frozen again as it is, at once, without the model. For an outline entry, the same as `keep-text`. |
| `rewrite-to-outline` ("Rewrite the chapter to follow the outline") | The plan of the chapter follows the new entry (its purpose becomes the entry's text, its key events are dropped, `outlineDigest` is the entry's), and a revision limited to the chapter (`onlyChapter`) rewrites the scenes the new entry requires; the chapter is reviewed as usual (fixes applied), closed and frozen again, and then the later chapters are checked as for `review-and-update` (unless nothing was rewritten). |
| `keep-text` ("Keep the text, update only the outline") | The plan follows the new entry (`outlineDigest`), nothing is rewritten. |

A decision that needs the model is recorded in `state.pendingReviews` and carried out by the next run before it goes on with the plan (by a run in progress, at its next step), one at a time, in the order of the book; one whose change is gone by then is dropped (`frozenCleared`), and when it is over the run says it (`frozenReviewed`).

### For the hosts

- `session.frozenStatus()` answers `{ mode, changes, pending, warnings }`: every change, in the order of the book, with `kind`, `number`, `slug`, `title`, `fingerprint`, the `actions` that can be done with it now (all of its kind for a chapter of the plan; only `mark-reviewed` for a chapter the autopilot has no plan for), `by`, `frozenAt` and `changed` (a frozen chapter), `outline` (`{ title, digest }` of the new entry) and the decision already recorded (`pending: { action, at }`); the decisions recorded; and the chapters whose record cannot be read. It refreshes `summary.frozenChanges`.
- `session.resolveFrozenChange(number, action, { kind?, note? })` decides about a change, as the answer to the question would, also while a run goes on: `mark-reviewed` at once (one commit of chapter.md, and of the state when there is something to close), `keep-text` at once (at the next step of a run in progress); the others recorded for the run. `kind` (`frozen` or `outline`) tells the change of a chapter that has both; without it the action says it. Refused with `FrozenChapterError`: `chapter_not_found`, `not_changed` (nothing to decide about), `invalid_action` (`FROZEN_CHAPTER_ERROR_CODES`). Answers the status after it.
- `session.freezeChapter(slug)` and `session.unfreezeChapter(slug)` freeze a chapter by hand (`by: author`, as it is now: a change is accepted) or take its record away; the decisions that waited for it are dropped. They answer `{ slug, number, frozen }` (the record, or `null`).
- `summary.frozenChanges` counts the chapters with a change that waits for the author (a change with a decision recorded does not count), so that a band or a dock says it without the state: what the run found before its last step, or the last `frozenStatus()`. It is absent when none waits (a book without changes has the summary it always had).
- The routes of the personal server are in *The personal server client*.

## Evaluation style

`evaluation-guidelines.md`, the "Evaluation style" page of the web app, says how the author judges the book: `criteria`, a mapping of keys to `{ description }` (as the site writes it; a description written as text, a criterion left empty, and a list of `{ name, description }` are read as well), and a body with the critical method, the severity and the structure of a written evaluation. `parseEvaluationStyle(raw)` reads it as `{ title, criteria: [{ name, description }], body, path, warnings }` and `loadEvaluationStyle(store)` reads it from a book (`null` without the file). Like a profile it never throws and never drops a criterion in silence: YAML that cannot be read (with its line) and a criterion that cannot be read are warnings that name the file, and a file with warnings stops the run before it spends anything (`profileProblems`).

The autopilot judges with it:

| Step | What it reads |
|---|---|
| The director's review of a chapter | The criteria, the method and the severity. |
| The specialists (`FINDINGS`) | The criteria and the severity. |
| The final judgement of the book | The criteria, the method and the severity (`askDirector` takes it as `evaluationStyle`; an opinion asked by a host is unchanged unless the host passes it). |
| The review of the plan | Only the method and the severity: the criteria judge chapters. |

`evaluationStyleBlock(style, { criteria? })` is what a prompt carries: a block among the data of the request (the author's file, never instructions), delimited by its title and `END OF THE EVALUATION STYLE`, at most `EVALUATION_STYLE_MAX_CHARS` (3000) characters: the criteria first, each at most 400 characters, with a line that says how many are not listed when they do not all fit, then the method, cut with `clipText`, which keeps a part of its own however many criteria there are. The request says to judge with it. The score keeps its scale (0-10), the tools keep their schemas, and the sections a written evaluation would have do not change the answer: the criteria guide the judgement. A book without the file, or with a file that says nothing, sends the requests it always sent.

## Estimating a run

`estimateAutopilotRun(input)` says, before the autopilot starts, how many calls a book will make, how many tokens they will carry, what they will cost, how long they will take, what the author should read before pressing start, and what it assumed to say so. It is a function of its input and nothing else: no file, no clock, no network, no random number, and the answer is a new object every time. It is closed-form (the arithmetic of the pipeline, not a walk through the book), so a book of 5 000 chapters takes as long as one of five; a test holds it under 50 ms.

```ts
import { TWO_CALL_TASKS, estimateAutopilotRun, estimateContextFromState, estimateModelsFromConfig, estimateProgressFromState, measuredSpeed } from "narrarium-engine";

const speeds = measuredSpeed(activities, { ignoreTasks: TWO_CALL_TASKS });   // optional: without it there are no minutes
const estimate = estimateAutopilotRun({
  brief, options,                                      // the values of the form (the idea and the synopsis weigh in the prompts that carry them)
  maxReviewRounds: director.maxReviewRounds,           // 1 to 3: it is the director's profile, not an option
  language: book.language,                             // the texts come back in it: Italian for an Italian book, English for every other
  models: estimateModelsFromConfig(config, speeds),    // the model of each capability, as the router would choose it
  currency: config.costCurrency,
  outline: { entries, lastChapter, words },            // what the author wrote in the outline
  progress: estimateProgressFromState(state),          // a resume or "add chapters": only what is left counts
  context: { ...estimateContextFromState(state), designWords, canonWords },   // sizes you measured, in words (optional)
  readerPanelSize,                                     // readers that are enabled and not ignored by the director (the built-in panel has eight)
});
```

### The input

| Field | Meaning |
|---|---|
| `brief` (`outline/_brief.md`, see *The brief*), `options` | Read as the engine reads them (`normalizeBrief`, `normalizeOptions`): what is missing is the default, a number past the limits is the limit, anything that is not a value is ignored. Only `wordsPerScene` (and the idea and the synopsis, for their words), the chapters of `outline` and the `scenesPerChapter` hint (2 to 4 for the planner; 3 when it is not told) and `readers`, `maxReaders`, `readersOnPlan`, `specialists` change the numbers. `pauseAfterPlan`, `pauseAfterEachChapter`, `chaptersPerRun`, the budgets, `fillOutline`, `syncAfterChapter` and `publishEvery` change nothing the models are asked: they are accepted and ignored. |
| `maxReviewRounds` | The most rounds of review a chapter gets, 1 to 3 (2 when it says nothing), as in the director's profile. |
| `models` | `{ [capability]: { model, maxInputTokens?, maxOutputTokens?, pricing?, tokensPerSecond?, supportsReasoning?, provider?, underlyingModel? } \| null }` for the six capabilities the autopilot uses: `autopilot`, `director`, `reader-evaluation`, `reader-evaluation-summary`, `review`, `simple-tasks` (`ESTIMATE_CAPABILITIES`). `estimateModelsFromConfig(config, speeds?)` builds it from an `AiRuntimeConfig` with the first candidate of `resolveAiCandidates`, and copies no key and no address. |
| `outline` | `{ entries, lastChapter, words }` of the author's entries: the chapters of the book are the outline's (`bookChapters`), the chapters already planned when it has none (`progress.planned`). |
| `progress` | `{ chaptersDone, planned, conceptDone, finalDone, withoutSummary, withoutSummaryWords }`: a book that is started counts only the rest. `estimateProgressFromState(state)` reads the first five from the state of the autopilot; for a book the autopilot has not started, `estimateProgressFromChapters(snapshot.chapters)` reads `chaptersDone` and `withoutSummary` from the chapters that have prose. `conceptDone` is, when it is not said, whether there is a chapter or a plan; a book whose story design the author wrote (`isThinDocument(body)` is false) has no concept step either, and the host says so. A chapter written halfway counts as whole. |
| `scenario` | `{ rounds, repairs, planRevisions }`, each a number or `{ min, max }`: what the reviews of the run will be, when the host knows. See *The interval*. |
| `context` | Sizes in words that the host has measured (`countWords` of the files): `designWords`, `worldWords`, `ghostwriterWords`, `directorWords` (the whole profile), `canonWords` (the manifest of the canon; `0` for a book with no canon), `secretsWords`, `rulesWords`, `notesWords` (the director's standing notes now), `styleWords` (the evaluation style as a chapter's review carries it, criteria and method: the review of the plan carries about half). Each defaults to `ESTIMATE_TYPICAL`. `estimateContextFromState(state)` gives the rules of the author and, once the plan is approved, the notes of the director. |
| `readerPanelSize` | Readers in the panel (default: the enabled readers of the built-in panel, 8). The readers of a run are `min(maxReaders, readerPanelSize)`. |

### The output

`{ language, chapters, chaptersToWrite, words, calls, inputTokens, cachedInputTokens, outputTokens, cost, unpriced, minutes, unmeasured, capabilities, steps, warnings, assumptions }`.

- Every range is `{ min, max }`, in whole numbers for calls and tokens. `calls`, `inputTokens`, `outputTokens` and `cachedInputTokens` are the sum of the `steps` (15 kinds of call, with their `capability`) and also of the six `capabilities` (each with its `model`, `calls`, tokens, `cost` and `minutes`).
- `cost` is `{ min, max, currency? }` and is `null` when a capability that makes calls has a model with no price (or no model): `unpriced` lists which. A price of `0` is a price. The price of a model is known when it has both `inputPerMTok` and `outputPerMTok`.
- `minutes` is `{ min, max }` and is `null` unless every capability that makes calls has a speed (`tokensPerSecond`, a number above zero): `unmeasured` lists which. Time is never guessed.
- A capability that makes no call (no readers, for example) needs no model, no price and no speed: its `cost` and `minutes` are `{ min: 0, max: 0 }` and it warns about nothing.
- `cachedInputTokens` is the fixed start of every request (the system message and the function), for the capabilities whose model declares `pricing.cachedPerMTok`; `cost.min` counts it at that price and `cost.max` counts no cache. Without a cached price it is `{ min: 0, max: 0 }`.

### The interval

The estimate is an interval because the reviews are the model's: how many rounds a chapter takes, how many scenes the director has repaired, how many times it sends the plan back. The two ends are the least and the most the pipeline does, and a run is somewhere between:

| | rounds `r` | scenes repaired in a chapter `p` | revisions of the plan `v` |
|---|---|---|---|
| `min` | 1 | 0 | 0 |
| `max` | the director's `maxReviewRounds` | `r × scenes` (the scenes of a chapter: the planner's, 2 to 4, see *The brief*) | 2 (the third review of the plan is an approval) |

`scenario` pins any of them; when only some are given the others keep their end (`repairs` goes from `rounds.min − 1` to `rounds.max × scenes`), and the rounds are clamped to 1 and the director's limit. A scenario that pins all three makes `min` and `max` the same number. The ends are bounds, not a "typical" run, and there is no third figure.

### The calls

The numbers come from the pipeline step by step; `C` is the chapters left to write, `S` the scenes of a chapter, `R` the readers of the chapters (`R_plan` those of the plan), `E` is 1 with specialists and 0 without, `N` the chapters of the book, `written` the chapters done.

| Kind | Capability | Calls | Where it comes from |
|---|---|---|---|
| `concept` | `autopilot` | 1, unless `conceptDone` (a book with prose or an approved plan has it) | `runConcept` |
| `summarize-imported` | `simple-tasks` | one for each chapter of the author with no summary | `runSummarizeImported` |
| `plan` | `autopilot` | `B × (1 + v)`, `B = ⌈chapters to plan / 20⌉` (`PLAN_BATCH_CHAPTERS`) | `planRange`, `runPlan`: a fresh plan covers `N − written`, an extension of an approved plan `N − planned` |
| `plan-reader` | `reader-evaluation` | `R_plan`, for a fresh plan only (the readers do not read an extension) | `runPlanReader` |
| `plan-review` | `director` | `1 + v` | `runPlanReview` |
| `scenes` | `autopilot` | `C` | `runScenes` |
| `write` | `autopilot` | `C × S` | `runWrite` |
| `scene-summary` | `simple-tasks` | `C × (S + p)`: after each scene and each repair | `summarizeScene` |
| `reader` | `reader-evaluation` | `C × R` | `runReader` |
| `readers-summary` | `reader-evaluation-summary` | `C`, when `R ≥ 1` | `runReadersSummary` |
| `specialists` | `review` | `C × E × r`: one call for all the specialists, each round | `runSpecialists` |
| `director-review` | `director` | `C × r` | `runDirectorReview` |
| `repair` | `autopilot` | `C × p` | `runRepair` |
| `consolidate` | `autopilot` | `C` | `runConsolidate` |
| `final` | `director` | 1, unless every chapter is done and the book was judged (`finalDone`) | `runFinal` |

The readers of the plan do not depend on `options.readers`, and they are not asked again after a revision of the plan. `fillOutline` makes no call. The steps a plain run does not make (`replan`, when the author changed the outline of a chapter that is not written; `impact` and `revise`, for an intervention that rewrites; `freeze`) are not counted.

### The tokens

A call is counted as the engine's router counts it before it sends it (`ai/budget.ts`): the system message and the user message at four characters a token plus 4 tokens each, the function of a structured request at four characters a token plus 8. The system prompts and the functions are the real ones (`prompts.ts`, `director/opinion.ts`, `readers/evaluation.ts`); the wrappers and the request lines were measured on the real prompts; and what a prompt carries of the book is counted in words: a word is six characters, the space included, so **1.5 tokens a word** in Latin script, and for another language in proportion to its factor (`tokensPerWord(language) / 2.4`, so 2.5 times that for a language the engine does not know). The prompts that grow with the book grow as the pipeline makes them grow, with the same limits:

- the **story so far** adds 75 words a chapter up to 900 (`STORY_SO_FAR_TARGET_WORDS`) and each prompt cuts it where it cuts it (3 000, 4 000, 5 000 or 7 000 characters);
- a **list of the chapters** (the plan, the chapters before this one, the chapters of the book) is whole while it fits 24 000 characters (`OUTLINE_MAX_CHARS`); when it does not, `layoutChapters` keeps the 30 lines around the chapter it is about and a title for each of the others, so the list is *shorter* just after it stops fitting (about chapter 63 for the specialists) and then grows by a title a chapter;
- the **standing notes of the director** grow by a note a chapter up to the twelve the state keeps (`MAX_DIRECTOR_NOTES`);
- the **chapter** itself (`S × wordsPerScene` words) is read whole by every reader, by the specialists, by the director and by the closing, and a scene by its summary and by its repair.

A reply is the words of the schema or of the scene at `tokensPerWord(language)` a word (**2.4** for English, Italian and every other Latin script, more for the other scripts: 4 for Russian, 3.5 for Chinese…), and never more than the limit the pipeline puts on it (`scaleOutputTokens` of 9 000, 5 000… for the structured steps, `min(16 000, words × tokensPerWord + 800)` for a scene) nor than the largest answer the model declares (`maxOutputTokens`). The structured replies are counted in words of text: the keys and braces of the JSON are not (about 2%).

`ESTIMATE_TYPICAL` holds the sizes the estimate assumes where it cannot know them. They are the estimate's own assumptions: **the replies of a real model may be longer or shorter**, and so may your files. What a host can measure it passes in `context`.

| Group | `ESTIMATE_TYPICAL` (words unless it says) |
|---|---|
| The files of the book | `designWords` 700, `worldWords` 250, `ghostwriterWords` 150 (the default profile: 906 characters), `canonWords` 270 (about six characters with a summary and four other entries), `secretsWords` 105, `secretLineWords` 20, `revealsWords` 45, `rulesWords` 0, `styleWords` 0, `notesWords` 30 and `noteWords` 25 (the notes of the director when the plan is approved, and a note for each chapter), `ideaWords` 60 (when the brief has none), `freshBookWords` 34, `outlineEntryWords` 60, `canonEntryWords` 45 (quoted `canonEntriesScene` 4 times by a scene and `canonEntriesSpecialists` 6 by the specialists) |
| The plan, in prompts | `chapterWords` 130 (a block), `chapterLineWords` 55, `closedLineWords` 64 (a closed chapter: the summary of its closing), `sceneWords` 110, `sceneLineWords` 25, `listCapWords` 4 000, `listFullLines` 30 (lines), `titleLineWords` 5 |
| The story so far | `storyWordsPerChapter` 75, `storyWordsTarget` 900 |
| The review, in prompts | `findings` 5 (a count), `findingWords` 55, `readerProposals` 4 (a count), `proposalWords` 35, `readerLineWords` 55, `fixWords` 25, `summaryWords` 35 (a scene's summary) |
| The replies | `conceptWords` 1 550, `chapterReplyWords` 125 (a chapter of the plan), `sceneReplyWords` 105, `planReactionWords` 100, `planReviewWords` 100, `readerWords` 150, `readersSummaryWords` 190, `findingReplyWords` 48, `directorBaseWords` 75, `decisionWords` 20, `consolidateBaseWords` 100, `recapSceneWords` 25, `importedSummaryWords` 60, `finalWords` 330 |

### The warnings

`warnings` is ordered by gravity (errors, warnings, info); each has a stable `code`, its numbers, a `severity` and a `text` in the language of the book (Italian for an Italian book, English for every other). The interface can show the text or build its own from the numbers.

| `code` | `severity` | Fields | When |
|---|---|---|---|
| `noModel` | error | `capability` | A capability that makes calls has no model: the run would stop at its first step. |
| `smallWindow` | error, or warning when it fits with less than a fifth to spare | `capability`, `model`, `step`, `window`, `inputBudget`, `typicalPrompt` | The window (`maxInputTokens`) of the model, less the reply the step reserves (`requestOutputLimit`: the structured floor of 4 096 tokens, the room for reasoning, the model's maximum) and a 5% margin (`resolveModelTokenBudgets`), is smaller than the largest prompt the capability sends in this book (the last chapter, the last scene of a chapter). A model with no declared window is not checked, as the router does not check it. |
| `smallOutput` | warning | `capability`, `model`, `step`, `maxOutputTokens`, `typicalReply` | The model's largest answer is smaller than the longest typical reply of the capability. |
| `noPrice` | warning | `capability`, `model` | The model has no price: the cost is `null`. |
| `noSpeed` | info | `capability`, `model` | The model has no speed: the minutes are `null`. |
| `reasoningModel` | info | `capability`, `model` | The model reasons (`supportsReasoning`, or by its name as the router knows it): its reasoning tokens are not counted. |

### What it assumes, and what it leaves out

`assumptions` says it in words, in the language of the book. In short:

- the replies are of the typical sizes above and the files of the book are too (or the sizes given in `context`);
- the models answer within the limits the pipeline sets; a step that fails, a reply that is cut and a step that is repeated (and billed again) are not counted, nor are the reader that is skipped after an incomplete reply and the steps a plain run does not make (see *The calls*);
- the output is counted at the engine's factor for the language, which is **generous for English and Italian** (2.4 tokens a word; the factor of a real model is nearer 1.3 to 1.5): replies, output tokens and cost are a prudent guess, and the time too. A host that has run a book can measure its own factor (output tokens over words written) and pass it as `tokensPerWord`;
- the time is the output tokens at the speed of the model, not the reading of the prompt, the network or the retries;
- a model that reasons spends tokens that are not counted;
- the cache, where a price is declared, covers the fixed start of every request;
- a chapter written halfway counts as whole; the fixes of a round are told to the specialists and to the director of the next one (counted), and the notes of the director grow a note a chapter (counted), but the guidance of a real director may be longer or absent;
- the lists of chapters are condensed as `layoutChapters` does down to its second level; a list that goes past it is counted at its budget.

### How it is verified

The calls are exact, and the tokens are held to a tolerance, by running the real pipeline:

- `test/estimate.test.mjs` pins the call tables worked out by hand (a story, a novella, a draft of a novel, a book that is half way, chapters added, an outline longer than the brief, no readers, no specialists, a scenario that fixes the review) and the rest of the contract (warnings, cost, time, garbage input, purity, 5 000 chapters under 50 ms);
- `test/estimate-run.test.mjs` writes whole books with `createFakeAutopilotAi` (scripted so that the reviews turn out as the test says, with replies of the typical sizes) and compares the run with the estimate kind by kind: a run that is at the least the pipeline does makes exactly `calls.min`, one that is at the most makes exactly `calls.max`, one whose rounds and repairs the estimate is told makes its single number, and any run in between falls inside the interval. The tokens are measured as the router measures what it receives and as the words of what the fake answers, and are held to **3% on the tokens of the whole run and 8% on each kind of call that is at least 3% of it** (`TOLERANCE` in the test). The runs: four shapes of a story, each at its least and at its most; five rounds-and-repairs scenarios; a run with the reviews mixed; a book resumed half way; chapters added (in one batch and in two); chapters written by the author; an outline that asks for more; a draft of 24 chapters; a book of 80 chapters; Italian, Russian and Chinese books; a panel of three readers; a director that allows three rounds; a director with a long profile; a book with a synopsis, rules of the author and an evaluation style;
- `test/estimate-math.test.mjs`, `presets.test.mjs` and `measured-speed.test.mjs` check the closed forms against a brute-force sum, the presets, and the speed.

What the runs show (`ESTIMATE_REPORT=1 node --test test/estimate-run.test.mjs` prints the table): over the 27 runs the tokens of the whole run are within 0.9% in and 1.1% out, and each kind of call within 5.2% in and 5.6% out. The deviations that remain, and why:

- the specialists' reply, −5.6%: the findings the fake writes are 48 words each, and the estimate takes 250 words for a reply of five;
- the repairs of a book at its worst, −5%: the scenes the fake repairs name six entries of the canon, the estimate quotes four;
- the readers' summary, +3% (Italian) or less: the evaluations it reads are rendered with headings (`renderReaderEvaluationBody`) in the language of the book, which the estimate counts as 27 words a reader;
- the director's review of a long book, +3%: the findings the fake writes are lines of 60 words and the estimate takes 55, and a director that allows one round makes every review "the last round", a sentence longer in the request;
- the specialists of a book of 80 chapters, −3%: the list of the chapters before this one is laid out by `layoutChapters`, and the estimate follows it down to its second level (the 30 chapters around this one whole, a title for each of the others).

**What these runs cannot say** is whether the typical sizes are the ones of a real model and of your book: the fake answers with replies of the sizes the estimate assumes. Only a real run can tell, and the statistics of a run (`state.stats`: the calls, the tokens in and out, the cost) are what to compare the estimate with.

### Presets

`AUTOPILOT_PRESETS` are the three starting points of a NEW book, from the shortest to the longest. They are not an autopilot setting: once the book exists its outline and its brief say the rest. `autopilotPresetSkeleton(id)` returns the skeleton of one: `chapters` (the chapter entries the new book's outline is created with), `wordsPerScene`, the review options (`readers`, `maxReaders`, `readersOnPlan`, `specialists`) and `maxReviewRounds`. It is `undefined` for any other id, the custom book included. The skeleton is frozen.

| `id` | Chapters | Words per scene | Readers | Plan readers | Specialists | Rounds |
|---|---|---|---|---|---|---|
| `story` | 4 | 900 | 3 | no | yes | 2 |
| `novella` | 12 | 1 400 | 5 | yes | yes | 2 |
| `novel-draft` | 24 | 1 500 | 3 | yes | yes | 1 |

`novella` is what a new book starts with (`DEFAULT_BRIEF`, `DEFAULT_OPTIONS`). The presets have no publish option: where a book is published is the author's choice, as it always was.

### Measured speed

`measuredSpeed(activities, options?)` answers a `Map` from a model to `{ tokensPerSecond, samples }`: the median of the latest `options.last` (20) steps of the model that ended `succeeded`, each its output tokens over the seconds between its start and its end. A step is discarded when it has no data: not succeeded, no model, no tokens written, no or invalid dates, or shorter than `options.minSeconds` (1 s). A model with no sample is not in the map, so that `speeds.get(model)` is `undefined` and no speed is made up. It is a function of the log: no clock, nothing changed.

A host uses it with the log of activities it already has (`session.snapshot().activities`, or `autopilot/activity.json`, the last 200): `estimateModelsFromConfig(config, measuredSpeed(activities))` puts the speed of each model in the models the estimate takes, and the minutes appear; a model that was never measured has none, and the estimate says so (`noSpeed`). `samples` says how much the speed is worth, for a label like "measured on 12 steps".

An activity records the model of its **last** call and the tokens of all of them. A step that writes a scene (`write`, and `repair` and `revise` likewise) makes two calls, the scene and its summary, so when the model of the writer and the model of the simple tasks are not the same, the step is the summary model's and its speed is nobody's: such a host passes `ignoreTasks: TWO_CALL_TASKS`. (Recording the model of each call would remove the need; it is a change of the runner, which this function does not make.)

## AI tasks

The engine asks the host for these router tasks (capabilities): `autopilot` (concept, plan, scenes, prose, repairs), `director`, `reader-evaluation`, `reader-evaluation-summary`, `review` (specialists) and `simple-tasks` (summaries of scenes and of the chapters the author wrote). Missing routes fall back to models tagged `default`.

### What the models read of a scene

Prose that is judged or summarized (the specialists, the director's review of a chapter, the consolidation, the director's opinion on a scene or a chapter, the summary of a chapter the author wrote) is cut, when it is too long, in the middle: `clipMiddle(text, max, { head: 0.6 })` keeps the start and the end, joined by `[…]` (on a line of its own when the text has several lines), at a word and never inside a character. The limit comes from the book: `sceneCharacterLimit(wordsPerScene)` is ten characters a word (as much as the longest words of any script written with spaces) and half as much again, so a scene of the length the brief asks for is never clipped; the fixed limits these prompts always had stay as the least a prompt keeps, so no scene is cut that was not cut before. A scene within the limit reaches the model exactly as it is written. The ending the next scene is continued from is the real end of the previous one, however long it is.

### Secrets in a prompt

`secretRules(store, snapshot, chapterNumber?)` lists the secrets with the rule that holds for the chapter (`HIDDEN until chapter N`, `The reveal is planned in THIS chapter`, `Already revealable…`, or `No reveal threshold`) and, for each, its truth. A book with few secrets gets all of them, exactly as ever. A list over `SECRET_RULES_MAX_CHARS` (24 000 characters) is windowed like a list of chapters: secrets revealed more than `SECRET_WINDOW_CHAPTERS` (30) chapters before drop out first, then the truths and the long wording; what the chapter must not reveal (a reveal still to come, or none planned) and the reveal of the chapter itself stay as long as anything can, the nearest chapters first, and the last line says how many are not listed. Only the files of the secrets that are listed with their truth are read, so a book of thousands of secrets costs the same as a small one.

### Languages

Limits on the reply of a step are sized for Latin script (2.4 tokens a word) and grown for the language of the book: `tokensPerWord(language)` gives the factor of the language (by code, name or region: `ru`, `русский`, `zh-CN`), `UNKNOWN_TOKENS_PER_WORD` (6) for one the engine does not know, and `scaleOutputTokens` applies it up to `OUTPUT_TOKENS_CEILING`. Words are counted by `countWords` for every script, with `Intl.Segmenter` where a language has no spaces.

## The AI client

`createFetchAi(config, options)` is the one AI client of every host: the browser and the personal server give it the same `AiRuntimeConfig` (`pickAiRuntimeConfig(settings)`) and get the same requests and the same outcomes. A host adds only what is its own, through `options`:

| Option | Meaning |
|---|---|
| `fetch` | The `fetch` to use (default the global one). |
| `githubModelsBaseUrl` | Origin of GitHub Models, or of a proxy that forwards `/inference`. |
| `defaultTimeoutMs` | The time the provider has to begin answering for an integration that has no `requestTimeoutMs` (default `DEFAULT_REQUEST_TIMEOUT_MS`). |
| `minimumTimeoutMs` | The shortest start or idle deadline a call is given (default `MIN_REQUEST_TIMEOUT_MS`, 30 s). It is there for tests that count in milliseconds; a host has no reason to lower it. See *Timeouts and streaming*. |
| `onAttempt`, `onAttemptEnd` | Hooks that see every attempt that is sent and how it ended (below). |
| `acknowledgeFallback` | Asked before content goes to an integration of another account than the one it went to so far (below). |

What every host gets, whatever its options:

| What | How |
|---|---|
| Request | `buildChatRequest(candidate, request, { githubModelsBaseUrl })` is the only place a request is built: URL, headers, body, streaming, tools or JSON-in-prompt, and the output limit parameter of the model family. Where the thinking level goes (`reasoning_effort`, or the chat-template argument the model says: see *Thinking*) is decided there too. Pure and exported, so hosts can test their configuration against it. Every request streams (`stream: true`, `stream_options: { include_usage: true }`), a structured one included, unless the integration's `streamMode` is `"off"` or the model declares `supportsStreaming: false`: see *Timeouts and streaming* and *Declared capabilities of a model*. A host that has a conversation (the web app's Copilot: its history, and the images the author attached) gives `AiRequest.messages` (`{ role: "system" | "user" | "assistant", content }`, the content text or a list of parts, `{ type: "text", text }` and `{ type: "image", dataUrl }`) and that is what is sent, in place of `system` and `user` (give empty text); a part of text goes out as a text part and an image as an `image_url` with its data URL, and an image weighs `IMAGE_TOKEN_ESTIMATE` (4096) tokens of the prompt, whatever its size. With a structured request the JSON instruction of a model without tool calls goes into the first system message (into one of its own, placed first, when there is none). The messages are never changed. A request without `messages` is built exactly as it always was. |
| Output limit | A structured request gets at least `STRUCTURED_OUTPUT_FLOOR` (4096) tokens. A model known to reason by name (o1/o3/o4, gpt-5, codex-mini; for Azure the declared underlying model, else the deployment name) gets `REASONING_OUTPUT_MARGIN` (12 000) more, because its reasoning is counted in the limit; so does a model whose configuration declares `supportsReasoning: true` (a declaration never takes away the margin of a model known by its name). Never above the model's own `maxOutputTokens`. An Azure deployment of unknown identity gets `max_completion_tokens` from API version 2024-09-01, `max_tokens` before. |
| Prompt size | A candidate whose `maxInputTokens` (context window) cannot hold the prompt (estimated with `likelyMessageTokens`, the tool schema included, against `resolveModelTokenBudgets`: window minus the output reserve minus a 5% margin) is skipped. If no candidate can, `AiPromptTooLargeError` (not retryable) gives the estimate and the largest budget. A prompt is never cut. |
| Privacy of fallbacks | `fallbackDisclosure.sameBoundaryOnly` excludes fallbacks outside the primary's integration (the boundary). `requireAcknowledgement` asks `options.acknowledgeFallback(from, to, { capability, label })` before content goes to an integration it has not gone to: only `true` allows it, a throw cancels the call, and a host without the hook (the server) never crosses (fail closed). The engine asks at every call that needs the crossing (once per pair of accounts within a call), so a host that remembers acknowledgements answers from its memory. When nothing is left to call, the error names the setting and how to change it. |
| Routing limits | `routingExecution`: `maxCandidates`, `maxTotalDurationMs`, `maxTokenAttempts`, `maxEstimatedCost`. The total time never interrupts the first candidate before its own timeout; later candidates start only while time remains and run for what remains. Tokens and cost are estimated per attempt from the real prompt and the output limit (reasoning margin included): candidates are kept while the sum fits, and a first attempt that alone exceeds a limit gives `AiRoutingBudgetError`. A configuration without these fields (saved by an older host) has no such limits and no privacy policy. |
| Timeouts | Three, in every host: how long the provider has to begin answering (an integration's `requestTimeoutMs`, else `options.defaultTimeoutMs`, else `DEFAULT_REQUEST_TIMEOUT_MS`, 600 s; never under 30 s), the longest silence while it answers (`idleTimeoutMs`, 600 s) and the most one call may take (4 h). See *Timeouts and streaming*. |
| Hooks | `onAttempt(attempt)`: `attemptId`, the effective `messages` (with the JSON instruction a model without tools receives), the output limit, `stream`, `streamMode`, `tools`, `endpoint`, `timeoutMs` and `timeouts` (the three deadlines: see *Timeouts and streaming*), `toolsOnly` (whether Tools only was in force), `thinking` (the level sent, absent when none was), `reasoningParameter` (where it went, only when it went as the chat-template argument: see *Thinking*), `skipped` (the models left out, absent when none was: see *Tools only* and *Thinking*) and `notes` (what the attempt does not do that the configuration asked, because of what the model declares, in English; absent when there is nothing to say: see *Declared capabilities of a model*). `onAttemptEnd(end)`: the same `attemptId`, `outcome` (`ok`, `failed`, `cancelled`), `usage`, `cost`, `usageKnown`, `costKnown`, the reply `text` or the `error` (without credentials), `failureKind` (`timeout`, `cancelled`, `provider`), `status`, `retryAfterMs`, `timeoutMs` and `timeoutPhase` (for a timeout), `streamed`, `firstByteMs`, `toolCalled`, `durationMs` and, once a reply was read, `finishReason` (the provider's own word, empty when it said none), `replyCharacters` (its text without the reasoning, and the arguments of its function, `{}` being none) and `reasoningCharacters` (the reasoning field of the provider, and a `<think>` block in the text: the count, never the words), for every attempt that was sent, failed ones included; the three facts are there also for a reply the engine refused after reading it (one that was cut, or filtered), and absent for an attempt that never got one (a refusal, a connection that failed, a deadline that ran out first). The `messages` of `onAttempt` are copies and carry the roles and the parts (an image with its data URL), so a listener cannot change what is sent. A hook that throws never breaks a call. |
| Approving endpoints | `effectiveAiBase(integration, githubModelsBaseUrl?)` is the origin and path every request of an integration starts with, defaults included (`https://api.openai.com/v1`, `https://models.github.ai/inference`). A host that approves where API keys may be sent should compare these. |
| Wire format | Server-sent events with several `data:` lines are joined with a newline; the pieces of a forced function call (`delta.tool_calls[].function.arguments`) are joined into the arguments of the reply, and a last piece that carries the whole `message.tool_calls` is read too; a JSON reply to a streaming request (a server that ignores `stream`) is read as the reply; an `error` in a 200 reply is a provider error, and so is an `event: error` whatever its data is. A line ends with LF, CR or CRLF (the three that the SSE specification allows, a CRLF cut between two chunks included); a `data:` with no space after it, a last line with no newline, and `: comments`, `id:` and `retry:` lines are read as they should be; a character that a chunk cuts in two is kept until the rest comes. The tokens are read from whichever chunk carries `usage` (`prompt_tokens`/`completion_tokens`, or `input_tokens`/`output_tokens`; the cached ones from `prompt_tokens_details.cached_tokens`, `input_tokens_details.cached_tokens`, `prompt_cache_hit_tokens` or `cache_read_input_tokens`); a count of zero never replaces a real one. |
| Errors | `AiProviderError` carries `status`, `retryable`, `transient` (it depends on the moment: 408, 429, 502, 503, 504, Cloudflare's 520-524, network, a stream that stopped), `transport` and `partialText` (what the transport saw of the call, and the reply that had arrived: see *A stream that stops halfway*), `retryAfterMs` (the `Retry-After` of a 429 or 503, at most five minutes), `timedOut` with `timeout` (which deadline ran out, for how long), `truncated` and `reasoningOnly` (the reply was cut while the model reasoned: seen as reasoning, or, with nothing written at all, from a model declared as reasoning). `AiToolsRequiredError` (nothing can be asked: Tools only is on and no model can call a function; see *Tools only*) is the error of a call that was never sent. Keys, `Bearer …`, `api-key: …`, `?key=…` and `sk-…` are removed from every message (`redactSecrets`), also before the runner saves it. The error of a candidate that was tried carries `target` (`{ provider, model, integrationId, endpoint? }`, the endpoint only an origin: see *What the interface reads*). |

### Timeouts and streaming

*Why.* A slow model (a 30B one) behind a proxy used to fail every time with "request timed out": the client had **one** absolute timer for the whole call, and a structured reply (a forced function call) was never streamed, so the only thing that arrived was the whole answer once the model had finished. Any timeout shorter than the generation failed, and even a long one could be cut by a proxy or a tunnel that closes a connection that stays silent (100 s is typical). Now the deadlines are separate and every reply streams, so a model that is alive is never silent and a connection that is dead is found.

**The deadlines** of one call, in every host:

| Deadline | What it limits | Default | Where it is set |
|---|---|---|---|
| **Start** | From sending the request until the headers arrive (the connection included). For a request that does not stream (`streamMode: "off"`) it is the whole call, body included, as it always was. | 600 s (`DEFAULT_REQUEST_TIMEOUT_MS`), never under 30 s (`MIN_REQUEST_TIMEOUT_MS`) | The integration's `requestTimeoutMs`, else `options.defaultTimeoutMs`. A lower value (6000) is **raised to 30 s when the call is made** and says so; the configuration keeps what the author wrote. |
| **Idle** | The longest silence between two pieces of a stream, from the headers on. Every byte starts it again, a comment such as `: keep-alive` included. | 600 s (`DEFAULT_IDLE_TIMEOUT_MS`) | The integration's `idleTimeoutMs`, kept between 30 s and 3600 s (`MIN_IDLE_TIMEOUT_MS`, `MAX_IDLE_TIMEOUT_MS`). |
| **Total** | The whole call, whatever the provider keeps sending. | 4 h (`TOTAL_REQUEST_CAP_MS`) | Nowhere: it is not configurable. |

The author's `signal` wins over all three: a call cancelled is an `AbortError` and never a timeout, even when a deadline runs out at the same moment. `routingExecution.maxTotalDurationMs` is unchanged: the first candidate runs for its own deadlines, and a later one for the routing time that is left, which limits all three and which no minimum raises. No timer outlives a call, however it ended.

**Streaming.** `integration.streamMode` is `"auto"` (the default) or `"off"` (`pickAiRuntimeConfig` leaves out anything else). In `auto` **every** chat request streams, the forced function of a structured one included (`stream`, `tools` and `tool_choice` travel together). The arguments of the function arrive in pieces (`choices[].delta.tool_calls[].function.arguments`): the reader joins them by `index` (a piece without one belongs to the only call there is), takes the call of the function that was asked for, else the first, and ignores any other; a stream whose last piece carries the whole `message.tool_calls` is understood as well. The joined arguments are what `structuredFromReply` reads, exactly as before, and their characters are what an estimated `usage` counts when the provider reports none. `"off"` never streams: use it for a provider or a proxy that cannot. A JSON body in answer to a streaming request (a server that ignores `stream`) is read as a whole. Prose is unchanged: `onText` gets the text so far (and once, whole, for a reply that came as one JSON body). For a structured request `onText` is never called.

**Node's own limits.** In Node the platform's `fetch` (undici) has two limits of its own, 300 s each, whatever the engine's deadlines say: `headersTimeout` (the headers of a response) and `bodyTimeout` (the silence between two pieces of a body). A host that runs the engine in Node and wants a longer silence than five minutes (a model that thinks for ten without sending anything) passes, as `options.fetch`, a `fetch` over a dispatcher with those two raised, or off (`0`).

**What the server does about it.** The personal server does not have this limit: the `fetch` of its process is its outbound guard (`installOutboundNetwork`, on `node:http`), which limits the connection and nothing after it, so there the idle deadline above is the only limit of a silence (its tests pin it). The measured limit of Node's own `fetch` is 300.9 s on Node 22 and 24: a body that is silent that long ends with `TypeError: terminated` (`BodyTimeoutError`), a response whose headers take that long with `fetch failed` (`HeadersTimeoutError`), and the client reads the first as a lost connection.

**Gateways in between.** Whatever the idle deadline is, a gateway between the app and the model has its own, and the shortest one decides. LlmProxy resets the connection (`context.Abort()`: no last chunk, no `[DONE]`, no error event) when its runtime sends nothing for `Gateway:UpstreamIdleTimeoutSeconds` (300 s unless its owner changed it; 5 s to 24 h) or when the runtime's connection breaks, and answers JSON errors (`error.code`: `capacity_exhausted`, `model_not_running`, `capacity_lease_lost`, `upstream_unreachable`, `upstream_timeout`, `rate_limit_exceeded`, `token_budget_exceeded`...) only before the first byte. Cloudflare in front of it closes a connection that has been silent for 100 s (`524`). LlmProxy starts its response before the model says a word, so a long prefill is a silence of the *stream*: **Idle** is its limit, not **Start**. To let a model think for longer than a gateway allows, raise the gateway's limit and the integration's **Idle timeout** together (the gateway's first); and where a call ends as "the connection was lost" with the transport saying that the last chunk came a round number of seconds before the end (`silentMs` of about 100 000 or 300 000), it is the gateway that cut a silent stream. Without a keep-alive from the model there is nothing the client can do about that, and `: keep-alive` comments from a gateway that sends them are enough to keep the count going.

**A stream that stops halfway.** When the provider has begun to answer and the reply does not reach its end, the client does not return it and does not forget it: it throws an `AiStreamInterruptedError` (an `AiProviderError`, always `retryable` and `transient`, so the run repeats the step as it repeats any failure of the moment, and does not give up on two identical messages) whose `how` says what happened: `lost` (the connection broke), `ended` (the provider closed the stream without `[DONE]` and without a finish reason, or with one the client does not know), `provider-error` (the runtime reported a failure inside the stream, whatever status it gave it: a 500, a crash, no status) or `provider-abort` (the finish reason was `abort`, `error`...). A failure that cannot change by asking again is final even then: an invalid request (a 4xx other than 408, 409 and 429) or the credentials refused, and one that is reported before the model wrote a word keeps the rule it had (`transient` only when its status or words say so). What had arrived is kept: `error.partialText` is the text, else the arguments of the function, of at most `MAX_PARTIAL_CHARACTERS` characters (never the reasoning, never a credential), and the client **never applies it**. The tokens of the call are an estimate (`usageKnown: false`) unless the usage chunk came before it stopped.

`error.transport` (and `end.transport` of `onAttemptEnd`, for the attempt that failed and, as figures only, for one that worked) says what the transport saw: `status` (the response's: a stream that is cut still began with a 200), `bytes`, `chunks` and `events` that arrived, `lastChunkAfterMs` and `lastChunkAt`, `silentMs` (the silence before the end), `tail` (the last 300 characters that arrived, as they came, with credentials replaced and the words of the reasoning left out; only for a failed attempt, and words of the model that a host should treat as it treats the reply), `finishReason`, `usageReceived` and `usageRequested` (whether the provider reported the tokens, and whether the request asked it to), `end` (`done`: `[DONE]`; `closed`: closed without it; `reset`: the connection broke; `error`: the provider reported a failure; `timeout`: a deadline ran out) and `requestId` (`X-LlmProxy-Request-Id`, `X-Request-Id`...: what the provider or its gateway calls the request). The run keeps a short form of it in `errorDetail.transport` (see *What the interface reads*), the debug panel of the app shows its figures and never the tail, and no field of it is ever a key.

**The tokens of a stream, and `stream_options`.** The client asks every provider for them (`stream_options: { include_usage: true }`), reads them from whichever chunk carries them and, when none comes (a provider that ignores the option, a stream that stopped before the usage chunk, a count of zero), estimates them from what arrived and says so: `usageKnown: false`, `costKnown: false`, and the run counts the call among its «calls without token count». A provider that **refuses** the option (400 or 422 naming `stream_options` or `include_usage`) is asked again, at once, without it, and the attempt goes on as one attempt; `FetchAiOptions.usageOptionRefusals` is where that is remembered (default: one set for each client, so every call asks once; an embedder that wants to ask once for all its calls shares one set).

**Progress.** `AiRequest.onProgress({ bytes, events, characters })` is called while a reply streams, at most every 250 ms, with numbers and never a word of the reply: the bytes received (comments included), the events of the stream and the characters of the reply so far (text and function arguments, not reasoning). It is how a host says "the model is answering (12 KB)" for a structured reply. A listener that throws never breaks the call.

**Closures and limits.** A stream that closes without `[DONE]` and without a `finish_reason` is still *incomplete* (retried as a transient failure); the reader is cancelled however a call ends, the end of the stream aside: after `[DONE]`, an error in the stream, a deadline, the author's cancel. Two limits stop a model that loops: **256 MB** of transport (`MAX_STREAM_TRANSPORT_BYTES`; the JSON envelope of every piece counts) and **16 million characters** of reasoning (`MAX_STREAM_REASONING_CHARACTERS`). Each is an error that says what it used and what to do ("Lower the thinking effort of the model or choose another one") and is **not** retried, because the same loop would come back; what it used is counted in the cost.

**What a timeout says.** The `AiProviderError` of a timeout is `timedOut`, `transient` and `retryable` as ever (the run retries it like any transient failure, and its `errorKind` is `timeout`), and carries `timeout: { phase: "start" | "idle" | "total", ms, raisedFrom? }`, which is also in `errorDetail` as `timeoutPhase` and `timeoutMs` (see *What the interface reads*). The message, in English and without a key or an address, says which deadline ran out, how long it was and where it is changed:

- `openai muse-glimmer-30b: the provider did not start answering within 30 s (the "Provider timeout" of the integration "LlmProxy" was 6 s and was raised to the 30 s minimum)`
- `openai muse-glimmer-30b: the provider sent nothing for 600 s while answering (the "Idle timeout" of the integration "LlmProxy")`
- `openai muse-glimmer-30b: the provider did not finish within 4 h (the longest one request may take: it cannot be changed)`
- a later candidate cut by the routing time: `…: request timed out: the provider did not finish within the 150 ms left of the total routing time (maxTotalDurationMs)` (its `timeout` says `routing: true`: the limit is the author's «Total routing time» less what the candidates before it took, which can be raised, and not one of the call's own)

An integration without its own value says `the default provider timeout` or `the default idle timeout` and where to change it.

**What the hooks say.** `onAttempt(attempt)` carries `timeouts: { startMs, idleMs, capMs, raised?: { from } }` (the deadlines as they are applied, `raised` when the minimum lifted the provider timeout) and `streamMode`; `timeoutMs` is `timeouts.startMs`. `onAttemptEnd(end)` carries `streamed` (the reply was read as a stream), `firstByteMs` (milliseconds to the first byte of its body, or of the response for a JSON reply; absent when nothing arrived), `toolCalled` (for a structured request, whether the model delivered the result as a function call; absent otherwise) and, for a timeout, `timeoutMs` and `timeoutPhase`. It also carries `transport` (see *A stream that stops halfway*: for an attempt that worked, its figures only) and, for an attempt that failed after the model had begun to answer, `partialText`.

**Providers that cannot stream.** A provider that rejects `stream_options` is asked again without it (see *The tokens of a stream, and `stream_options`*); one that does not stream with functions answers 400, and the error then adds `If this provider cannot stream its replies, set "Streaming" of the integration "…" to "off"` (only when its own message talks about streaming), and `streamMode: "off"` brings the old behavior back for that integration. A model that cannot stream while the others of its integration can declares `supportsStreaming: false` instead (see *Declared capabilities of a model*): only that model is called without `stream`. Leave a model that reasons streaming wherever you can: its reasoning counts against the output limit, and a reply that does not stream is silent until it is whole, which a proxy or a tunnel may cut (LlmProxy's own documentation says the same of its reasoning models). A connection that is lost while the provider answers is told with what to check: the proxy or the tunnel between the app and the provider.

### The route of a call

The route is the author's, place by place: the primary is position 0 and the fallbacks follow, in the order they wrote them. `describeAiRoute(config, capability)` answers it as `AiRouteEntry[]`: the candidate that stands in each place, or, for a target that cannot be called (its integration is gone, its provider cannot chat here, its model is not in the integration, the model is not allowed the task), the target and why (`unusable`: `integration-missing`, `provider-unsupported`, `model-missing`, `task-not-allowed`). `resolveAiCandidates` is what is left of it, as it always was. A candidate that cannot be called keeps its place, so that the fallback that is asked instead is never taken for the primary: `attempt.index` (`onAttempt`, `onAttemptEnd`) is the place in the route as written, 0 for the primary.

What became of every candidate is an `AiRouteStep`: `{ position, integrationId, integrationName, provider, model, outcome, endpoint?, status?, durationMs?, message?, timeoutPhase?, timeoutMs?, routing?, leftOut?, why?, promptTokens?, windowTokens? }`. `outcome` is `ok`, `failed`, `timeout`, `cancelled` for a candidate that was asked (with what the provider said, cleaned of credentials and cut at 240 characters, and for a timeout which deadline ran out and, with `routing`, that it was the routing time that was left and not a limit of the call), or `left-out` for one that was not, with `leftOut` saying why: `unusable`, `no-tool-calls` (Tools only), `boundary` (`sameBoundaryOnly`), `context-window` (the prompt needs `promptTokens` and the model's window leaves `windowTokens`), `budget` (`maxTokenAttempts` or `maxEstimatedCost`), `not-acknowledged` (`requireAcknowledgement`) or `out-of-time` (`maxTotalDurationMs` was used up).

- **The error of a call that failed has the whole route.** `AiProviderError.route` (also `AiUnavailableError.route`, for a route written and none of it callable, whose message then names each target and why) is every step in the order of the route: the primary that failed at once, then the fallback that ran out of time. `error.target`, `error.model` and the rest of the error are still the last candidate's. The notes that the message ends with now also say a candidate that the context window or the routing limits left out, and a target that cannot be called. `classifyAutopilotError(error).detail.route` and `errorDetail.route` keep it, cleaned (valid steps only, no credential, an endpoint only as an origin, at most `MAX_ROUTE_STEPS`, 12).
- **The attempts say what was left out.** `onAttempt(attempt).leftOut` is every candidate the plan leaves out, each as a step (the same list on every attempt of the call, with a fallback that the author did not acknowledge added to the attempts after it). It is in addition to `skipped`, which keeps its shape.
- **The records keep it.** The record of a call (`AiCallRecord.attempts`) lists the candidates that were left out beside the attempts that were asked, in the order of the route, numbered from 1 together: an entry with `outcome: "skipped"` and `skip: { reason, why?, promptTokens?, windowTokens? }`, no duration, no usage, no error. `CallEndInfo.attempts` and the `call-ended` event count only the attempts that were asked.
- **A host that is ending.** `createFetchAi(config, { interrupted })`: while it answers `true` (a browser page that is being reloaded or closed), a request that fails is a failure of the host and not of the provider. The attempt is closed as `cancelled` and the call ends with the failure: the next candidate is not asked, because it would be sent the whole prompt, and billed, by a host that is no longer there.

### Tools only

Every autopilot agent answers through a function of its own (the concept, the plan, a reader's evaluation, the director's decisions, the summary of a scene… each has its schema, and the request forces the call with `tool_choice`): the answer is a field that is parsed, not a JSON that the message asked for and that the engine had to find in some text. *Tools only* makes that the only way. It is on unless the configuration turns it off: `AiRuntimeConfig.toolsOnly`, which `pickAiRuntimeConfig` reads from `settings.aiToolsOnly` (and from `toolsOnly` in a configuration that was already picked, which is what a personal server stores and reads back; the settings' own word wins when both are there, and a value that is not a boolean is ignored). A host with no such setting has it on. `redactAiRuntimeConfig(config).toolsOnly` says what is in force.

With Tools only on, a request with a function (`json`; a request for prose never changes) behaves like this:

- **A model marked as without tool calls is skipped** (`supportsToolCalls: false`: the "Forced tool calls" switch of the model in AI Integrations), a primary and a fallback alike, and nothing is sent to it. A model whose tool calls were never declared is asked as before: only an explicit `false` skips. The privacy policy is applied to the whole route first (a skipped primary is still the account that `sameBoundaryOnly` keeps the content in), and the position of a candidate in the route (`onAttempt.index`) does not move. `AttemptPlan.skipped` and `onAttempt.skipped` say what was left out (`[{ model, reason: "no-tool-calls" }]`, the same list on every attempt of the call, absent when nothing was skipped), and the final error of a call that failed says it too: `Skipped "beta-model" in "Beta": it is marked as without tool calls and "Tools only" is on.` The route is cut to `maxCandidates` before the skipping, so a skipped candidate counts against it.
- **If none is left**, the call ends before anything is sent with `AiToolsRequiredError` (an `AiProviderError`, not retryable, with `models`: the names of the models that were left out, and `skippedModels`: the same as `{ integration, model }`, the integration by its id, since two integrations may have models of the same name; empty from a host that made the error without it). Its message names them and says the two ways out: `"Tools only" is on, and every model this task can use is marked as without tool calls ("alpha-model" in "Alpha"), so a structured answer has nowhere to go. Turn on "Forced tool calls" for the model in AI Integrations, or turn off "Tools only" in the AI Router. Nothing was sent.` Its `errorKind` is `config`: the configuration has to change, so the run stops at once instead of retrying (see *What the interface reads*).
- **The answer must be the call of the function.** The arguments of the call are used, however they arrive (whole, or in the pieces of a stream) and with the tolerance they always had (double-encoded, or wrapped in `arguments` or `result`). The text of the reply is never read: not as the answer, and not as a fallback for arguments that are empty (`{}`, still rejected as they were) or that carry none of the expected fields. A reply that has text and no call is rejected, retryable like every rejected reply (the next candidate is tried, and the run repeats the step once with the reason), and what the attempt cost is kept: `openai muse-glimmer-30b: the model answered in text instead of calling the function "result": "Tools only" is on, so the text of a reply is never read as the answer. If this model cannot call functions, turn off "Tools only" in the AI Router.` A reply with nothing at all is still an empty reply.

With `toolsOnly: false` it is all as it was: a model without tool calls is used and gets the schema in its system message, and the JSON in a text reply is the answer when the function was not called. `onAttempt.toolsOnly` says which of the two was in force for a call.

### Thinking

How hard a model is asked to think, per integration and per route target, and in which parameter the level reaches each model. `AiIntegrationConfig.thinking` and `AiRouteTarget.thinking` (the primary and every fallback of a task's route) are one of `AI_THINKING_LEVELS`: `"automatic"`, `"low"`, `"medium"`, `"high"`, `"xhigh"`. `pickAiRuntimeConfig` keeps a level spelled exactly so and drops anything else (the target, or the integration, is kept without it).

| The setting | What the request carries |
|---|---|
| absent on the target | the level of its integration, when it has one |
| absent on both | no level |
| `"automatic"` | no level, even when the integration has one |
| `"low"`, `"medium"`, `"high"`, `"xhigh"` | the level, in the parameter that the model it goes to says (*How the level is sent*): `reasoning_effort` unless the model says otherwise, in the body of every chat request (OpenAI-compatible, Azure OpenAI, GitHub Models), for prose and for a structured reply, streamed or not |

`AiCandidate.thinking` is the level the candidate resolves to (`target.thinking ?? integration.thinking`, absent when neither says), also for a task without a route of its own (then it is the integration's); a fallback has its own, the primary's is never carried to it. The `default` route only chooses the integration of the tasks that have no route, so its `thinking` is not used. `buildChatRequest` sends the four levels and nothing else, in the parameter of the model, and `ChatRequest.thinking` says what it sent; `onAttempt.thinking` is that level and is absent when nothing was sent.

*How the level is sent.* Not every model takes its level as `reasoning_effort`, the OpenAI field. Meta's documentation says of Muse Glimmer, the owner's main model, that it takes its level (`low`, `medium`, `high`, `xhigh`) as an argument of its chat template and that `reasoning_effort` is not implemented by llama.cpp (LlmProxy's `docs/model-profiles.md` says the same: «Do not assume the OpenAI field»); ExecuTorch rejects `reasoning_effort` with a 400. So the model says it: `AiChatModelConfig.reasoningParameter`, the **"Thinking parameter"** of the model in AI Integrations («Parametro del thinking» in Italian), one of `AI_REASONING_PARAMETERS`. `pickAiRuntimeConfig` keeps it only when it is spelled exactly so (`normalizeReasoningParameter`), the safe view shows it, and `AiCandidate` carries it.

| `reasoningParameter` | What the body carries for a level |
|---|---|
| absent, or `reasoning_effort` | `reasoning_effort: "<level>"`, as it always was: a model that does not say is called with the very requests it always had, byte for byte |
| `chat_template_kwargs.reasoning_strength` | `chat_template_kwargs: { "reasoning_strength": "<level>" }` and no `reasoning_effort`, in the place where `reasoning_effort` goes. It is merged with any other key that `chat_template_kwargs` already has in the body (`applyReasoningLevel` is the one place where a level lands in a body; the body has no other today) |
| `none` | Nothing, even when the task or the integration asks for a level. The attempt says so in its `notes`: `The thinking level "high" was not sent: "muse-glimmer-30b" has its thinking parameter set to "none".` (a model that is also declared as not reasoning says this one: it is the author's own word) |

The levels, and who sets them (the target, the integration, `automatic`), are the same for the three; `supportsReasoning: false` still sends no level, whatever the parameter. `ChatRequest.reasoningParameter` and `onAttempt.reasoningParameter` say where the level went, **only** when it went as the chat-template argument (absent: it went as `reasoning_effort`, or no level was sent), and `thinking` is the level either way. The gateway has to let the field through: LlmProxy does (it rewrites the `model` of the body and caps the token limits, and forwards the rest to the runtime).

*The hint.* `suggestedReasoningParameter(modelName, underlyingModel?)` is a pure hint for the screen that offers the setting, never an order: it gives `chat_template_kwargs.reasoning_strength` for the model names that a documented source ties to the chat-template argument, and `undefined` for every other name. Today that is Muse Glimmer and nothing else (`muse-glimmer`, `muse-glimmer-30B`, `meta-models/Muse-Glimmer-30B-GGUF:Q4_K_M`, `unsloth/Muse-Glimmer-30B-GGUF`, `muse-glimmer:30b-mlx`, `meta-muse-glimmer`: what comes before the last `/`, and a tag after the name, do not matter; Muse Spark and every other family are not guessed, because no source says it). The sources are cited in the comment of the function: Meta's "Run inference" and "Prompting guide" pages for Muse Glimmer, and LlmProxy's `docs/model-profiles.md` with its Muse Glimmer profile. With a declared `underlyingModel` (an Azure deployment) that is the name that is read, as `isReasoningModel` does. The engine never applies the hint by itself: a model is called with `reasoning_effort` until its author sets the parameter.

*A provider that does not accept it.* A 400 or a 422 that names `reasoning_effort`, `reasoning_strength` or `chat_template_kwargs`, in its message or in its error object (`"param": "reasoning_effort"`), while a level was sent, is a permanent error that is not repeated and says what to change. Either name is a refusal of the level, whichever of the two was sent (a gateway may answer with the name of the one it translated the level into), and the remedy names the setting of the model and offers the other parameter and `none`: `openai muse-glimmer-30b: the model does not accept a thinking level (HTTP 400 — Unrecognized request argument supplied: reasoning_effort). Nothing was applied. Set "Thinking parameter" of the model "muse-glimmer-30b" in AI Integrations to "chat_template_kwargs.reasoning_strength" (the level as an argument of the chat template, as Muse Glimmer takes it) or to "none" (no level is sent), or set thinking to "Automatic" for this task in the AI Router, or for the integration "LlmProxy" in AI Integrations.` When the level was sent as the chat-template argument, the parameter offered first is `"reasoning_effort"` (the OpenAI field). The next candidate of the route is tried (it may have no level, or another parameter); when the run ends on it, its `errorKind` is `provider` and `errorDetail.status` is 400. With no level sent (nothing chosen, `automatic`, `reasoningParameter: "none"` or `supportsReasoning: false`), on any other status, or for an error that talks about the chat template and not about its arguments, the error is the plain one it was. The engine does not know which models reason unless the configuration says it: with `supportsReasoning: false` on a model the level is not sent to it at all (and the attempt says so in its `notes`: `The thinking level "high" was not sent: "muse-glimmer-30b" is declared as not reasoning (supportsReasoning is off).`), so an integration with models of both kinds can carry a level and spare the ones that would refuse it; a model that declares nothing is sent the level, as before, so give a level to an integration that has only models that take one, or to the route targets that use them.

`redactAiRuntimeConfig(config)` shows what is set, none of it secret: the level of every integration (`integrations[].thinking`), the route of every routed task with the level of each target (`taskRouting`: `{ primary?, fallbacks }` for each task, `{}` when there is no route), `toolsOnly` and, for every model, what it declares and how its level is sent (`integrations[].models[]`: see *Declared capabilities of a model*, and `reasoningParameter` above).

### Costs and budgets

`estimateCost` bills cached tokens like normal input unless the model has a `cachedPerMTok`. A reply carries `usageKnown` and `costKnown`: when the provider reports no tokens, `usage` is an estimate (`usageKnown: false`, `costKnown: false`); a model without a price has no `cost`. The autopilot counts those calls in `stats.usageUnknownCalls` and `stats.costUnknownCalls`, says once per run that the money budget (`options.budgetLimit`) cannot apply to a model without a price (`budgetNotApplicable`), and `options.budgetTokens` stops the run at a number of tokens instead (0 = off).

### Retries

A step that failed with a transient provider error is retried up to three times, after about 4 s, 12 s and 36 s (with jitter, never sooner than the provider's `Retry-After`); the `failureRetry` insight carries `attempt`, `retries` and `waitMs`. A rejected reply, or a failure that is not the provider's, is retried once, the first with the reason. The same failure twice in a row that does not depend on the moment (an empty reply, a 500 with the same message) stops the run at once. A failure that is marked as not retryable is never repeated: the run stops with it (a 401, a call that no model can take because Tools only is on, a 400 that refuses the thinking level). A reply cut while the model had only reasoned is retried once with an output limit three times larger (`AiRequest.outputBoost`), and the next steps of that kind start with it; a model declared as reasoning (`supportsReasoning: true`) whose reply is cut with nothing written counts as one that only reasoned, even when its server does not show the reasoning. `retryDelayMs` is the base delay: every delay scales with it, `0` makes them instant. A pause ends the wait. While the run waits, `summary.retry` says when the next attempt is (see *What the interface reads*).

**Retry later** («Riprova più tardi»). `options.longRetry` is a second level, off unless the author turns it on: `{ everyMinutes, cycles }`, the minutes from 1 to 10080 (a week) and the cycles from 1 to 1000, or `"unlimited"` written as a word (a value that is absent is never read as consent; see *What the interface reads*). When the quick retries of a step are used up (or the same failure came twice in a row) and the failure is one that may pass with time, the run does not stop: it says so with the insight `longRetryWait` (`cycle`, `cycles`, `null` for no limit, and `waitMs`: «Il passo è fallito dopo i tentativi ravvicinati: riprovo tra 15 minuti (ripartenza 2 di 3)», *The step failed after the quick retries: retrying in 15 minutes (restart 2 of 3)*), waits `everyMinutes`, and then repeats the step from the book as it is then, with all its quick retries again. The cycles start from zero after every step that works. When they are used up the run stops with the error, as it would have without the option, and says after how many restarts: «Il passo è fallito ancora dopo 3 ripartenze (Riprova più tardi): …», with the code `longRetryExhausted` (an insight, and the `code` of `run-ended`). With `"unlimited"` it goes on until the step works, or the author pauses it.

- **Which failures.** Only a transient failure of the provider, a closed list (`classifyRetry(error)` says `{ short, long }`, crossed with the quick level): HTTP 408, 429 and 5xx, an endpoint that cannot be reached, a timeout, a stream that was lost or ended too early, an empty reply. Never a reply the engine rejected (it would be rejected again: the quick level gives it its one retry with the reason), an error that is not retryable (400, 401, 403, 404, 422, Tools only, a prompt no window holds, a reply cut by its limit, a runaway stream, the routing budget, a fallback the privacy settings keep out), another status the client retries (409), a failure of the book store or of a host, a conflict, the lease, the budget, a pause of the author, or anything nobody classified.
- **Part of the run, not a state of its own.** The wait is in memory, inside the run, which keeps the book: its heartbeat is saved every `persistHeartbeatMs` as during a long step, so another host does not take a run that waits for hours for a dead one. Nothing is saved for the wait (no plan of the next attempt in the book, no activity for the time that passes), and every attempt that failed is counted as always (its activity, its cost). The budgets, the limits of the run, a pause and the lease are checked before every step, as they always are: a run whose budget is already used up does not wait, it pauses for the budget. A pause (`"now"`, `"after-step"`) ends the wait at once, as it ends a quick one; `"after-chapter"` does not end the wait of a step of the chapter in progress. A host that takes the book over ends it at the next heartbeat: the run stops and writes nothing more (`takenOver`). The steps that end in a wait of «Retry later» do not count against the ceiling of steps of one run (`runStepCeiling`), which is there to stop a run that loops: the waits bound them, so `"unlimited"` is not cut short. If the process dies the run is interrupted like any other (its heartbeat grows old, or the same host sees it at once); started again, it repeats the step at once, with the cycles from zero.
- **While the run goes on.** `longRetry` is one of `LIVE_AUTOPILOT_OPTIONS`: `session.updateOptions({ longRetry })` changes it while the run goes on, also while it waits. New minutes or cycles count from the next cycle (the wait in progress is neither shorter nor longer, and the cycles already begun count); `longRetry: null` turns it off, and a run that waits for it stops at once with the failure it waited to try again, saying so (*"Retry later" was turned off while the step waited to be tried again: …*; in Italian «Riprova più tardi» è stato spento mentre il passo aspettava di essere riprovato: …), with the code `longRetryOff`. What another device saves reaches a waiting run with its next heartbeat.
- `retryDelayMs` scales the long wait too, as it scales the quick ones (`0` makes it instant), so a test never waits.

**Retry now** («Riprova ora»). `session.retryNow()` (and `AutopilotRun.retryNow()`) ends the wait before the next attempt, a quick one or one of «Retry later», so that the attempt starts at once: `true` when the run was waiting, `false` when there is no run or it is not waiting (nothing happens, and it is no error). It uses up nothing more and gives nothing back: the retry, or the cycle, the wait belonged to stays counted. The insight `retrySkipped` says it, with the `waitMs` that was left («Attesa saltata: riprovo subito (14 minuti prima del previsto).», *Wait skipped: retrying now (14 minutes early).*), and a `state` event without `retry` follows at once. It is not a pause: a pause asked before or after it works as always.

### What the model's replies must be

- A forced tool call must carry at least one of the schema's required fields (else one of its declared properties). With *Tools only* on (the default) the text of the reply is never read and a reply with no call is rejected; with it off the JSON in the text is used when the call says nothing useful, and a reply with neither is rejected. A rejected reply is retried once with the reason.
- `<think>` blocks are dropped, and so is everything up to the last `</think>` of a model that never opened it.
- What the engine escapes in prompts (`&amp;`, `&lt;`, `&gt;`) is un-escaped in prose and in every text field of a structured reply (`unescapePromptData`).
- The director decides with a score: the reply must carry `verdict` and `score` (0-10; above 10 and up to 100 is read as a percentage). An `approve` below the `approvalScore` of `director.md` counts as `revise`, with the reason in the record, for the plan, every chapter, the final review and `askDirector`.
- A simulated reader must answer with a score and its reaction. A reader whose reply is still incomplete after the retry is skipped (and said so): the review goes on with those who answered.

## Model catalog and declared capabilities

*Why.* The models of an integration, their limits and what they can do used to be typed by hand: a model had a switch for tool calls and two numbers, nothing read an endpoint, and the engine did not know whether a model streams, reasons or reads images. An OpenAI-compatible gateway can say all of it. BookWriter reads `GET /models` and `GET /models/details` when the author presses "Read /models", and LlmProxy (the gateway this was built against: its `docs/api-contract.md`) adds `GET /v1/modalities`. The engine reads the same three, validates what comes back, and keeps what a model declares so that its requests follow it. Everything here is additive: a configuration that says none of it is called exactly as it was.

### What is read, and from where

| Request | Needed | What it gives |
|---|---|---|
| `GET <base>/models` | yes | The OpenAI list, `{ "data": [{ "id": … }] }`. Without it there is no catalog. |
| `GET <base>/models/details` | no | LlmProxy's: for each model its `type` (`chat`, `embedding`, `image`, `speech`, `transcription`, `realtime` or `classifier`), `context_window` (prompt and answer together), `max_output_tokens`, `input_modalities`, `output_modalities`, `endpoints` and `capabilities: { streaming, tools, vision, reasoning }`. |
| `GET <base>/modalities` | no | LlmProxy's: everything the gateway offers, grouped by type (always the seven, in its own order, the ones that run nothing included) with the paths, the modalities and the models that run for each. |
| `GET <origin>/api/v1/models` | no | LM Studio's own list, asked only on this computer (see *LM Studio*). |

`<base>` is `effectiveAiBase(integration)`: the very base that the chat requests of the integration use (its endpoint, trailing slashes aside, or OpenAI's own), with the key in the same header; `catalogTarget(integration, path)` works it out and is `null` for an integration with no such list. Only integrations of the provider `openai` (any OpenAI-compatible endpoint) have a list to read. Azure OpenAI (a deployment is made by hand, and nobody lists them), GitHub Models (its catalog is at another address and in another shape, which a host reads as it already does) and Microsoft 365 are an `AiCatalogError` of reason `unsupported`, and nothing is sent.

**The contract of LlmProxy, as the engine recognizes it.** An entry of `/models/details`:

```json
{ "id": "muse-glimmer-30b", "object": "model", "type": "chat", "context_window": 131072, "max_output_tokens": 8192,
  "input_modalities": ["text", "image"], "output_modalities": ["text"], "endpoints": ["/v1/chat/completions", "/v1/responses"],
  "capabilities": { "streaming": true, "tools": true, "vision": true, "reasoning": true } }
```

- `null` is "not declared": a number that is not a whole number from `CATALOG_MIN_TOKENS` (256) to `CATALOG_MAX_TOKENS` (10 000 000) is absent in the entry the engine makes, never a `0`.
- **`false` is not "cannot".** The capabilities of a model are `chat && flag`: everything that the administrator did not declare is sent as `false`. A model that streams well, with its box not ticked, says `streaming: false`.
- LlmProxy's implementation always sends `type`, but the example in its contract leaves it out: an entry with no `type` (or one the engine does not know) has the type `unknown`.
- `/models/details` and `/modalities` say the same thing about a model. When both are read, what `/models/details` says wins field by field, what only `/modalities` says is kept, and an id that only they know is added (up to 2000).

### The parsers

Pure: no I/O, no clock. Everything that comes in is data from a server nobody vouches for: it is bounded, validated field by field, never trusted for what it is called (`__proto__`, `constructor` and `prototype` are never an id) and never quoted in an error. The limits are BookWriter's (`fetchModels`, `tokenLimitsFromDetails`).

| Function | Reads | Gives |
|---|---|---|
| `parseModelList(payload)` | OpenAI `GET /models` | The ids, sorted and without repeats. **All or nothing**, as in BookWriter, so that a wrong answer never replaces a catalog that was right: a payload that is not a list, an entry without a good id (a string of 1 to `CATALOG_MAX_ID_LENGTH` (256) characters, no space at its edges, no control character), an empty list (`empty`), more than `CATALOG_MAX_MODELS` (2000) entries, or a list that says it goes on (`has_more: true`: a first page is not the catalog, and the engine does not follow pages) (`too-large`) is an `AiCatalogError`. |
| `parseModelDetails(payload)` | `GET /models/details` | `AiModelCatalogEntry[]`, in the order received: `{ id, type, contextWindow?, maxOutputTokens?, inputModalities?, outputModalities?, capabilities }`. The numbers are there only when they are whole and in range; a capability only when it is a boolean; `type` is one of `AI_MODEL_TYPES` (`chat`, `image`, `speech`, `transcription`, `embedding`, `realtime`, `classifier`; case and spaces do not matter) or `unknown`; the modalities are short lower-case words, at most 16. An entry that cannot be one is left out and the others stay; at most 2000 entries are read. Only a payload that is not a list is an `AiCatalogError`. |
| `parseModalities(payload)` | `GET /modalities` | `AiModalityGroup[]` in the order received: `{ type, endpoints, inputModalities?, outputModalities?, modelCount, models }`. A model with no type of its own has the type of its group; `modelCount` is the gateway's when it is a count, else the models that were read; `endpoints` are short paths, at most 16; at most 32 groups, and 2000 models in each, are read. A payload that is not a list is an `AiCatalogError`. |
| `tokenLimitsFromDetails(entry)` | an entry | BookWriter's formula: see *The limits*. |
| `modelFieldsFromCatalogEntry(entry)` | an entry | What the entry can fill in a model of the configuration: see *The limits* and *Declared capabilities of a model*. |
| `parseLmStudioModels(payload)`, `lmStudioContext(models, id)` | LM Studio | See *LM Studio*. |

### Reading an integration

`fetchModelCatalog(integration, { fetch?, signal?, timeoutMs? })` gives an `AiModelCatalog`:

```ts
{ models: AiModelCatalogEntry[];                                   // every model, of every kind, sorted by id
  source: { models: true; details: boolean; modalities: boolean }; // which answers were read
  modalities?: AiModalityGroup[] }                                 // what the gateway offers by kind, when /modalities was read
```

- It asks `GET /models` first (needed), then, together, `/models/details` and `/modalities`. **Every failure of those two is silent**: the catalog is then what `/models` says, an id that only `/models` lists has `type: "unknown"` and says nothing of what it can do, and `source` says which answers were read.
- **The models of every kind come back, each with its `type`**, so that one call fills the models and the tables of the other tools (images, speech, transcription, embeddings). Without `/models/details` and `/modalities` the list has no kinds and every model is `unknown`: a screen that wants chat models then takes them all, as BookWriter does.
- A request is a plain GET: `accept` and the header of the key, nothing else, `credentials: "omit"`, `redirect: "error"` (a redirect is refused, not followed: the endpoint it points to is never asked), `cache: "no-store"`, `referrerPolicy: "no-referrer"`. The key is in no message and in no result.
- *Time.* An endpoint may be silent for `CATALOG_TIMEOUT_MS` (8 s) per request, before it answers and between two pieces of its answer (the silence is what is watched, not the total), and no request lasts more than `CATALOG_TOTAL_CAP_MS` (a minute), so an endpoint that trickles for ever is stopped all the same. `timeoutMs` is the host's choice of the silence, at most ten minutes (the cap is then that long, when it is longer than a minute). No timer outlives a call.
- *The body* is read in pieces, up to `CATALOG_MAX_BYTES` (600 KB): a type that is not JSON, a length that is not a number or is over the limit is refused before a byte is read; a body that grows past the limit, whatever its length said, is cut where it passes it; the reader is let go however the read ends.
- A cancelled `signal` is an `AbortError`, never a catalog (a call cancelled before it began sends nothing).

**Errors.** A failure of `/models` is an `AiCatalogError` (an `Error` with `name: "AiCatalogError"`, a `reason` and, when an HTTP status gave it, `status`). Its message is in English, names the integration, says why and what to do, and never quotes what the endpoint sent, the address or the key:

| `reason` | When | The message says |
|---|---|---|
| `unreachable` | No answer: the server is off, the address is wrong, a redirect was refused, the connection dropped (in a browser also CORS, which it cannot tell apart) | check that it runs, the address, the redirect, and CORS |
| `timeout` | It did not answer, or went silent, within the time; or the whole took longer than the cap | try again |
| `unauthorized` | 401, 403 | check the key |
| `not-found` | 404 | the address should end with the version path (`/v1`) |
| `rate-limited` | 429 | wait and try again |
| `server-error` | 5xx | it may be busy or restarting: try again |
| `http-error` | Any other status | check the address and the key |
| `invalid` | Not JSON, or not a list of models | the address may not be the API base |
| `empty` | A list with no model | start a model there (a gateway does not list one that is stopped) |
| `too-large` | More than 2000 models, a list that comes in pages (`has_more: true`), or more than 600 KB | enter the model names by hand |
| `unsupported` | Azure OpenAI, GitHub Models, Microsoft 365 | there is no list to read |

Every message that can be answered by typing says it: *enter the model names by hand*, which is what a host did before and still does.

**Providers whose `/models` is not OpenAI's.** Only the OpenAI shape, `{ "data": [{ "id": … }] }`, is read, and a list that comes in pages is refused: nothing here follows pages, and a first page must never pass for the catalog. Checked against the providers' documentation: Anthropic's `GET /v1/models` is `{ "data": [{ "id": …, … }], "has_more": … }` with 20 models to a page (its entries have an `id`, so without the refusal its first page would have been read as everything: it is `too-large`); Together AI answers a bare array; Cohere `{ "models": [{ "name": … }], "next_page_token": … }`; and Ollama's own list (`/api/tags`) is `{ "models": [{ "name": … }] }` (its OpenAI-compatible `/v1/models` is the OpenAI shape and is read). The bare array, `models` and `name` are `invalid`: never a half catalog, and the author enters the names by hand. The limits that a provider declares under other names (Anthropic's `max_input_tokens` and `max_tokens`, OpenRouter's `context_length`) are not read: only LlmProxy's `context_window` and `max_output_tokens` are.

### The limits

`tokenLimitsFromDetails(entry)` is BookWriter's formula, `{ inputTokens?, outputTokens? }`: **input** is the window minus the answer the model declares, or, when it declares none, minus a quarter of the window up to 4096; an answer with no window is only the answer; an answer that is not smaller than its window is not believed; an input that is not a usable number of tokens (it would be under 256) is not said. A window of 131072 and an answer of 8192 give `{ inputTokens: 122880, outputTokens: 8192 }`; with no answer, an input of 126976.

**Mind the difference.** BookWriter's `inputTokens` is what is left for the prompt once the answer is taken off. The engine's `maxInputTokens` is the context window itself (the field is labelled "Context window tokens"), and the engine takes off the answer and a 5% margin itself when it judges a prompt (`resolveModelTokenBudgets`): BookWriter's number put there would take the answer off twice. So `modelFieldsFromCatalogEntry(entry)` is what a host uses to fill a model: `maxInputTokens` is the declared window, `maxOutputTokens` is the declared answer (only when it is smaller than the window) and each capability is there only when it is `true`. `tokenLimitsFromDetails` is for a host that keeps BookWriter's numbers.

### Declared capabilities of a model

`AiChatModelConfig` has, besides `supportsToolCalls`, `maxInputTokens` and `maxOutputTokens`, three optional booleans: `supportsStreaming`, `supportsReasoning` and `supportsVision`. **Absent is as before**: a candidate that does not say is built into exactly the request it always was. `pickAiRuntimeConfig` keeps them only as booleans (anything else is dropped, so what is stored is picked again unchanged), `AiCandidate` carries them, and a personal server stores them and shows them (`PUT /ai` runs `pickAiRuntimeConfig`; `GET /ai` is the safe view) without any change to the protocol.

| Field | What it does |
|---|---|
| `supportsToolCalls` | Unchanged: with *Tools only* on, `false` skips the model for a structured request. Anything else is asked as before. |
| `supportsStreaming` | `false`: the model is called without `stream` and `stream_options` (and with `accept: application/json`), for prose and for a structured request alike (the function is forced all the same), whatever the `streamMode` of the integration says, and the attempt's `notes` say `Streaming was not used: "muse-glimmer-30b" is declared as not streaming (supportsStreaming is off).` It never turns on what `streamMode: "off"` turned off (and then there is no note: the integration already said it). |
| `supportsReasoning` | `true`: the model gets the output margin of a model that reasons (+12 000, never above its `maxOutputTokens`); a reply cut by the output limit with nothing written is a reply cut while reasoning (`reasoningOnly`: `…the model, which is declared as reasoning, used its output limit before writing the reply (its reasoning counts in the limit)`), which the autopilot retries once with a limit three times larger even when the server does not show its reasoning; and a thinking level may be sent (in the parameter of the model: see *Thinking*). `false`: a thinking level is **not** sent, and the attempt says so (see *Thinking*): a provider is never given a request that it would refuse. A model known to reason by its name keeps its margin whatever `false` says. The temperature and the name of the limit parameter (`max_tokens` or `max_completion_tokens`) do not change either: they follow the family of the model, not whether it reasons, because a local model that reasons takes both. |
| `supportsVision` | Nothing in a request depends on it: it is data for the interface (the engine sends no image). |
| `maxInputTokens`, `maxOutputTokens` | As before: the window decides whether a prompt fits (a candidate that cannot hold it is skipped) and no request asks for more than the largest answer. |

**Mind the window.** The margin of `supportsReasoning: true` comes out of the context window: the budget of a prompt is the window, minus the output limit of the request (the margin included), minus 5%. A model declared as reasoning with a window of 8192 and no declared answer, asked by a step for 2500 tokens, is asked for 14 500: the budget of the prompt is one token and the model is skipped (`AiPromptTooLargeError`, whose advice is about the window, not about the margin). With a window of 32 768 and a step that asks for 9000, the budget falls from 22 129 to 10 129 tokens; from 65 536 up there is room. Declare the largest answer of the model (`maxOutputTokens`: a catalog fills it in when the gateway declares it): no request asks for more, and the budget is computed with it (a window of 131 072 and an answer of 8192 leave 116 326 tokens for the prompt, margin or not). The same arithmetic has always applied to a model known to reason by its name.

`redactAiRuntimeConfig` shows `integrations[].models[]` as `RedactedAiModel`: `{ name, capabilities }` and, only for what the model declares, the six fields above (and its `reasoningParameter`, when it sets one: not a thing a catalog declares, but the author's word on how its level is sent, see *Thinking*).

**`false` is not a restriction.** LlmProxy says `false` for everything that nobody declared, so a catalog cannot tell a model that does not stream from one whose administrator did not tick the box. Importing `false` as `supportsStreaming: false` would turn streaming off for a model that works, and as `supportsToolCalls: false` it would take the model off every structured task: **`modelFieldsFromCatalogEntry` never turns `false` into a restriction, it only says `true`**, and a host that merges a catalog does `{ ...model, ...modelFieldsFromCatalogEntry(entry) }`: what the gateway declares wins for the fields it declares (as BookWriter's explicit "Read /models" does), and what it leaves out stays as the author wrote it. A `false` that the author sets by hand is respected. (This is also why the engine, unlike BookWriter, asks a model for a function unless it is marked `supportsToolCalls: false`: see *Tools only*.)

### The connection probe

`probeEndpoint(integration, { fetch?, signal?, timeoutMs? })` asks an OpenAI-compatible endpoint one short question, `GET <base>/models` (the same request as the first of the catalog, with the key, so that a gateway that refuses it is told from one that is off), and waits `PROBE_TIMEOUT_MS` (4 s, as BookWriter's `localEndpointTimeoutHint` does). It is the base of a "Check the connection" in an error panel (a failure of kind `network` or `timeout`: see *What the interface reads*). The result, `AiEndpointProbe`:

| `outcome` | When | The rest |
|---|---|---|
| `ok` | A 2xx arrived | `httpStatus`, `latencyMs` (until the answer began), `cors: "ok"` and, when the body is a list of models that could be read in time (up to 256 KB), `models`. A gateway with nothing running answers `models: 0` and the message says to start one. A 2xx that is not a list of models is `ok` all the same, without `models`, and the message says that the address may not be the API base (a web page, say). |
| `http-error` | Any other status: the server is reachable, and the status says what to fix | `httpStatus`, `latencyMs`, `cors: "ok"`; 401 and 403 say to check the key, 404 the version path (`/v1`), 429 to wait, 5xx that it may be busy or restarting. The body of an error is never read. |
| `unreachable` | No answer within the time, or the connection failed | `latencyMs`, `cors: "blocked-or-unreachable"`. **In a browser a request that CORS blocked looks exactly like a server that is off, an address that is wrong or a connection that failed**, and the message says so, and what to check. |

`message` is in English, with the remedy, and never has the key, the address or a word of what the endpoint sent. The probe throws only for a cancel (`AbortError`) and for an integration with no list to ask (`AiCatalogError`, reason `unsupported`): what the endpoint does is a result, never an exception.

### LM Studio

`parseLmStudioModels(payload)` reads LM Studio's own `GET /api/v1/models` as BookWriter's `lmstudio-models.ts` does: only the entries of `type: "llm"` (at most `LMSTUDIO_MAX_MODELS`, 500, with keys of at most `LMSTUDIO_MAX_KEY_LENGTH`, 200, characters), each as `{ key, reasoning?, maxContext?, loaded }`. `reasoning` is `{ options, default? }`, the levels the model allows in the engine's order (only `low`, `medium`, `high` and `xhigh` are levels: `off` and `on` are not) and the default when it is one of them; `null` when the server says the model has no level to choose; absent when it says nothing of reasoning. `maxContext` is the longest context the model supports and `loaded` the instances that are loaded now, with the context each was loaded with (at most 16). `lmStudioContext(models, modelId)` finds a model by its key or by the id of a loaded instance, as BookWriter does, and gives `{ loaded?, max? }`.

`fetchLmStudioModels(integration, options)` asks for that list at the root of the server (`<origin>/api/v1/models`, whatever path the endpoint has), **only of a server on this computer** (`localhost`, `127.0.0.1` or `[::1]`, with no credentials in its address) and only for an OpenAI-compatible integration; a key that is configured is sent, to this computer only. Anything else, and any failure (a server that is not LM Studio, one that cannot be reached, an answer that is not its list), gives `undefined`: this list is an extra, and the caller keeps what it knew. It throws only for a cancel.

### What stays with the host

The engine reads and says; it never reads a catalog by itself during a run and never saves one. The host decides when (an explicit "Read models" is what BookWriter does, and every failure there leaves the author typing), which models of the catalog become models of the configuration (the `chat` ones, and the `unknown` ones when neither `source.details` nor `source.modalities` was read), and keeps what the author typed for every field that the gateway leaves out. A host that runs these functions on a server must give them a `fetch` that applies its own policy for the endpoints that a key may be sent to: the functions do not decide that (`effectiveAiBase` is what to compare).

## AI calls

Each AI call of an autopilot task is recorded (`src/autopilot/calls/`): what was sent (system and user, as sent), what came back while it streamed, and each provider attempt (its endpoint origin, transport facts, usage, cost, a cleaned error). Hosts keep the records: the runner writes them through the port below, and the core (types, port, recorder, retention, the reference store) is in the same folder. The records are never sent anywhere else.

- **Types** (`types.ts`): `AiCallRecord` (identity, request, `status`, `response`, `attempts`, `timing`, `storedBytes`, `dropped`), `AiCallAttempt`, `AiCallTaskHeader` (the task that outlives the 200 entries of `activity.json`; `AiCallTaskDraft` is what a writer gives), `AiCallTask`, `AiCallTextInfo`. The limits are `AI_CALL_LIMITS` (system and user 1 MiB each, response 2 MiB keeping its head and its last 256 KiB, 4 MiB per call, 64 calls per task), the budgets are `AI_CALL_BUDGETS` (256 MiB per book in a browser, 1 GiB per device, 2 GiB per book on a server, 1 GiB of free disk), the checkpoints `AI_CALL_CHECKPOINT` (2 s or 16 KiB). `aiCallIdOf(activityId, seq)` makes a call's id, `activity_<uuid>-0003`, which is safe in a file name.
- **Port** (`port.ts`): `AiCallStore`, implemented by each host. `begin({ record, system, user })`, `append(callId, attempt, offset, text)`, `end(callId, final)`, `saveTask(draft)`, `listTasks(bookId, { before, limit })`, `readTask(bookId, activityId)`, `readText(bookId, callId, field, from, attempt?)`, `keep(bookId, activityId, pinned)`, `deleteBook(bookId)`, `prune(bookId, budget)`, `totals(bookId)`. Every write may come twice and out of order; the store keeps the same state. `AiCallDiskFullError` is what a host throws when it is short of disk.
- **Offsets** are bytes of UTF-8 in the kept text of one field. `append` sets the bytes at `offset` (a repeat leaves the text as it was). Each provider attempt has its own response, numbered from 1; `attempt` is the number the recorder gave the text, not the index of the attempt. `readText` answers from a character boundary (rounded down) and returns `size`, the byte length kept, and `complete`.
- **`end` carries** the status, the response's size and partiality, the attempts (with their text sizes), the times and `dropped` (`limit`). The text itself came with the appends.
- **Recorder** (`CallRecorder`): created with the call's identity, its request and the known secrets; `onText` takes the cumulative text the client reports (a shorter text, or `""`, starts a new attempt) and `finish(status, attempts)` ends it. It writes every 2 seconds or 16 KiB, never waits for the store, reports the first store failure once through `onError`, and redacts every string and cuts URLs to their origins. A response longer than its limit keeps its head and its last eighth (at most 256 KiB); the record says `dropped: "limit"`.
- **Retention** (`planRetention(tasks, budget)`): a pure function of task headers. Oldest unpinned tasks that are not running go first, whole; pinned and running tasks are never dropped and count against the budget.
- **Memory store** (`MemoryAiCallStore`): the reference implementation of the port, in memory, for tests and for the recorder in a run.

### Configuration

`AutopilotSessionConfig` (and the run) take:

- `calls?: AiCallStore`: where the records are kept. Without it nothing is recorded: no cost, and no `call-started`, `call-ended` or `callId`.
- `callsSecrets?: () => string[]`: the known secret values of the host (its keys and tokens), redacted from every record. Read when each call starts.
- `callsBudgetBytes?: number`: the budget of the book's records; after each task the oldest finished unpinned tasks are dropped to keep it (default `AI_CALL_BUDGETS.browserPerBookBytes`).
- `callsAccountScope?: string | null`: the account the book belongs to, when the store is fenced by it (a browser). Null by default.

The runner writes one call per `ai()` call of a task: `begin` before the request, the text as the client streams it (`onText` for prose, `onStructuredText` for the JSON of a structured reply), the provider attempts (the client's per-request `onAttempt` and `onAttemptEnd`, which the request carries and which are never sent), and `end` when the call settles. The header of each task is saved when it starts (`running`) and when it ends (`done`, `failed` or `stopped`), and the budget is applied after each task.

### Events

- `call-started`: `activityId`, `callId`, `seq` (the call's number in its task, from 1), `label`, `capability`, `structured`, `systemBytes`, `userBytes`.
- `call-ended`: `activityId`, `callId`, `status` (`ok`, `failed`, `interrupted` or `aborted`), `attempts`, `characters`, `storedBytes`, `partial`, `durationMs`, `dropped` (`limit` or `null`). Neither event carries text.
- `task-progress` gains `callId` (when the book keeps records) and `callSeq` (always: the call's number in its step, from 1). A structured step that streams its JSON says it with `kind: "json"`, `preview` (the last 700 characters of the JSON so far) and `characters`, and without `bytes`; a shorter JSON (`""` too) is a new attempt, said at once. The numbers event of a structured step keeps its shape (`bytes`, `characters`), with the same `preview` and, once the JSON streams, the JSON's `characters`: the tail, the pace and the count are the call's own, never the ones of the call before. See *The step that is answering* for how a client follows them (`applyLiveProgress`).
- `insight` with the code `callsStoreFailed`: the store failed or is full (`AiCallDiskFullError`). The run goes on without records until the next run. It is said once per run.

The status `aborted` is what a call that the run stopped in the middle of its reply ends as (a «Pause now», or a server stopping), with the text that arrived, `partial` set.

### Structured replies stream

`AiRequest.onStructuredText` receives the cumulative value of a structured reply while it streams: the arguments of the function the model calls, or the text when it answers in text. It follows the rule of `onText`: a shorter value, or `""`, starts a new attempt (after a failed candidate, the client sends `""`). It is never part of what is sent, so the requests do not change. The client sends it for the OpenAI-compatible providers it reads as a stream; a whole JSON body is reported once, when it has arrived.

### Which attempt is which text

The recorder numbers the texts it receives: a text starts at the first text of a call, and again at each text that is shorter than the one before (a fallback, a retry), or at `""`. An attempt of the client has `textAttempt` set to the number of the text it started, when it produced one, and `null` otherwise. So an attempt that failed after some text keeps its text as `textAttempt` n, and the next attempt that answers has n+1. The provider attempts are numbered in the order they ran (`index`, from 1). A host that does not forward the attempt hooks gets one attempt, taken from the response or the error.

### What the recorder adds to the port

`CallRecorder` also reports `textAttempts` (the text attempts so far), `storedBytes`, `responseCharacters` and `dropped`, after `finish` for the last three. `RunCalls` is the run's side of it: it starts a recorder per call, saves the task headers, applies the budget, and stops the records for the run at the first store failure.

## Sync

`syncBookStores({ local, remote, base })` is a three-way sync of two `BookStore`s (the browser's working copy and the personal server's): it copies what changed on one side, reports what changed on both (`conflicts`, settled by `resolveConflict`) and returns the `base` to remember for the next one. It reads from a store that has `readMany` a batch of paths at a time, and commits in chunks of at most 400 changes and 24 MiB, so a book of any size passes the limits of one request.

What it does not move is reported, never silently ignored and never a reason for the sync to fail. `result.skipped` lists, in path order, each file with its `reason`:

| Reason | Meaning |
|---|---|
| `too-large` | The file is over `maxFileBytes` (`SYNC_MAX_FILE_BYTES`, 8 MiB, what the personal server accepts), with its `size` in bytes; or a store refused to send it because it is too much (HTTP 413), without a `size`. The size is checked before the file goes into a commit: a store may list `size` in its `BookFileEntry`, and then the file is not even read. |
| `unsafe-path` | A path that is not a safe repository path (`../x.md`, `.git/…`, absolute): the same paths as `rejected`. |
| `not-text` | A file that is not text (binary assets are left to the hosts) and is not the same on both sides. |

A skipped file is not recorded as synced (a file that was never synced stays out of `base`, one that was keeps the version the other side has), so the next sync says it again until it can be moved; the deletion of a file is never skipped.

## The personal server client

`NarrariumServerClient` is the typed client of the personal server API, shared by the web app and the CLI (see the [server README](../server/README.md)).

- **Version compatibility.** `serverCompatibility(info)` tells whether the server speaks an API this engine supports (`MIN_SUPPORTED_SERVER_API` to `MAX_SUPPORTED_SERVER_API`, both 1 today): `{ status: "ok" | "server-older" | "server-newer", message }`. A server that does not say which API it speaks is an older one. It never throws; `verifyServerIdentity` returns it as `compatibility`, and so does `client.verifiedInfo()` in `identity`, so the host decides how to show it (update the server, or update the app).
- **Pairing.** `pairWithServer(options)` still answers the token. `pairWithServerDetailed(options)` answers `{ token, verification?, requestVerification?, compatibility? }`, and `onWaitingApproval({ verification?, compatibility? })` is called while the owner approves. The verification is four digits the server derives (see the server README): while the request waits, the admin panel shows the same four digits next to it (`requestVerification`, which `onWaitingApproval` receives as `verification`), so the owner can tell this device's request from another one; once approved, the panel shows the digits of the token next to the client (`verification` of the result). `onPaired(pairing)` hands over the same details to a host that keeps calling `pairWithServer`. An older server that sends none is fine; a value that is not four digits is ignored.
- **Signing out.** `client.signOut()` revokes the token the client holds (`DELETE /api/v1/session`) and no other: `{ revoked: true }`, or `{ revoked: false }` when the token was already revoked. A server that cannot be reached is an error, because the token may still be valid there (`forgetSession()` is the older call and reports a revoked token as an error).
- **The AI status.** `client.aiStatus()` (`GET /api/v1/ai`) answers `ServerAiStatus`: `configured`, the `integrations` without their keys (an integration that sets a thinking level says it), `routedTasks`, `updatedAt` and, while the owner has to approve an endpoint, `pendingApproval`. A server that passes `redactAiRuntimeConfig` on may also say `toolsOnly` (whether Tools only is in force) and `taskRouting` (the route of every routed task, with the thinking level of each target): both are optional, and a client of an older server gets neither (a missing `toolsOnly` is *unknown*, not *on*). `putAiConfig(config)` (`PUT /api/v1/ai`) sends what `pickAiRuntimeConfig` reads, so `toolsOnly` and the `thinking` of the integrations and of the route targets travel with the rest, and a server that runs the same engine keeps them (it picks the configuration when it saves it and when it reads it back).
- **Quick controls.** Pause at the end of the chapter, the limits of one run and the settings that can change during a run (see *Quick controls* above) go through three calls. A server that implements them announces `SERVER_FEATURE_AUTOPILOT_CONTROLS` (`"autopilot-controls"`) in the `features` of `GET /api/v1/info`, and `serverSupportsAutopilotControls(info)` reads it (never throws; an older server, or an odd answer, says no). Ask before sending what an older server would read as something else: it ignores `limits` (the run would not stop after the step or the chapter that was asked for, and goes on spending) and takes every pause mode but `now` for `after-step` (a `cancel` would pause). The calls need the `run` permission, like the other commands that steer a run, answer the snapshot (`AutopilotSnapshot`, with the server session's `summary`: `pausePending`, `limits`, `publish`), and fail as `{ "code", "message" }` with the status below, which `ServerRequestError` carries as `status` and `code`. Every one also answers 401 `unauthorized`, 403 `scope` (no `run` permission) and 404 `book_not_found`.

  | Client method | Request | Answer |
  |---|---|---|
  | `pauseAutopilot(bookId, mode)` | `POST /api/v1/books/:id/autopilot/pause` with `{ "mode": "now" \| "after-step" \| "after-chapter" \| "cancel" }`. A body without `mode` is `after-step`, as it always was. | `200` the snapshot. `cancel` with nothing waiting, and any mode with nothing running, are `200` too: the summary's `pausePending` says what is waiting now. `400 invalid_request` for a `mode` that is none of the four, or a body that is not a JSON object. |
  | `startAutopilot(bookId, input)` | `POST /api/v1/books/:id/autopilot/start` with the body it always had (`brief`, `options`, `force`) and `limits?: { "steps"?: number, "chapters"?: number }`. | `200` the snapshot. `400 invalid_request` when `limits` is present and is not a JSON object. The server hands the numbers to the engine as they are (a value that is not a whole number above zero is no limit) and does not save them. The other answers are as before: `409 busy`, `412 ai_not_configured`, `429 too_many_runs`, `503 maintenance`. |
  | `updateAutopilotOptions(bookId, input)`, also `updateOptions` | `PUT /api/v1/books/:id/autopilot/options` with `{ "publishEvery"?: "off" \| "chapter" \| "step" \| null, "pauseAfterEachChapter"?: boolean, "frozenEdits"?: "ask" \| "auto" \| "notify", "longRetry"?: { "everyMinutes", "cycles" } \| null, "resumeAfterRestart"?: boolean }`: at least one, and nothing else (`frozenEdits` from a server that announces `autopilot-frozen`, `longRetry` from one that announces `autopilot-retry`: see *Retry later and Retry now* below, `resumeAfterRestart` from one that announces `autopilot-auto-resume`: see *Resume after a restart* below). `null` takes the choice back, so that the server's default decides again (for `longRetry`, it turns it off). | `200` the snapshot, of the state that was saved (as `configure` answers), also while the autopilot runs: the step in flight is not repeated, and the run reads the new value at the end of the step, or of the chapter. `400 invalid_request` for a body that is not a JSON object, has none of the keys or has another key, or a value of the wrong type (`publishEvery` that is not one of the four, `pauseAfterEachChapter` or `resumeAfterRestart` that is not a boolean, a `longRetry` that is not a policy: the message says why). `409 conflict` when the state file kept changing under the write (try again) and `409 state_corrupt` when it cannot be read; `503 maintenance` while the server is about to restart. |

For a GitHub book its `afterCommit` hook pushes (what the engine calls after every step in `step` mode) and its `afterChapter` hook pushes too (what it calls when a chapter is closed in `chapter` and `step` mode): without that one, `chapter` would publish nothing.

- **Permanent rules.** The rules the author gave with `from_now` (`state.constraints`, in the order the author sees them) are edited and removed with two calls, which the engine's session already has (`session.updateRule`, `session.removeRule`). A server that implements the routes below announces `SERVER_FEATURE_AUTOPILOT_RULES` (`"autopilot-rules"`) in the `features` of `GET /api/v1/info`, and `serverSupportsAutopilotRules(info)` reads it (never throws; an older server, or an odd answer, says no): a client asks before it offers to edit or remove a rule, because an older server answers `404 not_found` to the routes. The client sends the text as it is given and an index as it is given (a number that names no rule is `404 rule_not_found`), and what it gets back is the error it always gives, with the status and the code of the server. The answer to a question of the director that is kept as a rule needs nothing new: `answer(bookId, { questionId, answer, asRule: true })` has always carried `asRule` (`QuestionAnswer`), and a note used once is still the default.

- **Retry later and Retry now.** A server that takes `options.longRetry` («Retry later», see *Retries*) and has `POST …/autopilot/retry-now` («Retry now») announces `SERVER_FEATURE_AUTOPILOT_RETRY` (`"autopilot-retry"`) in the `features` of `GET /api/v1/info`, and `serverSupportsAutopilotRetry(infoOrFeatures)` reads it (it takes the info or the list of its features; never throws; an older server, or an odd answer, says no). An older server plans the default number of chapters and ignores the Scaletta, so `startAutopilot` and `configureAutopilot` refuse it before sending anything: a `ServerRequestError` with status 501 and code `feature_unavailable`, which says to update the server. The client asks the server's `info` once for both checks.
- **Resume after a restart.** A server that resumes a run by itself when it starts again announces `SERVER_FEATURE_AUTOPILOT_AUTO_RESUME` (`"autopilot-auto-resume"`), and `serverSupportsAutopilotAutoResume(infoOrFeatures)` reads it (it takes the info or the list of its features; never throws). Such a server takes `options.resumeAfterRestart` (`true` or `false`) in the options route, `configure` and `start`; it pauses every run with `session.stopForShutdown()` when it stops, and when it starts again it resumes, one book at a time, the runs that `session.restartResumeCause()` names (with `session.start({ afterRestart: true })`, through every check a start of the author has: the AI configuration, the number of runs, the owner's switch and caps), at most three times a day per book (see the server's README). **The client never sends `resumeAfterRestart` to a server that does not announce the feature** (`false` included), for the same reason as `longRetry`: `updateAutopilotOptions`, `configureAutopilot` and `startAutopilot` ask the server's `info()` first and refuse with `501 feature_unavailable` before anything is sent. A request without the setting asks nothing more.

- **Conflicts with GitHub.** When the server's commits and GitHub's changed the same files, the server's run stops with a `conflict` (`errorDetail.githubConflicts`: how many files), its sync answers `409 github_conflict` (with `conflicts` in the `details` of the `ServerRequestError`), and `lastSync.conflicts` says it in the summary of the book. The author chooses which version of each file to keep, the server's or GitHub's, through two calls of a server that announces `SERVER_FEATURE_GITHUB_CONFLICTS` (`"github-conflicts"`), which `serverSupportsGithubConflicts(infoOrFeatures)` reads (never throws). **The client refuses a server without the feature before sending anything**: it asks `info()` once (and again until the server says yes, so that an update is noticed) and throws a `ServerRequestError` with status `501` and code `feature_unavailable`, whose message says to update the server. A refusal of the server keeps what it said with it in `ServerRequestError.details` (the fields of the answer other than `code` and `message`). Every call also answers `401 unauthorized`, `403 scope`, `404 book_not_found` and `409 no_remote` (a book that is not on GitHub). The rules (which version a deleted file follows, the autopilot's own files that are never asked about, the names the server does not write, the push that GitHub refuses) are in the server's README, *Conflicts with GitHub*.

  | Client method | Request | Answer |
  |---|---|---|
  | `listGithubConflicts(bookId, { offset?, limit? })` | `GET /api/v1/books/:id/github-conflicts?offset=&limit=` (`read`): the server fetches GitHub and compares by a merge that writes nothing. Only the parameters given are sent. | `200` `GithubConflictsResponse`: `{ conflicts, total, offset, limit, ahead, behind, branch, head?, githubHead?, fingerprint, autopilotFiles? }`, the conflicts of the page in the order of their paths (`GITHUB_CONFLICTS_PAGE_LIMIT`, 100, by default; at most `GITHUB_CONFLICTS_MAX_PAGE_LIMIT`, 500). Each `GithubConflict` is `{ path, server, github, serverBytes?, githubBytes?, resolvable, reason? }`: `server` and `github` are `"modified"`, `"added"` or `"deleted"`; `resolvable: false` (with `reason` `"unsafe-path"`, `"file-directory"` or `"not-a-file"`) is a file the server cannot choose for, kept as the server has it. `autopilotFiles` (`"server"` or `"github"`) says which side's state, log and plan a resolution keeps when both changed them. `400 invalid_request` for a page that is not whole numbers (the limit from 1 to 500); `502 git_failed` when git fails (GitHub cannot be reached). |
  | `resolveGithubConflicts(bookId, { choices?, default?, message?, fingerprint? })` | `POST /api/v1/books/:id/github-conflicts/resolve` (`write`): `choices` maps a `path` of the list to `"server"` or `"github"` (`GITHUB_CONFLICT_CHOICES`), `default` is the version of every other file, `fingerprint` the one of the list the author chose from (send it: without it the server compares with the last list it gave), `message` the subject of the merge commit (at most 300 characters). | `200` `ResolveGithubConflictsResponse`: `{ head, pushed, pushError?, resolved, ignored, unresolvable, counts, autopilotFiles? }`, after one merge commit with both histories, pushed when the book is published (`publishEvery` other than `off`); the run is not started again (the author resumes it). `400 choice_missing` (`details.paths`, `details.missing`), `409 conflicts_changed` (`details` is the first page of the list as it is now, with its `fingerprint`), `409 not_conflicted`, `409 busy` (a run is active), `409 unrelated_histories`, `422 invalid_github_path`, `400 invalid_request`, `503 maintenance`: nothing is written. |

- **The AI call records of a server.** A server that keeps what each AI call of its autopilot runs sent and what came back (the system and the user message, the answer while it streams and after, what each attempt did) and serves it announces `SERVER_FEATURE_AUTOPILOT_CALLS` (`"autopilot-calls"`), and `serverHasCalls(infoOrFeatures)` reads it (it takes the info or the list of its features; never throws). The methods below check it once (the answer is remembered when it is yes) and refuse a server without it with a `ServerRequestError` `501` `feature_unavailable`, before sending anything but `GET /api/v1/info`. The records are the book's text, so a client that may read the book reads them and one that may run its autopilot keeps and deletes; an app connected through MCP reaches none of them. The shapes are the engine's (`AiCallTaskPage`, `AiCallTask`, `AiCallTaskHeader`, `AiCallField` of `src/autopilot/calls/`); the personal server's own are `ServerCallText`, `KeepCallTaskRequest` and `ServerDeleteCallsResponse`, with the limits `SERVER_CALLS_PAGE_LIMIT` (20), `SERVER_CALLS_MAX_PAGE_LIMIT` (100), `SERVER_CALL_TEXT_MAX_BYTES` (256 KiB) and `SERVER_CALL_FIELDS`.

  | Client method | Request | Answer |
  |---|---|---|
  | `listCalls(bookId, { before?, limit? })` | `GET /api/v1/books/:id/autopilot/calls?before=&limit=` (`read`). Only the parameters given are sent. `limit` is 1 to 100 (20 when left out); `before` is the `next` of the previous page. | `200` `AiCallTaskPage`: `{ tasks, next }`, the tasks' headers newest first, `next` null on the last page. `400 invalid_request`, `404 book_not_found`. |
  | `readCallTask(bookId, activityId)` | `GET /api/v1/books/:id/autopilot/calls/tasks/:activityId` (`read`). | `200` `AiCallTask`: `{ header, calls }`, the calls in the order they were made, with no text. `404 call_task_not_found`. |
  | `readCallText(bookId, callId, { field, attempt?, from?, limit? })` | `GET /api/v1/books/:id/autopilot/calls/:callId/text?field=&attempt=&from=&limit=` (`read`). `field` is `system`, `user` or `response`; `attempt` names a response (from 1; the last one that has text when left out); `from` is a byte offset; `limit` is at most `SERVER_CALL_TEXT_MAX_BYTES`. | `200` `ServerCallText`: `{ text, from, next, size, attempt, done }`. A piece starts at the character that holds `from` and ends at the end of a character; `done` is true once the call has ended and `next` reached `size`. A reader that follows a running call asks again from `next` (if `size` is lower than the `next` it holds, or `attempt` changed, the call began another answer: start over). `404 call_not_found`. |
  | `keepCallTask(bookId, activityId, pinned)` | `PUT /api/v1/books/:id/autopilot/calls/tasks/:activityId/keep` (`run`) with `{ "pinned": boolean }`. | `200` the task's `AiCallTaskHeader`. A pinned task is never dropped to make room, but counts against the budget. `404 call_task_not_found`. |
  | `deleteCalls(bookId)` | `DELETE /api/v1/books/:id/autopilot/calls` (`run`), no body. | `200` `ServerDeleteCallsResponse`: `{ deleted: true, tasks, calls, bytes }`. Every record of the book on the server goes, the pinned ones too; what a browser or an account copied stays where it was copied. The book is never touched. |

- **The MCP endpoint of a book.** A server that gives each book its own MCP endpoint (`/mcp/<slug>`, which an assistant such as Claude Code, ChatGPT or Claude.ai connects to) announces `SERVER_FEATURE_MCP` (`"mcp"`) in the `features` of `GET /api/v1/info`; one on which apps such as ChatGPT and Claude.ai connect by themselves, through OAuth, also announces `SERVER_FEATURE_MCP_OAUTH` (`"mcp-oauth"`). `serverSupportsMcp(info)` and `serverSupportsMcpOAuth(info)` read them (never throw; an older server, or an odd answer, says no; each entry is read by itself, so one is never taken for the other). A client asks before it offers the setting: a server without `mcp` answers `404 not_found` to the routes below, and a server with `mcp` but without `mcp-oauth` answers `404 not_found` to the two that list and revoke apps, and its status carries neither `connections` nor `oauth` (a missing `connections` is *unknown*, not *none*). The calls fail as `{ "code", "message" }` with the status below, which `ServerRequestError` carries as `status` and `code`; every one also answers `401 unauthorized`, `403 scope` (a token without the permission in the table), `400 invalid_book` for a book id the server cannot keep and `404 book_not_found` for a book that is not there. The types are `ServerMcpStatus` (with `ServerMcpOAuth`), `UpdateMcpRequest`, `ServerMcpClient` and `ServerMcpClientScope`; the answers are passed on as the server gave them (what a newer server adds is not dropped), except that `listMcpClients` answers the list itself, an empty one when nothing is connected and also for an answer that has no list.

  | Client method | Request | Answer |
  |---|---|---|
  | `mcpStatus(bookId)` | `GET /api/v1/books/:id/mcp` (`read`). | `200` the status: `{ bookId, enabled, slug, path, url, public, message?, protocolVersions, updatedAt, connections?, oauth? }`. `enabled` is false until the owner switches the book on. `url` is the address to paste into the assistant (`<public address>/mcp/<slug>`, or the local one while the server has no public address); `public` says whether it can be reached from outside, and `message` says why not when it cannot. `connections` is how many apps are connected through OAuth, and `oauth` is `{ issuer, metadataUrl, resourceMetadataUrl, scopes }`, where the OAuth server is (both only from a server that announces `mcp-oauth`). Asking for the status of a book that has no slug yet gives it one, and the slug is kept. |
  | `updateMcp(bookId, { enabled?, slug? })` | `PUT /api/v1/books/:id/mcp` (`write`) with `{ "enabled"?: boolean, "slug"?: string }`. Only what is given is sent, and only those two (a `false` is a value). | `200` the status after the change. `400 invalid_slug` (a slug is 1 to 80 characters: lowercase letters and digits, joined by single hyphens), `409 slug_taken` (another book has it), `400 invalid_request` (a body that has neither key, or an `enabled` that is not a boolean), `503 maintenance` while the server is about to restart. **Switching a book off, or giving it another slug, disconnects every app that was connected to it** (`connections` is 0 in the answer): they do not come back when it is switched on again, the owner allows them again. |
  | `listMcpClients(bookId)` | `GET /api/v1/books/:id/mcp/clients` (`write`: it says who may change the book). | `200` `{ "clients": [...] }`, and the method answers the array of `ServerMcpClient`: `{ id, clientId, name, redirectHost, scopes, createdAt, lastUsedAt }`. `id` is the connection's (what `revokeMcpClient` takes; the same app connected twice has two), `clientId` the id the app registered under, `name` what the app calls itself (cleaned, one line: show it as text), `redirectHost` the host the app sends the owner back to, `scopes` what the owner allowed (`read`, `write`, `run`; show the ones you know and leave out the rest), and the two dates are ISO times. Never a token. |
  | `revokeMcpClient(bookId, id)` | `DELETE /api/v1/books/:id/mcp/clients/:id` (`write`), no body. | `200` `{ "revoked": true }`: the app's next call is refused and its tokens are useless, so it has to ask the owner again. `404 client_missing` when the book has no such connection (it was revoked already, it ended with the book's switch or slug, or it belongs to another book), told apart from `404 book_not_found` by the code. |

  The apps are allowed by the owner on a page of his own server, with a passkey or the admin code: this client never does it, it only lists and revokes. The passkeys, the apps of every book at once and the audit of what was called are the server's admin panel's, and are not part of this API. A host that offers the setting shows `url` to copy and says what it needs: it can be pasted into ChatGPT or Claude.ai only when `public` is true.
