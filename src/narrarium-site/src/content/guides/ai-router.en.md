# AI integrations and Router

Narrarium uses your AI integrations. Add Azure OpenAI, OpenAI-compatible endpoints or GitHub Models in **Settings → AI Integrations**, which also holds keys, models, prices and default models. For Azure OpenAI the **API version** of the integration is the default of its models, and the card of each model has its own **API version** field for a deployment that needs another one (empty: it inherits the integration's, and the field says which). Then choose in **Settings → AI Router** which model handles each task.

## GitHub Models quick start

Create a GitHub PAT authorized for GitHub Models, add a **GitHub Models** integration in **AI Integrations**, load the model catalog and assign capabilities to the models you want to use.

## Reading the models of an endpoint

In the card of an **OpenAI / compatible** integration, two buttons next to the key work with the address and the key as they are written. They are not there for Azure OpenAI, GitHub Models or Microsoft 365 Copilot, which have no such list.

**Check the connection** asks the endpoint one short question, its list of models, and says in one line how fast it answered and how many models it lists («Responds in 120 ms · 6 models»), or what to correct: error 401 is the key, 404 an address that does not end with the version path (for example */v1*), 429 and 5xx an endpoint that is limiting requests or busy. When nothing answers, a browser cannot tell a server that is off from a wrong address or from a server that does not allow this site (CORS), and the line says so; the engine's own words are in the technical details. The error panel of the autopilot offers the same check, with the same result and a link to the card, on the integration of the step that failed, for network, authentication, timeout and provider failures; when the run is on your personal server, the check still asks from your browser.

**Read the models from the endpoint** opens a list of what the endpoint says it has, by kind (text, images, text-to-speech, transcription, embedding, other), with the context window, the largest answer and what each model can do (tool calls, streaming, reasoning, vision), and whether the integration already has it. It reads */models* (the list, needed) and, when the gateway has them, */models/details* and */modalities* (LlmProxy's: the limits, the capabilities and the kind of each model). Without them the dialog says «Only /models», lists every model as text and ticks none, because nothing says which of them chat.

Tick what to add or update and press **Add/update N models**. The new text models are ticked at first. A model you already have is updated only where it is empty (its limits and the capabilities the endpoint declares); what you wrote is never overwritten: your numbers, a capability you set (a switch turned off included), its roles, names, prices and Thinking parameter. A capability the endpoint does not declare is not turned into a restriction. A new model gets what the endpoint declares of it, and the first model of an integration that has none takes the default roles. For a name that the engine knows (Muse Glimmer today) the dialog suggests the **Thinking parameter** *chat_template_kwargs.reasoning_strength*, already ticked, and you can untick it before confirming. A model that is not for chat can be set as the image, text-to-speech or transcription model of the integration while that field is empty.

**Load models from API**, in the list of chat models, still works, for endpoints that answer in a simpler way.

## Task routing

**AI Router** has one table for each kind of task: **Text (chat)**, **Text-to-speech (TTS)**, **Speech-to-text (STT)** and **Images**. A table lists the endpoint (the integration) and the model of each task; the text table also has **Thinking**, and its first row, **Default**, is used by every task that has no route of its own. A row without a choice of its own shows, dimmed, what Narrarium would use. **Brainstorming**, the Copilot's mode on the Synopsis page, has its own row in the Copilot's group: without a route of its own it follows the Copilot's route, models and thinking included, and its cells say so (*Copilot: …*); without that either it goes where the Copilot goes. A model allowed the Copilot is allowed Brainstorming too, and one tagged **Brainstorming** in **AI Integrations** comes first for it. **Wildcards**, the room of provocateurs and sentinels who give ideas and findings, has its own row in the review's group and follows the review in the same way (*Review: …*), the review's models allowed; a model tagged **Wildcards** comes first for it. The privacy of fallbacks and the execution limits are in the box **Routing options**.

The tabs above a table are the **Primary** and the **fallbacks**, tried in order when the primary fails (rate limit, network). **Where a change applies.** A change applies to the next call of an autopilot that runs in the same tab, even before you save it (a note on the page says so while one runs); **Save** keeps it after a reload and applies it to a run in another tab of the same browser. A book whose autopilot runs on your personal server is asked with the AI configuration that was sent to the server, not with this one: the page says what the server holds and has a button to send the current configuration. A model that the autopilot leaves out (its context window cannot hold the prompt, **Tools only**, the privacy setting, the routing limits, a model that is no longer there) is never left out in silence: the records of the step and the error panel say which one and why. Every tab works the same way, with the same filters and the same group editing. **New tab** adds a fallback level, up to the maximum number of candidates in *Routing options*. **Swap with…** exchanges the targets of two tabs, thinking included, for the selected rows or, with nothing selected, for all of them; it tells what it did and offers **Undo**. The **…** menu moves a tab left or right (a swap with its neighbour) and deletes it, after asking how many rows lose it.

**Tools only** is the switch at the top of the page. With it on (the default) every agent of the autopilot (writer, director, readers, specialists, summaries) and every structured answer of the Copilot (an evaluation, a yes/no confirmation) answers by calling its own function, and not with a JSON written in the message: a model marked as without tool calls is skipped, and a reply in text instead of the call is refused. When no model of a task can call a function, the autopilot stops with **The AI configuration needs fixing**, and the page lists the tasks of the autopilot that are in this case under the switch; the Copilot says the same in the chat, with the same two ways out. To use such a model, turn on **Forced tool calls** for it in **AI Integrations**, or turn the switch off. The prose of the Copilot is never affected.

**The limits follow the model.** Whether a request fits is decided by the context window of the model it goes to: its **Context window tokens** in **AI Integrations**, or, when that is empty, 128,000 tokens, the window of most models today (a model that holds less, such as a local one, is the one to set). The autopilot refuses a prompt that does not fit and says the numbers; the Copilot and Brainstorming cut it to fit and say how much. **Routing limits**, in *Routing options*, are a safety for the fallbacks: **Maximum token attempts** and **Maximum estimated route cost** bound what the fallbacks after the first attempt add together, so that a chain of fallbacks cannot multiply a request; the first attempt, the model you chose, is never stopped by them. A fallback is estimated on what it would send and on the output it asks for, never on the whole window of its model. When the first model fails and a limit kept its fallbacks out, the Copilot, Brainstorming and the autopilot's error panel say which limit, what the fallbacks needed and the limit, with **Raise the limit and send again** (in the autopilot, **and resume**): one click sets the limit to a round value that holds them, with room, here in the settings, and the value it replaces is remembered beside the field, with **Put back**. A limit you set by hand is yours again.

**Thinking** is how hard a model is asked to think. *Low*, *Medium*, *High* and *Extra high* are sent to the provider; *Automatic* sends nothing; *Inherit from integration* takes the **Default thinking** set in the card of the integration in **AI Integrations**. The level of a route always wins over the integration's. The **Default** row has no level of its own, because it only chooses the endpoint of the tasks without a route: they use the one of the endpoint. A model that does not reason may refuse a level (error 400): choose *Automatic* for it.

## Editing many tasks at once

In the text table, filter by group (Autopilot, Copilot and actions, Review, Research), by name, or with **Only customized**. Tick the rows, or **Select all visible tasks**, and use the panel that appears: choose the **endpoint**, then the **model** (only models valid for every selected task), then the **thinking**, and press **Apply**. Nothing changes until you do. What you do not choose stays as it was, so you can change endpoint and model and leave the thinking, change only the model, or change everything. When the new endpoint does not have the model of a row, that row takes the first valid one and the message says so. A fallback needs a primary: rows without one are skipped, and the message says so too.

## Thinking

For chat tasks, **Thinking** is how much the model is asked to think before it answers (the provider's *reasoning_effort* setting). **Low** is fast; **High** and **Extra high** are slower and use more tokens. **Automatic** sends nothing, and a blank value takes the level of the integration. Each target has its own: the primary and every fallback. The Copilot sends a level only when it is explicit.

**Thinking parameter** is how the level reaches a model, and it is set per model, in the card of the integration in **AI Integrations**, next to **Forced tool calls**. By default the level goes as *reasoning_effort*, the OpenAI field. Muse Glimmer on llama.cpp takes it as *chat_template_kwargs.reasoning_strength* and ignores *reasoning_effort*: for a model with that name the card suggests it, and **Use it** applies it, never by itself. *none* sends no level to that model, and it does not turn thinking off. It works the same for the autopilot and for the Copilot, and the debug panel says when a level went as the argument of the chat template.

**Do not use thinking when tools are used** is a checkbox in the row of each model (also in a row you have just added). Some models refuse a thinking level only when the request carries tools: the provider answers *Function tools with reasoning_effort are not supported for this model…* and the structured steps of the autopilot would fail. Narrarium recognises that answer by its words and its parameter, never by the name of the model, and finds out how the model takes tools by asking: it asks the same step again without the level and, if that is refused too, with the level *none* (the GPT-6 models of Azure OpenAI take tools only with *none*), and turns the checkbox on for that model by itself. From then on its requests with tools go the way that worked, and its requests without tools keep their thinking. A model that takes none of these ways (the *gpt-6.2-sol* family takes function tools only on the Responses API) fails with the provider's words and what was tried, and nothing is changed in its row. A notice says what was done with the provider's own words and the two ways out: use the Responses API for this model, with a button (**Use the Responses API for this model**: there, a thinking level and function tools go together, so thinking stays on when tools are used), or turn thinking off when tools are used, which is what was done. Narrarium never switches a model to the Responses API by itself: it is your choice, and you can undo it in the model's row. The line of the running step says *Thinking: not sent (tools)* or *Thinking: off (tools)*. You can change the checkbox in the model's row at any time. On a personal server the model is remembered while the server runs; the setting reaches it when you send it the AI configuration, and a server older than this version needs its own update to keep it.

**API protocol** and **Address of this model (optional)** are two more settings of each model, in its row. The protocol says how the model's requests are made: *Chat Completions* (the default, as every model has always been asked) or the *Responses API*, which takes a thinking level and function tools together, so a model that refuses them on Chat Completions (*gpt-6.2-sol* and its family) can be used with thinking on. For an Azure OpenAI integration Narrarium builds the address itself (`/openai/responses?api-version=…`, or `/openai/v1/responses` for the v1 endpoint), and asks the Responses API with *2025-04-01-preview* when the integration keeps an older API version for its Chat Completions models; the line **Requests go to** in the row says where the requests of the model go. GitHub Models has no Responses API. The address of a model is only for a gateway whose address is not the one Narrarium builds from the integration: it is used exactly as you write it, query included, with the key of the integration, and no API version is used for that model; do not put a key in it, since it is saved with the settings and sent to a personal server (the row warns when its query looks like one). When an address ends with */responses* the row offers the Responses API with a button, and never switches the model by itself. A model asked through the Responses API says so in the debug panel, in the trail of the router and in the diagnostics, with the host and the path of its own address (never the query). On a personal server, the server owner approves the address of a model like the endpoint of its integration, and a server older than this version needs its own update to carry both settings.

**What the provider said.** When a provider refuses a request, the error panel of the autopilot, the trail of the AI Router, the records of the calls, the Copilot and the diagnostics you copy say its answer in its own words, as labelled fields: the HTTP status, the message, the type, the param and the code. An answer that has no such fields (a text, the page of a gateway, nothing at all) is shown as it is, and no key is ever in it. The debug panel keeps only the status, the type, the param and the code, never the message.

A model that cannot call tools is marked **no tool calls**: the structured steps of the autopilot and of the Copilot cannot use it while *Tools only* is on.

Browser TTS and STT are virtual Router integrations and do not consume AI tokens.

## Timeouts and streaming

Every integration in **AI Integrations** has three settings that decide how long a slow model is given. The autopilot and the Copilot use them in the browser, and the autopilot on your personal server too (they go with your AI configuration, so send it again after a change).

- **Provider timeout (ms)**: how long the provider may take to start answering. The minimum is 30,000 ms (a lower value is raised to it, and the setting keeps what you wrote) and empty means 600,000 ms (10 minutes). Voice and images count it as the time of the whole request instead, 60,000 ms when it is empty.
- **Idle timeout (ms)**: the longest silence between two pieces of a streamed reply, from 30,000 to 3,600,000 ms; empty means 600,000 ms. Every piece that arrives starts the count again, so a model that keeps writing is never cut off, however long it takes (one call lasts four hours at most). It is not used while Streaming is Off. A gateway between the app and the model may have a shorter limit of its own (LlmProxy resets a silent connection after 5 minutes unless its owner changed it, Cloudflare after 100 seconds): the shortest limit decides, so raise the gateway's together with this one.
- **Streaming**: with **Automatic (recommended)** every reply of the autopilot and of the Copilot arrives in pieces, the structured ones too, so a slow model is not cut off by a proxy or a tunnel that closes a connection that stays silent. Choose **Off** only if the provider refuses streamed replies together with function calls: its error is a 400 that mentions stream, and the message tells you to set **Streaming** of the integration to off. With Off the whole reply has to arrive within the provider timeout.

When a step fails because the response was too slow, the technical details of the error say which wait ran out and which of these settings to change (the Copilot writes the same sentence in the chat). A personal server older than 0.1.7 does not know **Idle timeout (ms)** and **Streaming**: it waits as it always did until you update it (**Version and updates** in **Settings → Personal server**).

**Passing errors.** When the provider answers the Copilot with a passing error (a 429, a 500, 502, 503 or 504, or a connection that drops, as a flaky node or a tunnel does now and then) the Copilot does not give up at the first one: it asks the same model again, at most two more times, after about 1 s and then about 3 s, never sooner than the provider asks and not at all if the provider asks for more than 10 s, and only while the **Total routing time (ms)** leaves room for it. The chat says it quietly, once for each retry («The provider answered with a passing error: trying again in 3 s (2 of 3)…»), and a reply that had begun to arrive starts over from the beginning. **Stop** ends the wait at once and is never shown as an error. Each attempt is a line of its own in the panel of AI requests and in the costs. A reply that stops halfway (the connection is lost, the provider closes the stream early or reports an error in the middle of it) is a passing error too, and the part that had arrived is never used. A request that ran out of time (**Provider timeout (ms)**, **Idle timeout (ms)**), a request the provider refused (400, 401, 403, 404…), a reply that was refused and a prompt that does not fit are never repeated. After the third attempt the Copilot goes on as it always did: to the next model of the route, or to the error, in the words of the provider.

## Costs

Every call that may cost something is recorded once, in the costs of your account, by day, book, use (Autopilot, Copilot, actions of the editor, audit, simulated readers, research, images and voice, other), capability, integration, model and currency: the calls, the tasks, the tokens the provider reported (input, cached input and output), what they cost at the price of the model in AI Integrations and, apart from them, the calls with no price and the calls with no token count, with what those are estimated to have cost. The price of chat tokens is the engine's rule, the same in every host: cached tokens are priced at the input price when the model has no cached price. A task is one step of the autopilot, one turn of the Copilot (every call it makes, its tools included) or one request of another feature; a research counts only the calls it made itself. Each device keeps its own part of the costs, which travels with your account data, so two devices never count a call twice; what was recorded before this version is kept as **Earlier**. A book whose autopilot runs on your personal server has the server's summary instead. Reader evaluations save their own provider/model/token/cost metadata while using the same cost engine. The currency, the exchange rates and the relabelled amounts are in **Settings › Costs** (see *Budgets and costs* in the autopilot guide).

**The Costs page** (the coin in the top bar, or **Costs** in the account menu) is one dense table of everything the ledger holds. Its rows are the **Books**, the **Months** or the **Uses**; its columns are the spend, the tasks, the calls, the tokens, a small chart of the last six months (said in words to a screen reader, month by month) and, for the books, their budget. The **totals** (spend, tasks, calls, tokens and the calls whose cost is not known) stay in sight at the top of the table and follow the filters. The filters are the **Period** (this month, the last 30 days, all time, or from a day to a day), the **Book**, the **Use** (Autopilot, Copilot, actions of the editor, audit, simulated readers, the wildcards' ideas, research, images and voice, other: the wildcards you consult yourself are their own use, those the autopilot consults are the autopilot's), the **Task** (the capability of the router, Brainstorming included), the **Model**, the **Integration** and the **Currency**; on a phone only the period is in sight and **More filters** opens the rest, and the rows are cards. The headers of the table sort it (and say how, with *ascending* or *descending*), and what the filters keep is announced once they settle. Money is never added across currencies: a row that spent in two shows both («€1.84 + $0.46»), or one amount, marked «≈», when you gave an exchange rate in Settings › Costs. The months older than three months are kept by month, so a period that touches one counts it whole; what was recorded before the ledger is the row **Earlier**. Open a book to see its settings at a glance: whether it is on GitHub, where its autopilot runs, its state and where it publishes, the models it used in the period, **Retry later**, the resume after a restart, whether this device keeps the calls of its autopilot, and its budget, which you can set there (see *Budgets* below). A book without a budget of its own shows the money cap of its autopilot (**Budget** in the **Review** of its configuration), against the autopilot's own count of what it spent: when a limit stopped the autopilot the bar is full and says so with the numbers the autopilot compared when it stopped («$5.02 of $5.00 · stopped»), and the state of the book says which limit it was (the money cap, the token cap). A book that runs on your personal server shows the server's own summary on its row, told apart and never added to the totals: the server counts every step of the book, those that ran in a browser before the book moved included, so adding it to what your browsers recorded would count some of them twice. **Export CSV** downloads the rows the filters keep, one line for each day (or month), book, use, task, integration, model and currency, every amount in the currency it was priced in and the estimates apart.

**Budgets.** On the **Costs** page, **Set a budget** (and **Edit budgets**) opens the budget of all your books: a limit **per month** and/or **in total**, in each currency you spend in (a field left blank is no limit), the percentage it **warns at** (80% unless you choose another) and **what counts** (every use that was recorded, the Copilot included, or the autopilot only). Open a book in the table and **Set a budget for this book** gives it a budget of its own, which applies together with the one of all the books. A budget counts what the ledger recorded in its currency, plus what has an exchange rate to it (Settings › Costs, marked «≈»); an amount in a currency with no rate is not counted, and the page says which. At the percentage a budget warns at, in words and with a sign and not only in colour: the **Budgets** section of the page says «Budget warning» with the figures, the book's row and the Autopilot page say the same, and the coin of the top bar shows a triangle with the percentage («85%»); at 100% they say «Over budget» and **Raise it to** … raises that budget with one click. The autopilot is paused by its own money cap, never by a second mechanism: when it starts or resumes, this browser gives it the cap that is left of your budgets, added to what it counted for the book, so it stops before the first step that would pass them, with the panel of the money cap (**The budget stopped the autopilot**) and two ways on: **Raise the budget to** … **and continue**, and **Continue anyway**, which goes on once whatever the budgets say (the next start counts them again). A call in flight is never cut. The cap of your own that you may have set in the configuration is kept: the run stops at the smaller. Money spent by other uses while a run goes on is counted at its next start, and the warnings follow it at once. For a book that runs on your personal server the cap is sent with the start; the server's own count of the book is in the total budgets, and a monthly budget counts only what this browser recorded.

**The spend in the top bar** is the small pill with a coin: what was spent **today** and **this month**, by every use of every book, as one link to the Costs page. It is loaded after the page is drawn, appears only when something was spent this month, and on a narrow bar shows the month only.
