# Autopilot and Director Spec

Narrarium can write a book on autopilot while the author keeps the final word. The same engine ([`narrarium-engine`](../packages/engine/README.md)) runs in the web app and in the personal server ([`narrarium-server`](../packages/server/README.md)), so the book files, the decisions and the live events are identical wherever it runs.

## Roles

- **Architect and ghostwriter** — design the concept and the plan, then write scene by scene following the selected ghostwriter profile.
- **Simulated readers** — read each finished chapter *blind*: no canon, no secrets, no plan. They write the same reader evaluations as the Reader evaluations page, then a panel summary.
- **Specialists** — check continuity, canon, secrets and reveal timing, timeline, character voice, style and pacing. Every finding must quote the text.
- **Director** — the author's stand-in. It approves or corrects the plan, decides on every finding (accept with a precise fix, or reject with a reason), scores the chapter and carries standing guidance forward. The software, not the model, turns accepted findings into repairs. When its autonomy allows it, the director asks the author instead of deciding a critical matter.

## Pipeline

1. Concept: story design, world context, characters, locations, factions, secrets with their reveal chapter.
2. Plan: chapters; simulated readers react to the pitch and the plan; the director approves or asks for changes. By default the autopilot pauses here so the author can read the plan.
3. For every chapter: scene plan → prose → readers → specialists → director → repairs → verification round (up to the director's limit) → consolidation (chapter summary, recap, story so far, `plot.md`).
4. Final: the director's judgement on the whole book.

A book that already has chapters is continued after the last one; chapters written by the author are never rewritten unless the author asks.

## Author interventions

| Scope | Effect |
|---|---|
| Next step only | Delivered once to the next writing step, then marked as applied. |
| From now on | A permanent rule for every following step, the director included. |
| Revise what is already written | The director picks the scenes that must change; they are rewritten and reviewed again. |

An intervention can interrupt the running step, which is then repeated with it. The author's instructions always win over the director's taste.

## Asking the director

On any book, chapter or scene page, **Ask the director** returns a structured opinion: verdict, score, strengths, concerns with quoted evidence, decisions, next steps and, when asked, a direct answer. Opinions can be kept in the book.

## Files

| Path | Content |
|---|---|
| `director.md` | Director profile: `type: director`, `name`, `persona`, `autonomy` (`full`, `ask-on-critical`, `ask-always`), `strictness`, `approval_score`, `max_review_rounds`, `priorities`, `taste`, `red_lines`, `reader_weights`, and the vision in the body. |
| `autopilot/state.json` | Brief, options, plan, current review cycle, author rules and interventions, director guidance, statistics. |
| `autopilot/activity.json` | The last 200 steps: what, why, next, result, model, tokens and cost. |
| `autopilot/plan.md` | Human-readable mirror of the plan. |
| `evaluations/director/` | Director opinions (`type: director-opinion`) for the book, chapters and paragraphs. |
| `evaluations/readers/` | Simulated reader evaluations and panel summaries. |

Chapters, paragraphs, canon entries, resumes and `plot.md` use the normal Narrarium formats and pass `validate_book`/`doctor_book`. Run `sync_plot`, `sync_all_resumes` and `sync_story_state` to regenerate the deterministic maintenance files after an autopilot session.

## Where it runs

- **In the browser**: each step is a local commit in the book's working copy; GitHub books are published as the author chose (every chapter unless chosen otherwise). Only one tab runs a book at a time; other tabs follow it live and can pause it, take a pause back, change the options that may change during a run, or send interventions.
- **On the personal server** (`npx narrarium-server`): the autopilot keeps working with the browser closed. GitHub books travel through GitHub (the server pushes after every step unless the author chose otherwise); local books are exchanged with a three-way file sync. The browser follows the server live.

### The Autopilot page

A control band stays at the top of the page and reads only what the engine already publishes: the status, the host and how long ago the run was last heard of (the newer of `summary.runner.heartbeatAt` and the last event the tab received), the step in progress with the text it streams (`live`; a step that answers with a value has no text to show, so while it answers the row says «The model is answering… (12 KB)» from the `bytes` of `task-progress`, one report a second, in every layout of the band and shortened in the mini-player: numbers only, never a word of the reply, and in no live region), the progress (`summary.progress`), the phase, the steps of the chapter in progress (derived from the activity log and the review cycle: write, readers, specialists, director, fix) and the cost and token use against the budgets (`summary.stats`, `options.budgetLimit`, `options.budgetTokens`). Right under it come the things that wait for the author, each shown once: the director's question, the error, the problems of a profile file, a plan to approve. The rest of the page is the history and, apart from it, the plan, the interventions, the rules, where it runs, the settings and a danger zone with **Reset** (which asks first). The history is one timeline made of what the web app already receives: the steps of the activity log (`AutopilotSnapshot.activities`, the last 200) and the events of the feed (`insight` and `sync` notices, which name their step with `activityId`; the `failureRetry` and `conflictRetry` notices, which name none; `run-started` and `run-ended`). It is grouped by chapter and by round of the review. The numbers of the rounds and their votes come from the plan (`state.plan.chapters[].rounds`, engine 0.1.6: the director's vote of each round, the readers' average of the first one, what the director accepted and rejected): the log keeps only the last 200 steps, so when a chapter has more recorded rounds than the log has reviews of it, the first ones are counted from the record, and a round has the vote and the verdict the plan recorded (`rounds[].verdict`, `approve` or `revise`, engine 0.1.8: what the round decided, which is not always what the model wrote, because an approval under the approval score of the director is withheld; the words of the review in the log are the fallback for a state that has none). A record that is shorter than the log's reviews of the chapter is not used (the page can hold a step of the log a moment before it has the plan that records it, and a vote on the wrong round is worse than none): the rounds are then numbered by the log and have what their reviews wrote. The verdict of a round is not in the record: it is read from the result line of the director's review (`approve 8/10 — …`) in one function, and a round whose review the log no longer has shows its vote and no verdict. For a state that has no record (an older engine), the round of a step is the number of director reviews of its chapter that finished before it, plus one (the closing of a chapter stays with the review that approved it). The group of the review of the book has the verdict and the score of `finalReview` (`summary.finalReview`; the log's `final` step is the fallback). A step that failed and was repeated is one row with its attempts (the activities that repeat a step that did not work: same kind, chapter, scene and reader), a retry notice belongs to the attempt that failed just before it, and a failed attempt says what kind of failure it was (`errorKind`) and which retry it belonged to (`errorDetail.attempt`, `errorDetail.retries`), also when the feed has no notice of it. The grouping lives in `autopilot/timelineModel.ts`, pure. The step that runs has no row (the band says what it is); its text, whole, is at the top of the list. The mini-player leaves out of its list what the page lists. The layout follows the width of the page and not of the window: two columns when it is wide; four tabs (Overview, Timeline, Plan, Rules) when it is not, with the Plan open while the plan waits for the author; on a phone the quick commands move to a bar at the bottom. A finished book offers to add chapters, and a card under the band, `AutopilotResult`, says how it went: the director's verdict on the whole book (`summary.finalReview`, whose words the page takes whole from `state.finalReview` when it is the same review; the log's `final` step is the fallback for a state that has none), the figures of the run (`summary.progress`, `summary.stats`, with the working time from `stats.workedMs`, the sum the engine counts over every run, and, for a book that was begun before the count (`stats.workedMsSince` is more than an hour after the state was created), «counted since» that day; without it the sum of the log, said to be a minimum when the log is full), how the chapters scored (the final score of each chapter and the votes of its rounds, from `state.plan.chapters[].rounds` (a round that sent the chapter back for fixes is marked with ↻ and said in words, when the plan records the verdict), in a picture with a text alternative and a table that a screen reader can read, windowed for a long book, with the lowest scores first on request), the three chapters to read first (the lowest final scores and the chapters that needed many rounds, each with the reason in a line) and the ways to read, export, ask the director and add chapters. What a state does not have (a verdict, a time, the rounds) is not shown and not made up. `autopilot/resultModel.ts` and `autopilot/bandModel.ts` are pure.

A run that ends with an error, and a run that waits to try a failed step again, have one panel under the band, `ErrorPanel`. It reads `summary.lastError` (`kind`, `detail`, the message) for a run that ended, and `summary.status === "running"` with `summary.retry` (`at`, `attempt`, `retries`) for one that waits; the kind (`network`, `auth`, `rate_limit`, `timeout`, `truncated`, `refused`, `conflict`, `budget`, `limit`, `profile`, `config`, `provider`, `unknown`) gives the title, the explanation and the actions, `detail` says where it happened (the endpoint, the model, the provider, the integration by the name the settings give it, the status, which retry), and the step and the number of attempts that failed in a row with the same words come from the log of the steps and the events the page heard: the step is the activity whose id `lastError.activityId` names (engine 0.1.8; when the log does not have it there is no step, and none is guessed from the clock), and a state without the id is matched by the time of the error, as it always was. Two details are said beside the facts, outside the alert, because they can differ from one attempt to the next: for a `timeout`, which limit ran out (`timeoutPhase`: waiting for the response to begin, silence between two pieces of it, or the total limit of 4 hours) and how long it was (`timeoutMs`), with the name of the field of the integration that changes it («Provider timeout», «Idle timeout»; the total limit cannot be changed); and, after a 429 or a 503, how long the provider asked to wait (`retryAfterMs`), next to the countdown. A browser can read `Retry-After` from another origin only when the provider exposes it (`Access-Control-Expose-Headers`); the personal server always can. A `config` error (engine 0.1.8: «Tools only» is on and no model of the step can call a function, so nothing was sent) says so in the alert, with the models that were left out, leads to **AI Integrations** and to the **Tools only** switch of the AI Router (`/app/settings/ai-router#tools-only`), and offers no **Retry now** while `toolsOnlyReport(settings)` still finds a task without a model that can call functions: the same configuration would give the same error. The own **Retry** of the band is the same for every kind, and it is not touched: it fails at once, with nothing sent. A state that an older engine wrote has no kind: the panel is an error with the words as they were, and the refusal to rewrite a file whose front matter cannot be read is read from the words as a profile problem. The countdown is counted from `retry.at`, the engine's clock, in a `role="timer"` that is not announced and outside the `role="alert"`; a polite status says when the wait begins and when it is over. The retry goes away with the `state` event that has none (the page keeps the newest summary it has heard, whole). **Copy diagnostics** copies a short English text with the category, where it happened, the message with no key and no path of a disk, the versions of the app and of the engine and the time. The mini-player and the list of books keep a short notice with the kind of the failure and, in the mini-player, the way to the page. `autopilot/errorModel.ts` is pure.

The mini-player of the web app (the Autopilot button next to Copilot) shows the state, the step in progress, the progress and the commands of one book, and in its "Live" tab one line for each of the latest events of every book. It keeps out of the way on the Autopilot pages, where the page shows all this, and keeps clear of the buttons and the fields of the assistant on a phone.

### Quick commands

The web app puts the commands the author reaches for most in one bar (the control band of the Autopilot page, which becomes a bar at the bottom of the screen on a phone; the "This book" tab of the mini-player; and its "Live" tab for the book in focus). They all go through the engine, once, so the browser and the server behave the same:

- **Pause** `now`, `after-step` or `after-chapter`, and **cancel** a pause that waits (`session.pause`, `session.cancelPause`; `summary.pausePending` says what waits).
- **Run one step or one chapter**: a start with `limits: { steps: 1 }` or `{ chapters: 1 }`, for that run only (`summary.limits`).
- **Publish** never, every chapter or every step: `options.publishEvery`, which `session.updateOptions` changes during a run (`summary.publish` says what is in force). A browser publishes from both hooks, `afterCommit` (every step) and `afterChapter`.
- **Where it runs**: a handover plan per book, an intention of the tab that made it. It asks the run to pause (after the step, or now), waits until it has ended, moves the book (`moveToServer` or `moveToBrowser`: the same consents and conflict handling as "Where it runs"), and starts the autopilot on the other side only if it was running; with a number of steps it runs that many there (`limits.steps`) and comes back. A move that cannot be made leaves the book stopped where it was, with the reason; a failure after the move (the start on the other side, the way back) does not move the book back, and the message says where it is. A handover never sends a secret: a server that lacks the AI configuration or the book's GitHub token sends the author to "Where it runs".
- **Older servers** that do not announce `autopilot-controls` ignore `limits` and take `after-chapter` and `cancel` for `after-step`, so the web app does not send those commands to them and says which version of the server has them.

### The personal server

- **Pairing and identity**: the browser pairs with a nine-digit code generated in the server's admin panel (`http://127.0.0.1:24243`) and approved there by the owner. Before sending its token, the browser asks the server to sign a fresh nonce with its Ed25519 key and compares the key's fingerprint with the one remembered at pairing.
- **Permissions**: each client token carries `read`, `write`, `run` and, only when the owner allows it, `update`.
- **Updates**: a client with `update` (or the admin panel) can ask the supervisor to install the latest npm release. The supervisor installs it only when it carries the npm registry signature and the provenance attestation of this repository's publishing workflow, and only when no autopilot is running. A failed installation keeps the previous version.
- **Network**: the server listens on `127.0.0.1` only and calls only the AI endpoints approved by its owner. Remote access goes through HTTPS, for example the Cloudflare connector managed from the admin panel.

See the [`narrarium-server` README](../packages/server/README.md) for commands, data folders and the release procedure.

## AI router tasks

The autopilot uses the router tasks **Autopilot** (writing), **Director**, **Reader evaluation**, **Reader evaluation summary**, **Review** (specialists) and **Simple tasks**. Tasks without a route fall back to models tagged `default`. For long scenes, set the context window and the max output tokens of the models.

**Tools only** (`settings.aiToolsOnly`; the switch is at the top of the AI Router page, and it is on unless the author turned it off) makes every agent of the autopilot answer through its own function: a model marked as without tool calls (**Forced tool calls** off, in the card of the integration) is skipped, and a reply in text instead of the call is refused. The engine's own functions decide it (`pickAiRuntimeConfig`, `resolveAiCandidates`, `applySameBoundaryPolicy`), so the page does not repeat the rule: `router/toolsOnly.ts` asks them which tasks of the autopilot would skip a model or have none left, and the page says so under the switch and on the rows of those tasks. A task with no model that can call functions stops the run with a `config` error. Once the author has switched it the value is stored as a boolean, every copy of the settings keeps it (the cloud, the offline cache, the account replicas), the personal server receives it as `toolsOnly`, and it cannot be changed offline.

The **thinking** is chosen per route (a column of the text table) and per integration (**Default thinking**, in its card): the level of a route wins, *Automatic* sends nothing even when the integration has a level, and a route with no level takes the integration's. The **Default** row has no level of its own: it only chooses the endpoint of the tasks that have no route, so those tasks go out with the level of the integration, and the row says so and links to the card.

How a level reaches a model is the setting of the model, its **Thinking parameter** (`reasoningParameter` of the chat model, in the card of the integration next to **Forced tool calls**): `reasoning_effort` (the default, the OpenAI field), `chat_template_kwargs.reasoning_strength` (the argument of the chat template, which Muse Glimmer takes and llama.cpp reads in place of `reasoning_effort`) or `none` (no level is sent; it does not turn thinking off). The card suggests the chat-template form for the names the engine's `suggestedReasoningParameter` knows (Muse Glimmer today), only while the model has not said, and never applies it by itself; what is stored is exactly what the author chose, the default included. The engine, on the browser and on the personal server alike, and the site's own requests (the Copilot) follow the same word of the model, and a value this version does not know is kept as it is and not used.

## Slow models

Each AI integration has three settings for a slow model, read by the engine in the browser and on the personal server alike (`pickAiRuntimeConfig`). **Provider timeout** (`requestTimeoutMs`) is how long the provider may take to start answering: 10 minutes when empty, never under 30 seconds (a lower value is raised when the call is made, and the setting keeps what was written). **Idle timeout** (`idleTimeoutMs`) is the longest silence between two pieces of a streamed reply: 10 minutes when empty, kept between 30 seconds and an hour in the page, which clamps what is typed. **Streaming** (`streamMode`) is Automatic by default, which streams every request, the structured ones of the autopilot included; **Off** is only for a provider that refuses streamed replies together with function calls (an HTTP 400 that mentions stream, whose message tells the author to set "Streaming" of the integration to off), and then the provider timeout counts the whole reply. Automatic is stored as no value, so a settings file of an older app is unchanged, and the three fields go wherever the integration goes: the cloud settings, the offline cache, the account replicas and the AI configuration sent to the server. A server older than 0.1.7 ignores the last two. Copilot, voice and images do not use the engine's client: they count `requestTimeoutMs` as the time of the whole request (60 seconds when empty), and the hint under the field says so. See *Timeouts and streaming* in the [engine README](../packages/engine/README.md).

## What the debug panel keeps of an attempt

The panel of AI requests keeps metadata only, never a prompt or a reply. For each chat attempt of the autopilot it adds what the engine says through `onAttempt` and `onAttemptEnd`: whether a structured answer was asked for as a function call or as JSON in the message, whether the request streams (and whether the reply was read as a stream), the level of thinking that was sent (and, when it went as the argument of the chat template, that), whether the function was called, the models «Tools only» left out, the time to the first byte, the state of «Tools only» and the deadlines the attempt ran with, and which of them ran out. Every field is optional, so an entry saved by an older version shows none of them; the store keeps only flags, numbers and the few words the engine uses, whatever it is given, and the history keeps its limit of size. `debug/attemptBadges.ts` is pure and turns the fields into the badges of the panel.
